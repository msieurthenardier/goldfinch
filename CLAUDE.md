# CLAUDE.md

Goldfinch — an Electron desktop browser with a media panel (scan/play/download page media) and a privacy panel (Shields + cookie-jar identities).

## Commands

- `npm start` — run the app
- `npm run dev:automation` — canonical dev launch (`scripts/dev-launch.mjs`, WSL/headless friendly); dev-only, profile-isolated. Add `GOLDFINCH_AUTOMATION_ADMIN=1` when admin-tier MCP ops are needed. **Two consumer models, don't conflate**: script harnesses that re-capture the printed key each run add `GOLDFINCH_AUTOMATION_DEV_MINT=1` per launch (prints one parseable `AUTOMATION_DEV_MINT {"key":"<jarKey>","adminKey":"<adminKey>"}` line, both keys shown once) and attach via env-key scripts (`scripts/lib/mcp-client.mjs`); MCP clients holding a standing token in a static config (e.g. a `.mcp.json` entry — a legitimate, documented attach path) mint ONCE, then relaunch WITHOUT `DEV_MINT` — every re-mint **replaces** the stored per-jar/admin key hash, so a stale static config starts 401ing. Launch states, key capture, attach recipes, ozone/WSLg notes: `docs/dev-testing.md`; full MCP reference (incl. `.mcp.json` registration): `docs/mcp-automation.md`.
- `npm run dist` — build installers (electron-builder); `npm run pack` for unpacked
- `npm test` — `node --test` over `test/unit/**` (pure security/privacy helpers). For real-environment / UI behavior, drive the running app over the MCP automation surface (`npm run dev:automation`); behavior specs live in `tests/behavior/`.
- `npm run lint` — ESLint, flat config (`eslint.config.mjs`)
- `npm run format` — `prettier --write .` over the whole tree (`.prettierrc`); run before committing
- `npm run format:check` — `prettier --check .`; the CI gate (`ci/tasks/lint.yml`, `.github/workflows/ci.yml`'s "Format check" step) — fails the build on drift
- `git config blame.ignoreRevsFile .git-blame-ignore-revs` — one-time local setup so `git blame` skips mechanical reformat commits (currently just the Leg 1 Prettier reformat, `339e808`)
- `npm run typecheck` — `tsc --noEmit -p jsconfig.json` (all `// @ts-check` files)
- `npm run a11y` — axe-core audit (`scripts/a11y-audit.mjs`) against the RUNNING app over the MCP surface (zero CDP). Verify-only — NOT part of headless CI (needs the live GUI). Violations diff against the curated `ACCEPTED` allowlist baked into the script — only NEW `(rule id, node-selector)` findings fail. Run recipe (attach, audited states, gate tags, fixture, exclusions): `docs/dev-testing.md` → *a11y audit*.

## Architecture

Three processes; understand the boundary before editing.

- **Main** (`src/main/`): `main.js` is the composition root, not the behavior owner. `window-factory.js` constructs each `BaseWindow`/chrome view and owns per-window close teardown; `window-registry.js` owns records `{win, chromeView, tabViews, activeTabWcId}`; `register-{tab,overlay,download,settings,browser}-ipc.js` own their channel families; `app-lifecycle.js` owns ready/restore/activation/quit; `session-runtime.js` owns web-session policy and retention cadence. `shields.js` = Shields config + tracking-param stripping; `jars.js` = container definitions; `trackers.js` = eTLD+1 + tracker classification; `settings-store.js` = app preferences; `internal-ipc.js` = origin-checked bridge for trusted `goldfinch://` pages.
  - **Main↔chrome routing has three classes — classify any new send/handler site before writing it**: (1) **sender-resolved inbound** — chrome-sender IPC resolves its window via `registry.getWindowForChrome(event.sender)`, guest-sender via `getWindowForGuest(event.sender.id)`; window lifecycle events (resize/maximize/…) route to their OWN chrome via the per-window create closure. (2) **broadcast fan-out** — `broadcastToChromeAndInternal` sends to ALL chromes + internal-session contents once globally. (3) **per-tab owner-routed pushes** — every main→chrome send tied to a specific tab resolves the tab's owning window's chrome AT EVENT TIME via `getChromeForTab(wcId)` — never fanned out, never left on a focused-window accessor (event-time resolution is what makes move-to-new-window's re-bind automatic). `getChromeContents()` survives only as a last-focused accessor (registry-tracked, seeded at create AND programmatic `win.focus()` — WSLg-safe, membership-validated) — don't build new code against it when a routing class fits.
  - **Lifecycle split**: `window-factory.js` tears down at `close` in this order: find overlay → tear-off overlay → menu sheet → whole-window closed-tab capture/session snapshot → per-tab side effects + **explicit guest destroy** (Electron never auto-destroys an attached view's webContents). `closed` then removes the record and defers chrome-wc destruction with `setImmediate`. `app-lifecycle.js` owns app-level MCP/store quit ordering. Closing one of N windows never quits; the last close rides `window-all-closed` (non-darwin).
  - **⚠️ Never read `win.*` inside `closed`-or-later handlers** — capture teardown inputs (e.g. `const winId = win.id`) at create time. A destroyed-`BaseWindow` property access throws, and an uncaught throw inside the native `closed` emission aborts the listener chain AND permanently wedges the Wayland close path with zero error output.
- **Preloads** (`src/preload/`): `chrome-preload.js` exposes `window.goldfinch.*` (contextBridge) to the chrome. `webview-preload.js` runs in every web page's **main world** (media scanner + fingerprint detect/farble). `internal-preload.js` is a third, distinct preload for trusted `goldfinch://` pages — context-isolated (opposite of `webview-preload.js`), exposes `window.goldfinchInternal` behind an `INTERNAL_ORIGINS` allowlist check (defense-in-depth; main-side `registerInternalHandler` is the authoritative boundary). Keep the three separate. `webview-preload.js` additionally drives a dedicated **isolated world** (`VAULT_ENTRY_OBSERVER_WORLD_ID`, the codebase's first isolated-world consumer) for vault-capture field reads that must be immune to page-world accessor spoofing — see the Password vault pattern's capture-trigger bullets below.
- **Renderer** (`src/renderer/`): `renderer.js` is the chrome composition/boot root. `chrome/context.js` owns DOM/state references; `tab-controller.js`, `navigation-controller.js`, `media-controller.js`, `privacy-controller.js`, `downloads-controller.js`, `window-controller.js`, `shortcut-controller.js`, `jars-client.js`, `overlay-menus.js`, and `auth-challenge-controller.js` (M21 F3 Leg 1 — the M14 F1 auth-basic/cert-picker challenge subscriptions, extracted out of `renderer.js` into their own sibling controller, deliberately kept separate from `vault-controller.js`) own behavior. `chrome/overlay-dispatch.js` (`createOverlayDispatch(deps)`, Mission 20 Flight 3 Leg 1) owns the generic sheet-activation dispatch switch and the shared overlay-closed sink — every menuType action is an injected dependency; the three controllers' own `handleActivation`/`handleClosed` chains (downloads/vault/site-security) still live in `renderer.js`, chained ahead of it. Each tab is addressed by `wcId`. Popup menus + the new-container dialog render from the main-owned **menu-overlay sheet**, not chrome DOM: chrome controllers own triggers/models/actions; the sheet owns presentation + the APG keyboard contract. The ARIA tab-strip contract remains pinned by `tab-keyboard-operability`.

Key cross-cutting facts:
- **Shields apply to every jar through `session-runtime.js`'s `onSessionCreated`.** Each container/burner/default tab is a session partition; new jars inherit automatically. One `webRequest` listener per event per session — recording and enforcement share it (`applyShields`).
- **Web `WebContentsView`s run `contextIsolation:false`** (preload in the page main world — required for farbling). `nodeIntegration` stays off; preload internals stay module-scoped. Internal views are additionally context-isolated.
- **Web guests run `sandbox:true`** (F2 DD4 — chrome view is the one deliberate, tracked exception, deferred per DD4): a compromised web-guest renderer (a hostile page's V8/Blink RCE) is contained by the OS sandbox instead of running with full user-account privileges. `contextIsolation` stays `false` on web guests regardless — farbling needs the preload sharing the page's main world — so the sandbox restricts the preload's Node API surface, not world isolation; the guest↔preload trust boundary (`nodeIntegration:false`, the `isTrusted` caveats) is unchanged.
- **`asar:false`** in the build config so `src/**` stays as unpacked disk files — required by the internal-page `path.join(__dirname, …)` resolver.
- **Find-in-page is a per-window floating overlay `WebContentsView`** — NOT chrome DOM. `src/renderer/find-overlay.{html,js,css}` + its preload (chrome-class trust), managed by the Electron-free `src/main/find-overlay-manager.js`, one lazy instance per window in the registry record's `findOverlay` slot; main owns lifecycle, positioning, focus, and the find session, and fans `found-in-page` counts directly to it. The guest is never inset — the bar floats over full guest bounds. Per-tab `findText`/`findOpen` stay in the chrome renderer, which drives `find-overlay:open`/`close` (per-tab restore sent AFTER `tabSetActive`) and syncs back via `find-overlay-text` (every query) and `find-overlay-closed` (overlay-side user Esc/✕ only). Close refocus resolves by SENDER: overlay-side close refocuses the guest; chrome-side moves no OS focus. Hidden on internal tabs and while a sheet menu is open. Not in `tabViews` → invisible to `enumerateTabs`, admin-tier only.
- Per-tab privacy data: main aggregates → `privacy-net` IPC → renderer; preload fingerprint counts → `ipcRenderer.send('guest-privacy-fp', …)` (web tabs, not `sendToHost`). Farble config is fetched synchronously at page load — toggling farble needs a reload.
- Persisted state lives in `userData/app.db` (`documents` table, one row per store — see App database). Legacy JSON files (`shields.json`, `containers.json`, …) import once on first boot and are renamed `.migrated`. The jars row is a v2 envelope `{ version: 2, defaultId, containers }`; a v1 bare array migrates on import.
- **The session snapshot is written continuously, debounced (squawk 0073), not only at before-quit/window-close** — `src/main/session-snapshot-scheduler.js`'s `createSessionSnapshotScheduler` (~1500ms trailing debounce, dedupe-by-serialized-string) is armed from every topology-changing site (`tab-create`/`tab-close`/`tab-hide`/`tab-set-active`/the shared tab-move core in `register-tab-ipc.js`, `did-navigate`/`did-navigate-in-page` in `guest-wiring.js`, new-window creation in `window-factory.js`), so a hard kill (installer, crash, power loss) no longer relaunches into a stale graceful-quit snapshot. `isRestorePending` (same file) gates writes while a restored window is still mid-boot-restore (partial `restoreTabs` vs live `tabViews`), releasing once the count catches up or a 30s settle timeout passes; `before-quit` still does its own unconditional write, `flush()`ing the debounce timer first so nothing fires after `appDb.close()`.
- **The password vault is a separate, self-contained substrate** — encrypted `.gfvault` files + `manager.json` under `userData/vaults/` (NOT `app.db`), a main-process-only key hierarchy, a chrome-owned entry/display sheet family, and a fill-only MCP surface. See the **Password vault** pattern below and `docs/vault.md`.
- **Frameless window**: `frame:false` on win/linux (custom minimize/maximize/close controls in the tab strip's `#window-controls` zone, wired via sender-resolved `window-minimize` / `window-toggle-maximize` / `window-close` IPC; Close is the record's `win.close()`, NOT `app.quit()` — the last close rides `window-all-closed`); `titleBarStyle:'hidden'` + traffic lights on macOS. `maximize`/`unmaximize` forwarded per-window over `window-maximized-change` keeps the button's `aria-label`/`data-state` live.
- Drag regions: `#tabstrip` is `drag`; the pill, tabs, and window-control buttons are `no-drag`; a `#tabstrip-drag` spacer guarantees a grab area. `chrome-preload.js` exposes `platform`; the renderer tags `<html>` with `platform-{platform}` for platform CSS.
- **⚠️ `WebContentsView` native-surface gotcha — "DOM correct ≠ render correct."** A guest view is an out-of-process native compositing surface, not a DOM box. Bounds/visibility changes around it can mis-render the composited pixels while every `getComputedStyle`/`getBoundingClientRect` read looks correct. A guest bounds change is a discrete `setBounds` STEP, not an animatable quantity — sustaining a chrome-ramps-while-guest-steps mismatch mis-renders on EVERY platform (operator-confirmed on native Windows; not a WSLg quirk). **INVARIANT: never animate chrome layout that resizes/repositions the guest slot; animate only things that float OVER the guest (find bar, menu sheet — view stacking that changes no layout around it), or make the layout change instant.** Rules: (1) prefer compositor-only properties that change no layout around the guest; (2) "DOM geometry reads correct" is necessary-but-insufficient — the acceptance signal is the rendered surface observed by a human in motion (even `captureWindow` misses inter-frame defects; discrete grabs land on settled frames); (3) gate any mechanism touching the guest region on a cheap on-platform spike; (4) don't attribute a render defect to the rig (WSLg) without a cross-platform control.

## Patterns

### `src/shared/` ESM modules

`src/shared/` is real ESM: pure modules use `export`/`import` with explicit `.js` extensions, loaded via `<script type="module">`. Unit tests `require()` the same file (Node ≥22 synchronous `require(esm)`) — the test runs the exact code the app ships.

- **Two specifier shapes, by consumer.** The `file://` chrome imports disk-relative (`../shared/url-safety.js`). Internal `goldfinch://` pages import **flat** specifiers (`./safe-color.js`) because `internal-page-map.js` owns an exact-match host→pathname→file map, not a directory passthrough — a disk-true relative specifier 404s at boot. Flat imports carry `// @ts-ignore` and type `any` (tsc can't resolve them; backlog, not a bug).
- **CJS-by-design quartet + eslint parse guard.** `automation-dev.js` and `internal-page.js` are **preload-reachable** (renderer-side Node `require` has no `require(esm)`) and MUST stay CJS; `dev-profile.js` and `guest-forward-allowlist.js` stay CJS by zero-benefit ruling. `eslint.config.mjs` binds all four to `sourceType: 'commonjs'`, and the later `src/shared/**` module block's `ignores` entry for them is **LOAD-BEARING** — without it, later-wins re-binds the quartet to `module` and deletes the parse guard (an `export` in a preload-reachable file must FAIL lint, not misbehave at a live boot).
- **Evaluate-seam closed set.** Controller implementations remain module-scoped; `renderer.js`'s composition tail republishes exactly the FD-approved 41-entry set with `Object.assign(globalThis, {…})`. Moving an implementation into a controller does not publish it. Growing the set requires an FD ruling.
- **Defer/module pin (permanent house rule, contract-tested).** Every classic `<script>` on a page that also loads a module script must carry `defer` — a non-defer classic executes during parse, before any module. `menu-overlay.html`'s `menu-controller.js` is the product's one remaining classic script (carve-out).
- **New-shared-module checklist**: module script tag only; internal-page consumers need an exact `internal-page-map.js` route; evaluate-reachable entry points go through the closed-set seam (FD ruling); a new contextBridge method still needs its `renderer-globals.d.ts` entry.
- **Two real-boot defect classes `npm test` can't catch**: (1) `mkdirSync`-before-synchronous-persist — `app-db.js`'s `open()` now does it once for the whole substrate; unit fixtures pre-create temp dirs so the suite never surfaces it; (2) classic-script top-level scope collisions — structurally gone for `src/shared/` (module scope); the old collision nets are retargeted as script-tag contract tests (tag-count guard + defer pin + module pin).
- **Grep-AC convention.** Negative/invariant ACs ("this body must not change", "this literal no longer appears") may specify a literal reproducible grep/diff, with each hit judged exempt-or-real, instead of a unit test.
- **Regex-target mutation pins (Flight 5, M17).** When a source-text pin's `.replace()` target would be an exact multi-line literal, use a wrap-insensitive regex instead (`\s+`/`\s*` between tokens, metacharacters escaped) with a captured-indent replacer function, so a Prettier re-wrap can't silently stale the anchor — keep `assertMutated` guarding every mutation (a no-op `.replace()` "discharges" vacuously). A dispatch-table scan additionally needs a bounded non-greedy lookahead so the match can't cross into the NEXT entry. Exemplars: `test/unit/move-authority.test.js` (captured-indent replacer), `test/unit/tab-drag-invariants.test.js`'s `CALL_SITE_RE` (wrap-insensitive call-site anchor), `test/unit/sheet-automation-gate-invariant.test.js` (bounded negative-lookahead scan, `(?:(?!\n\s*\w+:)[\s\S])*?`). Every re-target from an exact-literal pin to a regex-target one is neuter-verified.
- **MockTimers recipe.** Enable per test (`t.mock.timers.enable(...)` inside the test body — never file-global, which leaks fake time file-wide). Drain with real `setImmediate` around single-step ticks — never one big tick that jumps past intermediate states. Exemplar: `test/unit/automation-find.test.js`.

### Two-point hostile-URL security boundary

`isSafeTabUrl` enforces at two independent points: the renderer `createTab` gate (rejects non-`http:`/`https:`/`about:blank` before `tab-create` fires) and the main `will-navigate` guard (`e.preventDefault()` on the same predicate — blocks bypasses via `window.open` etc.). The shared predicate keeps both in sync.

**PDF-viewer carve-out (M14 F1 DD5) — the ONE relaxation, keep it exactly this shape**: `guardNav` stays strict on all three guest nav events (`will-navigate`, `will-redirect`, `will-frame-navigate`); only the `will-frame-navigate` registration is a wrapper that additionally allows a **subframe** (`isMainFrame === false`, fail-closed when the field is absent) on a **non-internal** guest whose URL parses to scheme `chrome-extension:` with host exactly `PDF_VIEWER_EXTENSION_ID` (`guest-wiring.js`). Web guests carry `plugins: true` (web branch only — internal guests have no `plugins` key, so the viewer can't instantiate there). Top-frame `chrome-extension:` navigations stay refused on every event; never widen the carve-out (unit-pinned matrix in `guest-wiring.test.js`).

### Recurring module shapes

Default choices for new logic:
- **Electron-free, injected-deps modules** (main-side): live Electron handles (an fs path, `app`, a view constructor) passed as constructor/call arguments, never `require('electron')` — the logic runs offline under `node --test` with fakes. Exemplars: `automation/engine.js` (`deps()` rebuilt per call), `settings-store.js`, `internal-assets.js`, `menu-overlay-manager.js`, `find-overlay-geometry.js`.
- **`src/shared/` ESM pure decision modules**: e.g. `jar-page-model.js`, `inherit-container.js`. A module consumed only main-side stays plain CJS (`guest-forward-allowlist.js`).

### Internal `goldfinch://` pages — trusted-embedder security model

Three equally-privileged internal origins: `goldfinch://settings`, `goldfinch://downloads`, `goldfinch://jars`. The trust boundary is **"internal vs web," never per-page** — all internal pages share the same `goldfinchInternal` bridge and can call any `registerInternalHandler` channel. Security-critical; treat as such.

- **The welcome surface is NOT a fourth internal page (M16 F2 Leg 1, DD1).** It is a chrome-owned tab (`tab-controller.js`'s `openWelcomeTab`/`attachView`, `welcome-controller.js`) with no `goldfinch://` URL at all — none of the gates above are engaged, widened, or bypassed by it. `welcome-controller.js`'s `show(tab)` delegates to `settle(tab)`, the single place that decides what happens to a welcome record (rewritten M16 F3 HAT items 3 and 6, DD7 pivot): each block's visibility is `tab.welcome.reasons.has(x)` alone — why the tab was opened, never whether the preference is still unset — so making a choice never hides its own block; `render(tab, opts)` draws whichever blocks the record's reasons carry, reflecting each one's saved value and a confirmation line once set. `settle` attaches the tab to a search URL only when a pending query is waiting and an engine has resolved (M16 F2 Leg 2, DD3); every other case re-renders in place — `submitHome`'s successful Set saves and stays rather than attaching, and there is no other fallback (the old defensive hide-panel/address-bar-focus branch and the `unsetReasons` helper it depended on are both gone — every welcome record's reasons always include `'home'`, so the branch they guarded was unreachable). `render`/`settle` accept a `{ search }`/`{ home }` override for the value just written, since the `settings-changed` broadcast that refreshes the live cache may not have landed by the time a submit's continuation runs. A block, once shown, stays visible for the life of that tab even after its preference is set by any path (this tab's own submit, Settings, another window) — but never eagerly refreshes: `onSettingsChanged` re-settles only the currently-shown record, and a background welcome record whose preference was filled in elsewhere catches up via `settle` the next time `show(tab)` is called on it (e.g. switching to that tab), not while it sits off-screen. Both blocks render together on a fresh profile (`DEFAULTS.homePage`/`searchEngine` both `null`, M16 F2 Leg 2 / DD5) — first launch, and every new tab thereafter, until at least one preference is chosen. The engine block renders `src/shared/search-engines.js`'s `SEARCH_ENGINES` table via `createElement`/`textContent` (no engine data hand-typed in the chrome), with the heading `Where should we search for "<query>"?` when a pending query exists. **The surface's DOM contract is frozen (M16 F3 Leg 1, DD2).** Every id, class hook, and `.hidden` toggle the behavior specs and `welcome-controller.js`'s own logic read — `#welcome-surface`, `#welcome-heading`, `#welcome-home-block`, `#welcome-home-input`, `#welcome-home-set`, `#welcome-home-status`, `#welcome-burner-note`, `#welcome-engine-block`, `#welcome-engine-heading`, `#welcome-engine-options`, `.welcome-engine-row`, `#welcome-engine-<id>` radios, `#welcome-engine-status` — is a contract, not an implementation detail: a visual restyle may add wrapper elements, classes, and attributes around them, but must never rename, remove, or change the toggling of one of these hooks. `test/unit/search-engines.test.js`'s DOM-contract structural test pins the id set, the `welcome-engine-` radio prefix, the `welcome-engine-row` class, and the `render(tab)` `hidden` toggles by reading the controller source — it goes red the moment any one id assignment is removed.

- **Scheme + session.** `goldfinch` is registered privileged (`{ standard: true, secure: true }`) at module load (before `app.ready`, which `registerSchemesAsPrivileged` requires); `standard: true` is load-bearing (real origin semantics + CSP). Pages are served from a dedicated in-memory internal session (`session.fromPartition(INTERNAL_PARTITION)`) whose `protocol.handle` is **session-scoped** — the global `protocol` would bind the default session.
- **`INTERNAL_PARTITION` is single-sourced** in `src/shared/internal-page.js` — import byte-for-byte, never re-type. Literal drift silently resolves a different session, the `__goldfinchInternal` marker goes absent, and every gate fails open.
- **CSP is stamped IN the response** (`INTERNAL_CSP` in `main.js`) — custom-protocol responses bypass `webRequest`/`onHeadersReceived`, so that hook would silently never fire. Do not relax the CSP without a security review.
- **The internal route map is owned by `src/main/internal-page-map.js`** (`createInternalPageMap`) and resolved per request by `createResolver` (`internal-assets.js`). It is a host → pathname → absolute-file exact map, traversal-proof by design: no path arithmetic on `url.pathname`. New subresources get explicit entries; never a directory passthrough.
- **The four gates** (defense in depth): (1) trust is **call-site provenance** — `createTab(url, container, { trusted: true })`, never inferred from the URL; the page-reachable `onOpenTab` route passes no flag, so web content can never select the internal branch; (2) the trusted branch validates with the `isInternalPageUrl` allowlist; the untrusted branch uses `isSafeTabUrl`, which rejects `goldfinch://`; (3) session-aware `will-navigate` — the internal session may navigate only within `isInternalPageUrl`; web views keep the stricter rule; (4) the protocol handler lives on the internal session alone — web tabs literally have no handler for the scheme.
- **NEVER widen `isSafeTabUrl` to admit `goldfinch://`.**
- **Chrome-fetch invariant (Mission 13 Flight 1): no page-controlled URL is ever fetched by the browser chrome outside the owning jar's session.** This is structural, not conventional: the chrome CSP forbids remote `img-src`/`media-src` origins (`img-src 'self' data: blob: goldfinch-media:; media-src 'self' blob: goldfinch-media:` — no `http:`/`https:`), pinned by `test/unit/csp-pins.test.js`. Favicons are fetched main-side in the guest's own jar session and delivered to the chrome as `data:` URLs (`favicon-fetch.js`). Media-panel remote URLs (thumbnails, posters, inline video, lightbox, docked audio) route through the `goldfinch-media:` proxy scheme below — never a direct `http(s):` assignment in `media-controller.js`.
- **`goldfinch-media:` scheme** (`src/shared/media-proxy.js`, `src/main/media-proxy-handler.js`): a session-scoped proxy, registered ONLY on the **default session** (`{ stream: true }` privileges) — the inverse trust direction from `goldfinch://`'s internal-session-only registration, but the same structural argument: jar-partitioned guest sessions have no handler for either scheme. `toMediaProxyUrl(wcId, url)` wraps only `http:`/`https:` targets into `goldfinch-media://proxy/<wcId>/<encoded url>`; every other scheme (`blob:`, `data:`) passes through unchanged — a call-site can never accidentally break blob-backed items by wrapping them. The handler resolves the live guest via `getTabContents(wcId)`, forwards the request through that guest's OWN session (`wc.session.fetch`, carrying `Range`/`Accept` only), and re-wraps the response with an allowlisted header set — the same re-wrap discipline as `handleInternal`, but streaming (no full-body buffering, required for media Range/seek to work at all).
- The internal view runs `contextIsolation: true`, `sandbox: true`, `preload: internal-preload.js`. The internal session is excluded from the web-content wirings (`applyShields`, downloads) via the `creatingInternalSession` flag + the `__goldfinchInternal` marker.
- **Address bar**: `updateAddressChip(tab)` (called from every address-sync site) sets internal/web/neutral chip state and makes the input `readOnly` on internal tabs. `#address-chip` also triggers the site-info popup (sheet-rendered; model from the shared `deriveSiteInfo`, `src/shared/site-info.js` — the one derivation source). "Site settings →" (`openSiteSettingsTab`) navigates an existing Settings tab **specifically** (host-only match, fragment- and path-blind — M16 F2 Leg 1, DD10; never any other internal tab) — or opens a new trusted one — to `goldfinch://settings/#privacy`. `navigate()` on an internal tab reroutes any non-internal URL to a new web tab (the UX half of isolation; the origin-checked `registerInternalHandler` is the security half).
- **Adding an internal page**: entry tree in `internal-page-map.js`; host in `INTERNAL_HOSTS` (`url-safety.js`); origin in `INTERNAL_ORIGINS` (both `internal-ipc.js` and `internal-preload.js`); open via the trusted `createTab` path — never by relaxing web gates. **`test/unit/internal-page-route-closure.test.js`** is the standing guard any route/allowlist widening is expected to pass — it walks the transitive relative-import closure of every internal page's routed modules and fails if any module in the graph lacks its own `internal-page-map.js` route (the same citation role `csp-pins.test.js` plays for the chrome-fetch invariant above).
- The downloads page's `internal-downloads-*` channels resolve the actionable `savePath` MAIN-SIDE by id. `src/main/jar-ipc.js` is a composition facade: registry/default twins live in `jar-registry-ipc.js`, data/retention twins in `jar-data-ipc.js`, and shared wipe/sweep sequencing in `jar-data-lifecycle.js`. Chrome and internal twins still execute the same named handler bodies. A successful wipe broadcasts `jar-wiped { id }` so chrome controllers close the jar's open tabs.

### `goldfinch://jars` page

### Settings store (`src/main/settings-store.js`)

The canonical home for app preferences — do not scatter new prefs into ad-hoc constants or `shields.js`.

- **Electron-free**; `userData` injected at `load(userDataPath, opts?)` (called from `init-profile.js`'s `initProfileAndStores`, after `appDb.open`).
- Persists via the app-db `documents` row `'settings'` (transactional UPSERT). Write errors propagate. `load()` **never throws** — each field is validated per-key against `DEFAULTS`; a corrupt field silently repairs to its default, valid siblings kept, unknown keys dropped. The app must boot on a corrupt row.
- `VALIDATORS` maps each settable key to a predicate; `set(key, value)` validates **before** mutating and throws `TypeError` on unknown keys/invalid values. `homePage` requires `null` or (`isSafeTabUrl(v) && v !== 'about:blank'`) — `''` is never valid; `null` is the only unset representation (M16 F1 / DD2, `jsconfig.json` runs `strict: false` so this is enforced by the validator and unit tests, NOT by `strictNullChecks`). `searchEngine` requires `null` or membership in the curated table `src/shared/search-engines.js` exports (an ordered `{ id, label, template, description }` list, also consumed by the renderer's search-URL construction) — never a user-supplied URL template; an id removed from the table, or any other corrupt/unknown value for either `homePage` or `searchEngine`, repairs to **unset** (`null`) at load (M16 F2 / DD5 — repair-to-default no longer means silently selecting a provider or a home page on the user's behalf).
- **Schema `version` is 3, and the v2→v3 bump was a deliberate departure from this store's own ladder convention** ("only for changed defaults on existing keys" — see the `automationEnabled` comment in `DEFAULTS`). No default changed at v3; the bump existed solely to force `load()`'s save-on-migrate persist to write `searchEngine` and `homePage` explicit to disk for every profile that had run the Flight-1 build (M16 F1 / DD5) — including a row-less profile (pinned via a best-effort `save()` at the end of `load()`'s no-row branch) and a corrupt document row (also pinned, not just repaired in memory — closed by design review; a corrupt *legacy `settings.json` file* already saved unconditionally on the other import path). Rule of thumb: **any load path whose resolved config differs from the on-disk bytes persists the resolved config.** `migrateStored()`'s per-rung transforms are individually guarded on their own `from` threshold (not the single "from < current version" check that only worked while there was one rung) so a v2 row doesn't re-run the v1→v2 `restoreSession` discard.
- **`DEFAULTS.homePage` and `DEFAULTS.searchEngine` are `null` (M16 F2 "The Welcome Surface" / DD5) — NO v4 bump.** Flight 1's v2→v3 pin-on-load had already written both keys explicit into every profile that ran that build, so there was no on-disk population left for a v4 ladder transform to reach; the pin-on-load mechanism itself is unchanged, only what it pins (a row-less profile now gets `null`/`null` pinned explicit, not a Google-flavored default). A fresh profile therefore has neither preference set; the chrome-owned welcome surface (below) is what asks.
- **Pluggable `{ serialize, deserialize }` codec seam** — a future `safeStorage`-backed codec replaces only that pair. Do not add encryption now.
- **`toolbarPins` gotchas** (apply to any object-typed key): the no-validator `typeof` fallback wrongly accepts `null`/arrays — object keys need an explicit validator. `NORMALIZERS.toolbarPins` deep-merges the stored value over `DEFAULTS.toolbarPins` at load AND in `set()`, so the object is always fully populated and a new pinnable key needs no migration — it fills with ITS OWN default (media/shields `true`, devtools `false`; there is no general filled-as-`true` rule). `getAll()` deep-copies the nested object so callers can't mutate live config.
- **`homePageCache` (`renderer.js:51-52`) now has the `searchEngineCache` shape (M16 F2 Leg 1, DD4 — squawk 0005 CLOSED).** It is boot-seeded explicitly (`window-controller.js:132`, the `toolbarPins`/`bookmarksBarEnabled` idiom below) AND kept live by the `settings-changed` handler (guarded `!== undefined`), so every window — including one opened after a home-page change — is current within one IPC round-trip. `setHomePage` (`renderer.js:503`) stores the value **raw** — `null` (unset) survives the cache and `currentHomePage()` returns it as-is; the deleted `HOMEPAGE` constant and its three `|| HOMEPAGE` coalescing sites are gone. `openNewTab(container?)` (`tab-controller.js`) is the one place that resolves the cache into an action: `homePage == null` opens a viewless welcome tab (`openWelcomeTab`) instead of a real one. The one boot-time `settingsGet('homePage')` (`renderer.js:1536`) still feeds only the FIRST tab directly (a read of the same source, not a cache write) — it and the boot seed may race; both write identical source data, so last-writer-wins is benign.
- **`searchEngineCache` (`renderer.js`) is the same corrected pattern (M16 F1 Leg 2, DD4), matched by `homePageCache` above; pre-seed value corrected to `null` (M16 F2 Leg 2, DD5) — a truthy placeholder would have routed a search typed before the boot seed lands to a provider nobody chose.** It is boot-seeded explicitly (`window-controller.js`, the `toolbarPins`/`bookmarksBarEnabled` idiom above) AND kept live by the `settings-changed` handler, guarded `!== undefined` — never truthiness, since `null` is a meaningful unset value per DD2 — so every window is always current within one IPC round-trip. `setSearchEngine` stores the value **raw**, no coalescing in the setter. `navigation-controller.js`'s `toUrl` no longer coalesces at all (M16 F2 Leg 2, DD3 — the app's last engine-coalescing read site is gone): a search with `currentSearchEngine() == null` returns `null`, and `navigate()` routes that into the welcome-surface search handoff below rather than ever resolving a query into a URL nobody chose a provider for. `goldfinch://settings` renders a radio group in `#appearance`, adjacent to the home-page control, from `src/shared/search-engines.js`'s `SEARCH_ENGINES` table (served to the page via the `internal-page-map.js` `/search-engines.js` route) — no engine id/label/description is duplicated in the page markup or its controller script; selecting an engine writes through the existing `internal-settings-set` bridge (DD3, no new IPC) and every open window's address-bar/context-menu search updates live via the cache above. A "Clear" button beside the radio group (M16 F2 Leg 2, DD6) writes `searchEngine: null` — every radio unchecks and a hint line explains the welcome surface will ask next time; a non-null broadcast re-checks the radio and clears the hint. The home-page field carries the same symmetric unset hint (`HOME_UNSET_HINT`, added at this leg's acceptance gate after a behavior-test FAIL on "each with its hint"): a `reflect(value)` helper in `settings.js`'s home-page IIFE sets the input and the hint together, called from both the initial load and the `onSettingsChanged` broadcast handler — so an external write (the welcome surface's Set, another window's Settings page) updates the hint too, not just the field (this also closed squawk 0010's stale-status-line report).

### Menu-overlay sheet

All chrome menus composite above the **live** guest from a transparent overlay `WebContentsView`.

- **Architecture.** A **per-window lazy singleton** (`src/renderer/menu-overlay.{html,js,css}` + `menu-overlay-preload.js`, chrome-class trust), managed by the Electron-free `src/main/menu-overlay-manager.js` (`createMenuOverlayManager`, injected deps, offline-tested), instantiated per window into the registry record's `sheet` slot — two windows can hold open menus simultaneously. Show = `addChildView` **after** the guest (z-order invariant); never focused before model init lands; hide = `removeChildView`; bounds track the active guest via the `tab-set-bounds`/`tab-set-active` hooks; `render-process-gone` → teardown-and-rebuild; destruction at per-window `close`. The sheet covers the **guest region only** (toolbar stays clickable; toolbar-anchored menus render flush at the sheet's top edge). Internal tabs are in scope (only the page-context menu excludes internal guests). Hosted surfaces: kebab, container picker, site-info, page context (+ toolbar-Unpin mode), the new-container `input-dialog`, tab-context, suggestions. Chrome owns triggers/models/actions; the sheet holds **no business logic and no privileged APIs** — it renders the model (labels via `textContent` only — guest/user strings never markup) and runs the APG contract via `menu-controller.js`. Every sheet template's controller entry is composed through the shared **`createSheetEntry`** factory (`src/shared/modal-card-controller.js`, M17 F3 Leg 1) — it wraps `menuController.register` with the show/hide/`reportDismissed`/`focusReturn` envelope plus `onOpen`/`onClose` hooks (the factory owns the trailing hide + `reportDismissed`; the hooks carry the sheet-specific show/focus on open and the scrub/field-reset/drop-ref middle on close). It injects `register`/`reportDismissed` rather than reaching a global, so each sheet lifecycle is unit-testable with mock nodes.
- **Channel protocol (1–7).** 1 `menu-overlay:open` (chrome→main: `{menuType, model, anchor, startIndex, token}`); 2 `menu-overlay:close` (chrome→main, programmatic — incl. trigger re-click `toggle`); 3 `menu-overlay:init` (main→sheet; **pending-init queue**, latest-wins — absorbs the lazy first-load race); 4 `menu-overlay:activated` (sheet→main: `{id, token, value?}` — `value` sanitized main-side by `sanitizeActivatedValue`, string ≤24 or dropped); 5 `menu-overlay:dismissed` (sheet→main: `{reason, token}`); 6 `menu-overlay-activated` (main→chrome — the dispatch executes the action, validated-no-op on every id); 7 `menu-overlay-closed` (main→chrome — reset `aria-expanded`, resolve refocus per entry policy). On activation, **7 is emitted before 6**. A chrome-minted monotonic open-token rides 1/3/4/5/7; stale-token closes are dropped.
- **Close family.** Every hide routes through `closeMenuOverlay(reason)` — idempotent, the single mutation point. Reasons: `escape` / `outside-click` / `blur` (fired only when the blurred window is the sheet's own) / `activated` / `superseded` (open-while-open = **model-replace**, no hide/re-show flicker) / `toggle` / `tab-switch` / `tab-hide` / `tab-close` / `teardown` / `vault-lock` (M18 F3 L1 — see the blur-survival bullet below). `focusChrome()` runs for `escape`/`activated` only; fixed-trigger menus refocus their trigger; page-context and tab-context are escape-only → captured `returnFocus` else the address bar. A 300 ms same-menuType suppress window (chrome-side, armed on blur closes) kills the trigger re-click close-then-reopen blink.
- **Vault credential sheets survive window blur; lock closes them (M18 F3 L1, DD8 — operator ruling, distinct from the drag-probe "DD8" referenced below).** `vault-unlock`, `vault-set`, `vault-stepup`, `vault-import`/`vault-import-unlock`, `vault-change-master`, `vault-recover`, `vault-compromise`, and `vault-compromise-recover` retain half-entered field state through window blur/refocus — the copy-paste-from-another-secrets-manager scenario, reversing the shipped default. A NEW per-open axis, `survivesBlur` (parallel to `dismissible`/`keepFocus`, never reused — reuse would leak the behavior to non-vault sheets), is decided ONCE at the chrome-side funnel every vault open passes through (`overlay-menus.js`'s `open()`, assigned unconditionally true/false against the shared allowlist `src/shared/vault-blur-survival.js` — no per-call-site override) and threaded through BOTH guard sites: `closeMenuOverlay` ignores reason `'blur'` (and ONLY `'blur'`) for a flagged menu; `menu-controller.js`'s window-blur listener carries an independent, identically-shaped guard. `vault-unlock` IS in the allowlist (the operator's literal scenario); the dismiss-locked one-time-key show sheets and the no-typed-secret `vault-capture`/`vault-picker` sheets are OUT (already covered by `dismissible: false`, or nothing to protect). Accepted trade-off: half-typed secret material persists in a blurred window until submit, an explicit dismiss, vault lock, or window close. **Close-on-lock** is the safety valve this raises the stakes for: every vault lock (manual or idle autolock, both routed through the store's injected `onLock`) fans `closeMenuOverlay('vault-lock')` out to every window's sheet unconditionally; the reason is a HARD close (bypasses the `dismissible` guard) but is SCOPED inside `closeMenuOverlay` to the same allowlist MINUS `vault-unlock` (`closesOnVaultLock`) — never force-closing an unrelated open menu, a show sheet, or the unlock prompt itself (locking is its precondition, not its invalidation).
- **Find interplay.** Sheet-show hides the find overlay; `closeMenuOverlay` restores it as an owned explicit step — except the tab-lifecycle reasons, which defer to `tab-set-active`'s per-tab restore (no double-handling).
- **Hardening.** All `menu-overlay:*` handlers are **sender-validated by webContents identity** (chrome for 1/2; the sheet's own wc for 4/5 — never payload-declared). The sheet is not in `tabViews`: invisible to `enumerateTabs`; non-tab non-chrome wcIds resolve **admin-only** (`isTabViewWcId` threaded into the engine). Sheet automation is governed by the **(menuType × op) gate** — see *Automation engine* below.
- **Four-guard decision channels.** Any state-CHANGING sheet→main channel carries FOUR named guards, in order: sender identity (`recordForSheetSender`), open-token freshness, `current.menuType === '<its menuType>'`, and a business gate. `menu-overlay:cert-override-proceed` (`register-overlay-ipc.js`) is the exemplar, extending the `bookmarks-overflow` drop/drag three-guard precedent with its own entry-derived business gate. A read-only or low-stakes channel (`bookmark-edit-submit`) is NOT the precedent for a decision channel — don't cite it to justify skipping a guard.
- **⚠ Eager close scrub (M15 F3 DD1f) — SECURITY, not tidiness.** There is now exactly ONE main→sheet close channel, `menu-overlay:close` (channel 8), sent by `closeMenuOverlay` **and** by `openMenu`'s model-replace branch when the menuType **changes**; the sheet's handler runs `report.silence()` then `menuController.closeAll()` immediately. This reverses the old *"deliberately NO main→sheet close channel; the hidden sheet keeps its rendered menu DOM"* rule, because that rule is what made a closed vault card's `textContent` co-resident with the next menu: `openMenu` sets `currentMenu` + `show()` **synchronously** and only then `deliverInit` crosses the IPC hop, so a lazy scrub leaves a window where main reports an admitted menuType while the DOM still holds the prior secret — narrower than human timing, therefore invisible to every live check. **Do not "simplify" it back to scrub-on-next-init.** A same-menuType model-replace deliberately does NOT scrub (the downloads in-place repaint needs `menuController.current` intact, and the residue is that card's own prior model). `<body>` data attributes are never cleared (the DD8 drag-probe readback depends on them).
- **Keep-focus opens (channel 9, `menu-overlay:refocus`, sheet→main).** A menu whose SPAWNING gesture also navigates the guest must survive the loading page's focus steal: `openMenu` payload `keepFocus: true` makes the sheet entry `dismissible: false` for that render (skipping the sheet controller's incidental window-blur/outside-click dismissal, exactly the `vault-capture` entry's fix) and makes the sheet report its blur back so `reassertFocus()` re-grabs OS focus — otherwise the card stays visible but unfocused and a typed master password lands in the page's own fields. Main gates the report on sheet-sender identity, `win.isFocused()` (a real app-switch must never pull focus back from another app — that case still closes main-side, `currentDismissible` stays true), and the menu's own opt-in; re-grabs are capped per menu session (`KEEP_FOCUS_MAX`) so a page that re-steals focus on a loop can't start a tug-of-war. Sole consumer: the `vault-unlock` prompt raised for a LOCKED-vault capture (unlock-to-save). Every deliberate decline path is unchanged.
- **Accelerators.** The sheet's `before-input-event` forwards the union set via pure `src/shared/sheet-accelerator.js`: guest-class actions (zoom, print, find, …) replicate against the ATTACHMENT window's active guest (internal-contents guard; Ctrl+F closes the menu then opens find); chrome-class actions ride `chrome-shortcut-action` → `dispatchChromeAction`. Unmodified APG keys (arrows/Home/End/Enter/Space/Escape/Tab) stay with the sheet — the menu contract wins inside the menu.

### Chrome indicators (pure decision models)

The chrome toolbar's status indicators — automation ("robot"), vault ("lock"), and downloads — each split their truth table into a **pure, DOM-free decision model** the chrome renderer `import`s and applies to the DOM. One shape, three instances: the model maps a **pushed broadcast snapshot** to a render model, **never caches** (a pure projection of the *latest* push — the source of truth stays main-side and rebroadcasts on every transition), never throws (malformed/partial input coerces via defensive defaults), and is unit-testable without DOM or clock (the suite `require()`s the same file the app ships).

- **Automation** (`src/shared/automation-indicator-model.js` — `buildAutomationIndicatorModel`, imported by `renderer.js` since the transitional `globalThis` bridge was removed): projects `{enabledJarKeyCount, adminKeyEnabled, activeJarIds, adminActive, containers}` → `{visible, count, mode, color}`. Visible when ≥1 automation key is *enabled* (independent of any live connection); `count` is enabled **jar** keys only. `mode` is `idle`/`jar`/`multi`/`admin` — **`admin` is the rainbow state**, the operator-visible "automation is active at the admin tier" signal, rendered only when the admin key is both enabled AND currently active, and trumping any concurrent jar activity. Color is defense-in-depth: only returned when the single active jar resolves in the live `containers` list AND its color passes `isSafeColor` (`src/shared/safe-color.js`, the product's own color domain), else it downgrades to `multi` — a stale/unknown jarId or an unsafe stored color never throws.
- **Vault** (`src/shared/vault-indicator-model.js` — `buildVaultIndicatorModel`): a pure projection of the pushed `vault-lock-state` payload `{setUp, unlocked}` (DD10 freshness contract, M12 F2) → `{visible, state}`; not-set-up hides (nothing to show), else visible `locked`/`unlocked`.
- **Downloads** (`src/renderer/chrome/downloads-indicator-model.js`, M11 F1): the one instance that accumulates rather than projecting a lone snapshot — a `reduce(state, event)` reducer (seed via `initialState()`) folds the `progress`/`done`/`hydrate`/`acknowledge`/`expire` broadcast stream into an immutable accumulator (fresh Map + array per step, never mutating), and `deriveModel(state)` projects that into `{visible, active, activeCount, recentCount, attention, ariaLabel}`. Still DOM-free and **timer-free**: expiry is time-INJECTED (the caller passes `now`), so the whole idle-window truth table (`IDLE_TIMEOUT_MS` = 5 min, `recent` capped at `RECENT_CAP` = 25 newest-first) is testable without a clock. State is conveyed in WORDS via `ariaLabel`, never color/animation alone.
- **Per-tab pushed-state routing rules (M20 F2, `security`).** (a) A NEW per-tab state gets its OWN owner-routed push channel — never ride an existing push whose chrome handler has unrelated side effects: `tab-security` (`guest-wiring.js`'s `did-navigate` handler) is its own wire, never riding `tab-did-navigate` (whose chrome handler resets media/privacy/suggestions). (b) An indicator never claims a state main has not pushed — no scheme-derived or default guess before the first push: `navigation-controller.js`'s `updateAddressChip` renders `SECURITY_STATES.NONE` for an unpushed/unrecognized `tab.security`, never a `/^https:/` guess. (c) The controller that stores a pushed state refreshes its own rendered consumer in the SAME handler: `site-security-controller.js`'s `onTabSecurity` sets `tab.security` and calls `updateAddressChip` for the active tab in one step; `load-failure-controller.js`'s `onTabLoadFailure` updates the chip UNCONDITIONALLY (a security indicator must reflect real state even while the operator is typing) while gating only the address-bar VALUE write behind the `document.activeElement` check.

### App database (`src/main/app-db.js`)

Durable substrate for the five small config/state stores — settings, downloads, session, jars, shields — on built-in `node:sqlite`. It is a **clone of `history-store.js`'s seams, not a shared import**: `app.db` is independent of `history.db` (separate corruption/quarantine domains; the write-hot visits table never shares a file with config rows).

- **Substrate ruling**: built-in `node:sqlite` (`DatabaseSync`), no vendored native module — preserves the zero-runtime-dependency identity. It's an experimental API (`ExperimentalWarning` at require time is cosmetic, accepted). **Standing tax: every Electron major bump re-runs the full store suite (`history-store` + `app-db` + all five stores) and treats a `node:sqlite` API break as a first-class migration cost.** Decision records live in the respective `flight.md` files (missions 08/10).
- **One `documents` table, one row per store**: `documents(store TEXT PRIMARY KEY, payload TEXT NOT NULL, updated_at INTEGER NOT NULL)`. `createDocumentStore(name)` returns `{ read(), write(payload, now?), remove() }`; every store write is a transactional whole-document UPSERT of its serialized payload (all five are low-cardinality wholesale-replace workloads — the substrate buys corruption discipline + transactional writes, not indexing). Each store's public API, defaults/validators, legacy-shape handling, and codec seam survive verbatim — codec output lands in `payload`, keeping a future encrypted-codec swap codec-only.
- **WAL family + lifecycle**: `app.db` + `-wal` + `-shm` (`journal_mode=WAL`, `synchronous=NORMAL`). `appDb.open(userDataPath)` runs in `initProfileAndStores`; `app-lifecycle.js` then loads the session store from the open singleton. `app-lifecycle.js` closes app/history DBs at **`will-quit`**, after `before-quit`'s snapshot writers; `close()` checkpoints the WAL and is idempotent.
- **Migration — import once, rename `.migrated`**: at each store's `load()`, row-absent + legacy JSON present → parse through the store's existing load/repair logic → write the row → best-effort rename `<name>.json.migrated` (never fatal). A corrupt legacy file still migrates (the repaired result). Once a row exists, bare legacy files are ignored. **Carve-out**: jars' readable-but-unknown-schema-version `containers.json` never migrates — kept in memory, file untouched, so a future compatible build can recover the original envelope (pinned by `jars-security-forward-version.test.js`).
- **Quarantine → fresh defaults**: a corrupt `app.db` (+siblings) is quarantined to `.corrupt-<ms-epoch>` and recreated — the app must boot. Stores seed defaults; `.migrated` files are **never re-imported** (arbitrarily stale by then). Jars' post-quarantine reseed is branch-dependent on the legacy-partition probe (intentional parity with pre-migration behavior).
- Shields is at house discipline (injected `userDataPath`, codec seam, transactional writes). Pre-load `save()` stays a silent no-op, but once loaded a row-write failure **propagates** — `shields.set()`/`setPaused()` can reject through their IPC handlers.
- **`user_version` ladder is cumulative STEPS** (v0 → v1 → v2 in one open; a fresh profile never pauses mid-ladder). v2 adds `cookie_seen(jar_id, name, domain, path, first_seen_ms)` — retention-sweep bookkeeping, metadata only, via `createCookieSeenStore()` → `{ insertIfAbsent, deleteByIdentity, deleteByJar, selectExpired }`.

### History store (`src/main/history-store.js`)

Per-jar browsing history on a live `node:sqlite` handle — real schema/indexes/FTS, unlike the document-row stores (needs range queries + full-text search at scale).

- **Recording** (`src/main/history-recorder.js`, `createHistoryRecorder` — Electron-free injected-deps factory, constructed during `app-lifecycle.js` readiness; navigation hooks are installed by `register-tab-ipc.js`). Gates in order: (1) positive registered-jar allowlist; (2) `http:`/`https:` scheme allowlist; (3) per-jar 30 s consecutive-duplicate suppression. A per-`wcId` map backfills late titles; teardown calls `forgetTab(wcId)`.
- **Retention**: `retentionDays` lives on the jar record (integer 1–3650, default 30, validated by `cleanRetention`). `session-runtime.js` owns `pruneAllJars()`; `app-lifecycle.js` invokes it at store open and schedules the hourly `.unref()` cadence. It builds the live `{jarId: days}` map and GCs orphan history rows. Up to ~1 h over-retention accepted.
- **`history-changed { jarId }` invalidation contract**: every mutation broadcasts only `{ jarId }` — never rows or counts; subscribers re-query through their own read path (invalidation-not-snapshot, same as `jars-changed`).
- **IPC twins** (`src/main/history-ipc.js`): each handler body defined once, registered twice — bare `history-*` (chrome trust) + `internal-history-*` (`registerInternalHandler`). Ops validate fail-closed in order (malformed payload → unknown jar → bad args); every failure returns a **static, non-interpolated** `history: <op> — <code>` string.
- WAL family (`history.db` + `-wal`/`-shm`), closed at `will-quit`; a corrupt db is quarantined to `.corrupt-<ms-epoch>` and recreated.
- **Two live-probed sqlite gotchas**: never mix a bare `?` with numbered `?1`/`?2` placeholders in one statement (SQLite collapses them onto one bound slot); keep FTS5 on the default `unicode61` tokenizer — a `tokenchars` override turns a whole URL into one token and silently breaks prefix search.

### Jars page data panels

The Cookies and Other-site-data panels share the History panel's constructor shape.

- **Cookies panel** (`jars-cookies-panel.js`): lists the jar's live session cookies via `jars-cookies-list` — **never a `value` field, at any layer** (the handler strips it before it crosses the payload). Per-cookie delete reconstructs the removal URL via `jar-data-helpers.js`'s `cookieUrl` (scheme from `secure`; leading dot unconditionally stripped from `domain` — safe for both host-only and domain-attribute cookies). No confirm step (single cookie = low stakes).
- **Other-site-data panel** (`jars-sitedata-panel.js`): a composite union with **two-tier honest labeling** (Electron's `Session` exposes no origin-enumeration or usage/quota API): "Has stored data" = origins with an on-disk IndexedDB leveldb directory (`originFromIndexedDbDirname`; a literal `_0` port segment is Chromium's default-port sentinel, normalized portless — live-measured, not documented); "Visited — storage unconfirmed" = history origins with no IndexedDB confirmation. **Documented gaps — don't silently paper over**: Local Storage is a consolidated non-origin-keyed store (its origins are unrecoverable); never-visited third-party-only and localStorage-only origins are invisible to both tiers; no usage/quota figure anywhere (raw file sizes would mislabel leveldb overhead as user data). Per-origin delete uses the SAME storage-class set as the retention sweep (cookies excluded); a history row survives an origin clear — the origin downgrades to "visited", it doesn't disappear.
- **Freshness**: panels query on tab-SELECTION (not section visibility) and re-query on their own mutations. No live `cookies.on('changed')` UI subscription (page activity would spam every open jars page). Cross-path staleness is closed by the `jar-data-changed { jarId, classes }` broadcast — fired by `handleClearData` (classes actually cleared), `handleWipe` (unconditional), and the retention sweep's **completion** (never the `setRetention` invoke, which resolves before the async sweep finishes).

### Retention sweep (`src/main/retention-sweep.js`)

Generalizes the per-jar `retentionDays` dial (one window, all classes) from history to cookies + site data, riding the same cadence (boot + hourly, plus an immediate one-jar sweep on a retention edit). The engine is Electron-free/injected-deps — every dependency (`cookieSeen`, `historyOrigins`, `sessionFor`, `cookieUrl`, `now`) is a fake in the unit suite.

- **Two independently-aged classes (deliberate, documented asymmetry)**: cookies age by **first-seen** (Electron exposes no cookie creation time — the reason `cookie_seen` exists); storage ages by **origin last-activity** from history (`expiredOriginsForJar`). Origins with no history signal are never auto-swept (no honest age signal; operator-deletable from the panel).
- **Cookie bookkeeping**: the `session-created` hook attaches a `cookies.on('changed')` listener for jar-matching partitions (partition recovered from `ses.storagePath` via `partitionFromStoragePath` — the hook receives only the Session; never an eager `fromPartition` warm, since `session-created` fires only on a partition's FIRST `fromPartition`). **Overwrite-cause ruling (measured)**: a same-identity value refresh fires an `overwrite`/`removed:true` + `inserted` PAIR — the removal handler SKIPS deletion on `cause === 'overwrite'` (the row keeps its original `first_seen_ms`) and deletes on `explicit`/`expired`/`expired-overwrite`/`evicted`; inserts are `INSERT OR IGNORE`. Cold start: a live cookie with no row gets stamped `first_seen_ms = now` at the next sweep — honest, not backdated.
- **⚠️ SEQUENCING invariant (unit-pinned)**: snapshot the aged-out origins BEFORE the same pass's history prune, in BOTH `pruneAllJars` and `handleSetRetention` — the prune deletes exactly the evidence `expiredOriginsForJar` reads; a post-prune read sees nothing for the target case. Order: (1) snapshot, (2) history prune (sync), (3) async cookie/storage sweep from the snapshot.
- Sweeps are async, fire-and-forget, per-jar/per-item isolated; every promise chain ends in a terminal catch (log-and-drop; quit-during-sweep named-accepted). `jar-data-changed` fires on completion with the classes actually swept.
- **Will-quit quiesce guard**: the cookies listener outlives `appDb.close()` — every write checks `appDb.isOpen()` first and is try/caught, so a write-after-close can never throw into Electron's event dispatch and wedge quit.
- **Bookkeeping dies with its data**: per-cookie delete → delete-by-identity; cookies-class clear / wipe / remove → delete-by-jar. All fail-soft — a cleanup miss just re-stamps a survivor as "new" (harmless staleness, never a correctness bug).
- Other named-accepted gaps: ~1 h cadence over-retention; a page can refresh a cookie between the sweep's read and its remove (TOCTOU, bounded by the 1-day window floor).

### Address-bar suggestions

Frecency-ranked, prefix-matched history suggestions, merged with a per-jar bookmarks source (M15 F1 Leg 4, jar-addressed M15 F2 Leg 3), render on the menu-overlay sheet (the only surface that composites below the toolbar — chrome DOM is occluded by the guest).

- The `suggestions` sheet template is `role="listbox"`/`option` (all text via `textContent`); a row click sends channel-4 `{ id: 'sug:<i>' }` — **INDEX dispatch** (`sanitizeActivatedValue`'s 24-char cap forbids a URL riding `value`).
- **`noFocus` regime**: `deliverInit` is the sheet's sole focus site; a channel-1 `noFocus: true` flag gates that call, so keyboard-driven suggestion repaints never move OS focus off `#address` (existing callers omit it, unaffected). A pointer click still moves native focus — the grace timer exists for exactly that race.
- **Chrome-owned close matrix** (the non-focusing regime means no sheet-side blur/outside-click ever fires): Enter-with-selection or row click → `activated`; Escape → `escape` (input keeps focus + text); input emptied → `input-empty`; `#address` blur → `blur` via a 150 ms grace timer whose callback re-checks the captured token AND `document.activeElement` (lets a click's activation win the blur-vs-click race); tab switch → main's tab-switch close, PLUS the brand-new-tab path's explicit `closeSuggestions('navigation')` (`createTab`'s synchronous `activateTab()` precedes any IPC, so the ordinary close never fires there); `activateTab` bumps `suggest.seq` on every activation (invalidates in-flight responses for the previous jar); active-tab navigation → `navigation`. Main's Ch2 handler validates reasons against `MENU_CLOSE_REASONS` (unknown → `superseded`).
- **⚠️ Ch7-before-Ch6 activated nuance**: the Ch7 sink cancels the timers on every close, but clears `suggest.items`/`selectedIndex` only for reasons OTHER than `activated` — the immediately-following Ch6 `sug:<i>` dispatch must still resolve the clicked row from `suggest.items`; the Ch6 handler finishes the reset. A naive reset-on-every-reason silently breaks every pointer-click navigation.
- **Data path**: `history-store.js`'s `suggest(jarId, query, { limit = 6, now })` — age-bucketed frecency (≤4d→100, ≤14d→70, ≤31d→50, ≤90d→30, else 10; grouped by URL) over the FTS-narrowed subset, via the `history-suggest` twins + chrome-only `historySuggest` bridge. `suggest` has its own 1–10 limit clamp (distinct from the store's 1–500). The 1-char query rides an UNCOVERED prefix path (the FTS `prefix='2 3 4'` index) — a full-token scan, measured separately. Bookmarks (jar-addressed `bookmarksSuggest({ jarId, query })`, matched via `matchBookmarks`) are queried ALONGSIDE history via `Promise.allSettled` — never `Promise.all` — so a rejected/`{ok:false}` source degrades to `[]` independently and never blanks the other; results merge bookmark-first (see "Bookmarks" below for the source/cache side).
- **Gates**: pure `omnibox-suggest-model.js` `shouldQuery({ focused, isInternal, isBurner, value })` — burner/internal tabs structurally never query (positive allowlist, no negative exclusion). Scoped to the active tab's own jar. Responses re-validate the FULL gate at arrival (`acceptSuggestResponse`) — a stale response never model-replaces a menu the operator didn't ask for.

### Bookmarks

Jar-scoped end to end (Mission 15 Flight 2): a real `bookmarks` table keyed by `jar_id` (Leg 2), and every chrome consumer — cache, star, bar, overflow, omnibox, favicon writer, popover, page-context — re-derived against the active tab's jar (Leg 3). No `goldfinch://` page reads bookmarks; every consumer lives in the chrome renderer.

- **Store + identity** (`src/main/bookmarks-store.js`, `src/shared/bookmark-url.js`): a jar-keyed `bookmarks` table in `app.db` (schema v3, M15 Flight 2 Leg 2 DD1) — `id`/`jar_id`/`url`/`title`/`icon`/`position`/`added_at`, unique on `(jar_id, url)` (the SAME url in DIFFERENT jars is legal and independent — the feature's core claim), position-ordered per jar (gap-free `0..n-1`, DD2). The store is stateless and jarId-first (`list(jarId)`, `add(jarId, …)`, `update(jarId, id, …)`, `remove(jarId, id)`, `reorder(jarId, ids)`, `clearJar(jarId)`) — the id alone never authorizes a mutation. Flight 1's per-field validate/repair split moved from load-time array validation to READ-TIME per-row validation on `list()` (url/id DROP-worthy, title/icon REPAIRED in the returned copies only — a read never writes back). A corrupt `app.db` now quarantines the WHOLE file (settings/jars/shields/downloads/session/cookie-bookkeeping included), not just bookmarks — the document-row's independent per-store corruption isolation no longer applies (accepted trade-off, DD4); a migration-STEP bug (vs. file corruption) is distinguished by `err.errcode` and propagates instead of quarantining a healthy file (DD-B). `bookmarkUrlsMatch` (exact committed-URL string equality, no normalization) is the ONE identity predicate — the store's `add()`/`update()` dedupe (now per-jar), the chrome cache's `findByUrl`, and the star fill state all share it. `add()` is idempotent PER JAR (a re-add of an existing URL in the SAME jar returns the existing entry, no broadcast); `update()` REJECTS a URL edit that collides with a DIFFERENT existing entry IN THE SAME JAR (`{ok:false, reason:'duplicate-url'}`) rather than merging — the same URL in a DIFFERENT jar is never a collision.
- **Broadcast contract**: every mutation fires `bookmarks-changed` with `{ jarId }` (M15 Flight 2 Leg 2 DD5 — invalidation-not-snapshot, `jars-changed`/`history-changed` precedent) via `broadcastToChromeAndInternal`; subscribers re-query `bookmarksGet({ jarId })`. All six IPC channels are jar-addressed; the four mutation channels reject a `jarId` absent from `jars.list()` with `{ ok: false, reason: 'unknown-jar' }` (covers burner/internal/deleted-jar ids in one rule); `bookmarks-get`/`bookmarks-suggest` skip that check — an unknown jar naturally yields zero rows, and a read must never fail during the jar-delete race window. Lifecycle (DD9): deleting a jar drops its bookmarks (`jar-registry-ipc.js`'s `handleRemove`, its own fail-soft try/catch); the full identity wipe does NOT; a fifth `JAR_DATA_CLASSES` entry (`bookmarks`, mapped to the History panel on `goldfinch://jars`) clears them on explicit request.
- **Chrome cache** (`src/renderer/chrome/bookmarks-client.js`, `createBookmarksClient`, M15 F1 Leg 2, jar-aware rewrite M15 F2 Leg 3 L3-DD-A/A2/B): a lazily-populated `Map<jarId, list>` — `findByUrl(jarId, url)`/`listFor(jarId)` are SYNCHRONOUS over the map (`null`/`[]` on a cache miss — the DD6 first-sight flash, accepted); `ensureJar(jarId)` triggers an async `bookmarksGet({ jarId })` refresh once per unseen jar (in-flight de-dup), called from the read paths (star refresh, bar render). A `jars-changed` broadcast evicts map entries for jar ids no longer live (the recyclable-id defense — jar ids are DETERMINISTIC and REUSABLE once a jar is deleted) via its OWN independent subscription, reading that broadcast's `containers` array directly rather than `jars-client.js`'s reactive state, so eviction never depends on subscription-registration order between the two clients. A late-resolving `ensureJar` fetch for a jar evicted while it was in flight is DROPPED, not stored (re-checked against the same "last known containers" snapshot the eviction path maintains) — storing it would recreate the recycled-id hazard the eviction exists to prevent; before the first-ever `jars-changed` broadcast there is nothing to evict against, so the check fails OPEN (a cold-boot fetch is never spuriously dropped). `bookmarksClient.boot` stays joined in the startup `Promise.all` for contract stability but is now a **default-jar prefetch** (`jarsBoot`/`getDefaultJarId` late-bound closures sequence it behind `jarsClient.boot`, since the default id is unknowable at construction and can legitimately be `null` when Burner holds the flag) rather than an everything-fetch — the Flight 1 "first tab's star renders only after the cache is populated" guarantee narrows to first-sight-of-EACH-jar. The module also HOUSES the bookmark business logic the line-budget discipline keeps out of `renderer.js`: the shared star-activation decision (`activateStar` — unbookmarked page adds then resolves the created entry, bookmarked page resolves the existing one directly, inert on internal AND burner tabs) and the bookmark-edit sheet's forwarded-submit body (`handleEditSubmit`, now jar-threaded — see the popover bullet below) — `renderer.js` wires only thin glue (construction, the boot-race join, the click/subscription registrations, `refreshBookmarksSurfaces`).
- **Star, sync paths, and activation-class bar rendering**: `#star` (between `#address-chip` and `#address`) is refreshed by `refreshStar(tab)` (`navigation-controller.js`, modeled on `refreshZoomControl` — hidden on internal tabs, BURNER tabs (M15 F2 L3 L3-DD-C), or no live wcId; primes the tab's jar via `ensureJar` then a synchronous jar-scoped cache lookup, no async race guard needed). Called from the three `updateAddressChip` navigation sites (`onTabDidNavigate`, `onTabDidNavigateInPage` — star only, never the bar: no live tab is ever re-homed to another jar, so navigation can't change which jar's bookmarks apply) plus two ACTIVATION-class sites (`tab-controller.js`'s `activateTab` body and the `createTab` wcId-arrival path — covers `restoreHistory`-based creates too) and the cache's own post-refresh signal (covers cross-window edits and `ensureJar` first-sight fetches alike). The two activation-class sites ALSO call `renderer.js`'s `refreshBookmarksSurfaces(tab)` — a single closure that computes `suppressed = burner || internal`, forwards to `window-controller.js`'s `setBarSuppressed`, and (when visible) primes the jar's cache and calls `bookmarksBarController.render(jarId)`. Burner and internal tabs render no bar at all (instant reflow, no animation — the `#bookmarks-bar` INVARIANT in `styles.css`); `Ctrl+D` and the page-context bookmark item are inert on both via `activateStar`'s guard, and the page-context item is OMITTED (not present-but-inert) via `pageContextModel`'s `canBookmark` opt.

Keyboard model: plain document tab order over native `<button>`s (no `role="toolbar"` / roving tabindex) — a documented simpler-but-still-APG-legal choice for this small, infrequently-focused row.

### Internal-bridge security model (`src/main/internal-ipc.js`)

`registerInternalHandler(ipcMain, channel, handler)` wraps `ipcMain.handle` with a two-condition sender check **before** the handler runs: (1) `INTERNAL_ORIGINS.has(event.senderFrame?.origin)` (a destroyed frame yields `null` → fails); (2) `event.sender.session.__goldfinchInternal === true` (strict equality). Any mismatch throws `'forbidden: non-internal sender for <channel>'` → a rejected `invoke` renderer-side. This is the authoritative boundary; the preload's `location.origin` guard is defense-in-depth only.

- **Node-vs-Blink origin gotcha**: Blink serializes a `{standard, secure}` scheme's frame origin to `goldfinch://settings` etc. — the correct values to match. Node's `new URL('goldfinch://settings').origin` returns `'null'`. Do NOT "fix" `INTERNAL_ORIGINS` to match Node's output.
- `internal-*` channels are origin-locked to internal pages; chrome channels (`shields-*`, `settings-get`, `automation:get-activity`, …) are bare `ipcMain.handle` on the `file://` chrome trust domain — see the bare-handle rule above; never wrap them with `registerInternalHandler`.
- **`chrome-welcome-set` (M16 F2 Leg 1, DD1) is a chrome-trust bare `ipcMain.handle`, NOT `registerInternalHandler`-wrapped** — the welcome surface is chrome DOM (`file://`), not a `goldfinch://` page. It is the one chrome-initiated settings WRITE (every other chrome settings channel is read/subscribe-only): restricted main-side to `homePage`/`searchEngine`, calling `settings.set(` literally (the broadcast-invariant net's detection half is a call-shape regex, squawk 0003) and `broadcastSettings()` itself — the `toggle-bookmarks-bar`/`unpin-toolbar-item` shape.

### Overlay-view patterns

Five patterns for any future main-owned overlay view:

1. **Electron's `findNext: true` means "start a NEW find session"**, not "step to next" — the inverse of the `<webview>`-era assumption. Main tracks the last query text and maps UI intent onto engine semantics (same text + Enter = step; changed text = new session). Migration-parity ACs need a spot-check of the underlying API contract, not just byte-parity.
2. **Pending-init queue**: a lazy overlay can receive its first payload before `did-finish-load`; sending immediately drops it. Queue at most one pending init (latest wins), flush on readiness.
3. **Sender-resolved close refocus**: when one IPC channel serves actors with different focus consequences, resolve behavior from the sender's webContents identity — never a payload flag.
4. **Electron-free injected-deps module** for main-side view logic (see Recurring module shapes).
5. **Enumerable vs addressable**: a view kept out of `tabViews` never appears in `enumerateTabs` (document this choice at construction) but stays addressable by wcId — admin-tier only. `enumerateWindows` reports every window's `sheetWcId`/`findWcId` directly (exact O(1) admin read; the old id-space probe walk is retired — `scripts/a11y-audit.mjs` reads `enumerateWindows` with **no fallback**). Absent id = never created (both overlays are lazy); present id + `sheetVisible: false` = instantiated but hidden. `activateTab` on a non-tab wcId returns a harmless `false`.

### Chrome panel in the guest slot

Pattern for any future full-panel takeover of the guest region — the load-failure interstitial (Mission 20 Flight 1) is the first instance, and the welcome surface (M16 F2) is a sibling shape. **Mechanism**: a chrome-DOM panel nested inside `#webviews`, CSS-sibling to the guest slot, shown/hidden OPPOSITE the guest rather than composited over it — the guest is HIDDEN, not merely occluded. **The two-axis invariant** (`applyGuestVisibility`, `register-tab-ipc.js`), widened at Mission 20 Flight 3 Leg 2 by the shared `guestTakenOver(entry)` predicate (`src/shared/load-failure.js`): a registry-entry state flag (`loadFailure`, `crash`, a viewless welcome record, …) AND the active-tab check both gate visibility, so a background tab's takeover state never leaks onto the strip's rendered guest, and `tab-focus-guest`/the `tab-set-active` re-arm/`isFindableTab` are all refused while `guestTakenOver` is true — every main-side focus/visibility site reads this ONE predicate, never a bare `entry.loadFailure`. Main stamps the state on the tab entry and pushes it over its OWN dedicated owner-routed channel — never riding an unrelated push (`tab-load-failure`, `tab-security`, `tab-crash`, `tab-hung`, each its own wire, `guest-wiring.js`). **Activation projection order**: `tab-controller.js`'s `activateTab` computes and applies EXACTLY ONE of the possible panel states for the newly active tab (crash / load-failure / welcome / neither, that precedence) from an explicit precedence list — never an accumulation of independent `.hidden` toggles that could show two panels at once; a crash and a load failure are exclusive by construction (the crash handler clears `loadFailure` in the same step it stamps `crash`) so both route to the same panel call, and `render()` itself branches on `tab.crash` first. **Crash specialisation (M20 F3 L2, DD1)**: a dead guest renderer (`render-process-gone`, `reason !== 'clean-exit'`) is the panel's third branch — `classifyCrash(reason)` supplies reason-aware heading/body copy (`killed`/`oom`/generic), the panel's Reload button (`#load-failure-reload`) calls `wc.reload()` to respawn the renderer with its history intact (Retry and Reload are deliberately different buttons — Retry re-tries the intended address, Reload re-runs the current entry), and the strip's `data-load-state`/aria-suffix derive from the ONE `deriveStripLoadState(tab)` function (crashed > failed > hung > none) rather than three field-scoped writers. **A frozen (hung) guest** gets a sibling non-blocking surface, NOT a guest-slot takeover — see "Tab strip" below. **Frozen-contract convention**: every id a controller or a behavior spec reads (`#load-failure-heading`, `#load-failure-view-cert`, `#load-failure-advanced`, `#load-failure-reload`, `#hang-notice`, `#hang-notice-wait`, `#hang-notice-kill`, …) is pinned as a DOM contract the moment a HAT/spec locks onto it — a visual restyle may wrap, but never rename, remove, or change the toggling of one of these hooks (the welcome surface's own frozen-DOM-contract bullet, above, is the same rule). **Census**: the automation `listTabs()` census projects the SAME state into a plain enum field (`loadState` — now `ok | failed | cert-blocked | crashed | hung` — plus `security`) so an agent can read "is this tab showing its takeover panel, or unresponsive" without ever touching the hidden/frozen guest; the admin-tier census additionally carries each tab's renderer `pid` (`wc.getOSProcessId()`, coerced `0`/`undefined`/throw → `null` — jar-key rows never see it).

### TLS trust

Mission 20 Flight 2's certificate-trust pipeline (interstitial → override → indicator → viewer), spanning main and chrome:

- **Answer-at-once, never queue.** `app.on('certificate-error')`'s callback (`src/main/cert-trust.js`) is answered SYNCHRONOUSLY, exactly once, inside a `finally` guarded by its own `catch` — unlike the auth-challenge queue (`auth-challenges.js`), Chromium never holds this callback open, so there is nothing to occlude or resolve later; a refused load simply fails into the ordinary `did-fail-load` path and a proceed re-navigates.
- **Override memory** (`cert-trust.js`'s remembered-override Set, `allow(key)`): keyed `${partition}\n${host}:${port}\n${fingerprint}` — per jar, per host:port, per certificate fingerprint, IN-MEMORY ONLY (no `fs`/`app-db`/`settings-store` import anywhere in the module — grep-AC'd). A remembered key answers future `certificate-error` events for that EXACT identity without re-prompting; it never widens to the host alone — a different cert presented on the same host:port re-prompts.
- **The four-guard proceed** (`register-overlay-ipc.js`'s `menu-overlay:cert-override-proceed`): sender identity, a live token match (collapsing "no menu open" into the same reason — no fifth string), the current menuType being `cert-override`, and the ACTIVE TAB'S OWN ENTRY (never the renderer payload) supplying `host`/`fingerprint`/`lastRequestedUrl` — a payload carrying a contradicting host/fingerprint/url/partition is silently ignored end to end; both the remembered-override key and the re-navigated URL derive from the entry, never from what the sheet sent.
- **The observer** (`src/main/cert-observer.js`, `setCertificateVerifyProc`): records what the network service saw, NEVER decides — its callback is unconditionally `-3` ("use Chromium's own verdict"), so no summary/log entry this module produces can ever change a trust outcome (the source-scan pin: the ONLY `callback(` literal in the file is `-3`). Both the observer's summary and the interstitial's own `cert-trust.js` summary speak the SAME stripped engine-error name (`stripNetPrefix`, e.g. `ERR_CERT_AUTHORITY_INVALID`) — never a raw numeric errorCode, so a viewer reading either source never sees two different vocabularies for the same failure.
- **`security`** (`src/shared/site-security.js`'s `SECURITY_STATES`/`deriveSecurityState`): one enum, one derivation, pushed on its OWN `tab-security { wcId, security }` channel from `did-navigate` (never riding `tab-did-navigate` — the adopt re-push must not replay that channel's own chrome-side resets, F2 leg-2 amendment) and forced to `none` from `did-fail-load` UNCONDITIONALLY (a failed/cert-blocked tab must never keep reporting a stale `secure` left over from a prior successful commit — belt-and-suspenders also in the chip and the automation census). The address chip's `data-security` attribute, the site-info popup's Connection row, and the census `security` field are all thin projections of this ONE value through the shared `connectionLabel`/`chipAriaLabel`/`isNotSecure` helpers — never a second, independent derivation; `insecure` and `overridden` share the "not secure" wording and the broken-lock shape, `overridden` alone names the certificate.
- **The readable sheet allowlist** (`resolve.js`'s `AUTOMATABLE_MENU_TYPES`, DD10): `site-info` and `cert-viewer` are display-only, non-secret models — admitted for `readDom`/`readAxTree`/`captureScreenshot` only (see the "Menu-overlay sheet" pattern's own gate, above); `cert-override`, the flight's one security-decision channel, is NEVER admitted — a proceed can only be driven by a real operator gesture landing on the sheet's Proceed button, unreachable to automation by construction. `tab-certificate-get` (the cert-viewer card's read, chrome-trust `requireChrome` + `ownsTab`) returns a strings-only, PEM-free certificate summary; `entry.certificate` on a tab record is the OBSERVER's wrapper `{verificationResult, errorCode, isIssuedByKnownRoot, summary}`, never a bare summary — read `entry.certificate?.summary`, never `entry.certificate` itself as if it were one.
- **Cached vs in-band, same commit.** A cached observation never outranks an in-band decision made for the same commit: `deriveSecurityState` (`src/shared/site-security.js`) checks the navigation's own `certOverride` stamp BEFORE the observer's cached verdict. The verify-proc observer (`cert-observer.js`) is HOSTNAME-keyed — Electron's verify `Request` carries no port — so two https origins on one hostname with different ports share a cache slot; the overridden path never reads it (it reads `certOverride.summary` instead), but a TRUSTED page's viewer on such a host may show the most recently verified certificate for that hostname rather than necessarily its own (accepted gap).

### Crash and hang resilience

Mission 20 Flight 3's crash/hang pipeline (guest crash panel + kill-and-reload, chrome reload-and-reconcile, local crash records), spanning main and chrome:

- **A crashed guest is a hidden guest under the Chrome panel in the guest slot, specialised.** `guest-wiring.js`'s `render-process-gone` handler (`reason !== 'clean-exit'`) stamps `entry.crash = { reason, exitCode, url }`, clears `loadFailure`/`hung` in the same step (a dead renderer is neither failed nor hung), and hides the guest through `guestTakenOver(entry)` (`!!(entry.loadFailure || entry.crash)` — the ONE two-axis visibility/focus predicate every SHOW/focus site reads, never a bare `entry.loadFailure`). **No guest ever auto-reloads** — a storm of guest crashes is a row of crash panels, never N reloads. The panel's **Reload** button (`tabNavigate({verb:'reload'})`) calls `wc.reload()`, which respawns the renderer and replays history (falling back to `wc.loadURL(effectiveUrl(entry))` when the crashed guest never committed anything, i.e. empty history).
- **Kill-and-reload gates on `entry.killRequested` ALONE, never on the reported `reason`.** `forcefullyCrashRenderer()` (the hang bar's "Kill and reload") reports itself as `reason: 'crashed'` on Linux/Electron 44, not `'killed'` — only a REAL `SIGKILL` yields `'killed'`. The flag is set immediately before the call and consumed by the following `render-process-gone` (which then skips the crash panel and reloads in place) and by `did-start-navigation` (a navigation landing before the crash event means the kill never happened — the flag must not linger).
- **Chrome recovery reconciles from the registry, reusing the boot barrier.** `window-factory.js` wires the chrome view's `render-process-gone` to `chrome-recovery.js`'s `createChromeRecovery()` (Electron-free, injected `{ now, windowMs = 60_000, maxReloads = 3 }`): closes the sheet (`'teardown'`), hides find/tear-off, resets `record.bootConfigServed = false`, sets `record.recoverTabs = true`, then `reload()`s the crashed chrome webContents in place (never recreated — the registry record's identity is untouched; `reload()` re-runs `index.html` and re-invokes `window-boot-config` WITHOUT resetting `bootConfigServed` itself — this is why the hook resets it). **`record.restoreTabs` is NEVER nulled** — `window-boot-config` checks `recoverTabs` STRICTLY BEFORE `restoreTabs` (so recovery wins when both are set), leaving `restoreTabs` intact for `isRestorePending`'s own boot-restore hazard gate. On the fresh document's `window-boot-config` invoke, the `recoverTabs` branch sends one `adopt-tab` per `record.tabViews` entry (insertion order; container re-derived MAIN-SIDE — burner `id`/`name`/`color` from `src/shared/burner.js`, an internal entry's `{ id: 'internal', name: <page host>, color: '#9aa0ac', partition: INTERNAL_PARTITION }` from `entry.trusted`/partition identity, a persistent jar matched by partition with a deleted-jar fallback to the default jar) then the shared re-push set (`pushTabStateFor` — load-failure/security/crash/hung if set, nav-state always), THEN flushes the gap-queued sends (deduped last-wins per `(wcId, channel)`, survivor at the LAST occurrence's position) — all BEFORE the fresh chrome's `window-boot-config` handler returns `{ bootTab: false }` (or `{ bootTab: !rec.noBootTab }` at zero tabs, so an all-closed window still boots a home/welcome tab). `onAdoptTab` (chrome-side) honors `payload.trusted` (main-derived, never renderer-supplied — the ordinary move path never sends it, so it always coerces `false` there) and activates only `if (payload.active !== false)` — recovery adopts stamp an explicit `active: false` on every non-active entry. Dropped and documented: welcome records, pending queries, find text, suggestions, typed-but-uncommitted address text, any open sheet's half-typed content, and favicons (refresh at the tab's next navigation) — an open `goldfinch://` tab is NOT dropped.
- **`sendOrQueue` is the ONE boot-gate decision for a per-tab main→chrome push.** `queueChromeSend(record, buildMessage)` and `createSendOrQueue(registry)` are module-level exports of `register-tab-ipc.js` (constructed once in `main.js`, threaded into BOTH `createGuestWiring`'s deps and used directly by the move/adopt block) — booted → send at once via the record's own chrome webContents; unbooted → push the thunk onto `pendingChromeSends` (flushed by `window-boot-config`). `guest-wiring.js`'s `sendToChrome` routes through it (`wireTabViewEvents` carries zero bare `chromeForTab(wcId)?.send` calls — grep-AC'd) so a push racing a chrome reload is queued and replayed after the recovery adopts, never lost.
- **Recovery policy: reload at once; cap 3 per 60 s; then pause for the window's lifetime.** A per-window ring of crash timestamps lives lazily on the registry record (`record.chromeCrashTimes`, `record.chromeRecoveryPaused` — `window-registry.js` itself is untouched); a 4th crash inside 60 s sets the window title to "Goldfinch — chrome crashed (recovery paused)" and stops reloading — permanently for that window (no re-arm; a fixed cause needs a new window or a relaunch). Each window recovers independently (one reload each); guests never reload on a chrome crash. **Acceptance-run fix pass F1**: the pause branch also clears `record.bootConfigServed` — a paused window reads `booted: false` + `recoveryPaused: true` (never `booted: true` — there is no live document behind a dead, never-reloading chrome), contributes zero `enumerateTabs` census rows instead of hanging on a round-trip, and `queueChromeSend` drops (never queues) any push aimed at it.
- **The crash-log field set is CLOSED — a security control, not a convenience.** `src/main/crash-log.js`'s `record()` DESTRUCTURES its input (never spreads it) and builds an object literal with exactly EIGHT keys — `ts`, `kind`, `reason`, `exitCode`, `origin`, `jarKind`, `windowId`, `recovery` — source-scan pinned. `recovery` is one of `panel` / `reloaded` / `paused` / `ignored` / `closed` (the last is the popup-crash site's own outcome — a popup has no panel/reload path, it just closes). `origin` is scheme + host + non-default port ONLY (path/query/fragment/userinfo always stripped; `goldfinch://host` reconstructed by hand since Node's `URL.origin` returns `'null'` for the custom scheme — the Node-vs-Blink gotcha again); a BURNER partition's origin is always `null`. No title, jar name, cookie, header, or page content can ever reach the file because the callers' input shape has none of those fields. Rotates at 200 lines (keeps the newest 100); every write is fail-soft (try/catch → one `logger.warn`, never throws into an event handler).
- **`crashReporter.start()` must sit AFTER the dev-profile `setPath('userData', …)` redirect, with NO `submitURL`.** Electron resolves the crash-dump database path from `userData` at `start()` time and has no `crashesDirectory` option — a call placed any earlier would write dev-launch dumps into the operator's REAL profile. `{ uploadToServer: false, compress: false, ignoreSystemCrashHandler: false, rateLimit: false }`, no `submitURL` key, no `addExtraParameter` call anywhere in `src/` (all source-scan pinned) — there is no upload path to configure, let alone disable. `crash-log.js`'s `pruneDumps(dir, keep = 20)` runs at every `app.ready`.
- **`app.on('child-process-gone')`** records GPU/utility/other non-renderer crashes (reason + exit code only — no `url`/`partition`/`windowId` exists for a non-guest child process); Electron's capitalised `type` (`'GPU'`/`'Utility'`/anything else) maps through an explicit table (`kindOfChildProcess`), never a `.toLowerCase()` shortcut.

### Cross-view focus + tab-type idioms

- **Focus-then-send**: any branch forwarding a keyboard-input-expecting action to the chrome view (e.g. the guest→chrome Ctrl+L handoff) MUST call `getChromeContents()?.focus()` **before** `.send(...)` — the send drives only DOM focus; without OS focus you ship a focused-but-untypeable control. (The sheet's own chrome-shortcut branch deliberately omits `.focus()` — not a copyable template.)
- **Decide tab type with `isInternalTab()`/`isWebTab()`, never by reading `.trusted`** — trust is call-site provenance at `createTab`, not a tab-shape flag to re-read.
- **Patch in place, never rebuild, whatever holds `document.activeElement`** on broadcast-rendered pages — a rebuild loses the caret and fires `blur` → a spurious commit under commit-on-blur models (e.g. jar rename). One rule, all widget kinds — no per-widget carve-outs.

### Tab strip

- **Viewless welcome records (M16 F2 Leg 1, DD1/DD2/DD4).** A tab can exist with `wcId === null` past the boot round-trip: `openWelcomeTab({ container, reasons, pendingQuery })` builds a strip record exactly like `createTab`'s untrusted branch (jar resolution, strip insertion) but sends no `tab-create` IPC and stamps `tab.welcome = { reasons: Set, pendingQuery }`; the chrome-rendered welcome panel (`#welcome-surface`, a CSS child of `#webviews`; `welcome-controller.js`) shows while such a record is active. `attachView(tab, url)` is the ONLY place it acquires a view — validates with `isSafeTabUrl`, sends `tab-create`, then runs `onViewCreated(tab, wcId)`, the SAME wcId-arrival continuation `createTab` uses (extracted once so the two paths cannot drift). `openNewTab(container?)` is the resolver every "new tab" call site uses now that `createTab` has no default URL argument: a set home page always wins (`createTab`); an unset one opens a welcome tab whose `reasons` come from the pure `welcomeReasons(home, engine)` helper (`['home', ...(engine == null ? ['search'] : [])]`, M16 F2 Leg 2, DD7) — both blocks show when neither preference is set (including at boot, where the reasons are computed from the values the boot `Promise.all` **awaits**, `searchEngine` joining `homePage`, never from the live caches, which race that same barrier). Never in `tabViews` (main's registry) until `attachView` succeeds, so it is structurally invisible to `session-snapshot.js`, `closed-tab-capture.js`, and every cross-window move path (DD8/DD9 — no new exclusion code, just an absent entry). `applyToolbarAffordances(tab)` (Media/Shields/DevTools) and `updateNavButtons` (Back/Forward) both disable on `tab.wcId == null`, re-checked on `onViewCreated` too so an ordinary tab's buttons don't stay disabled after its view arrives; `tabContextModel`'s `hasView` param (default `true`) omits `duplicate`/`move-new-window`/`move-window:*` for one.
- **Load-failure surface (Mission 20 F1, DD1/DD6/DD7).** A registry entry can carry `loadFailure: { code, name, url } | null`; the two-axis guest-visibility invariant (`applyGuestVisibility`, `register-tab-ipc.js`) hides the guest and refuses `tab-focus-guest` while it is set — main-side wiring lives in `guest-wiring.js`'s `did-fail-load`/`did-start-navigation` handlers. Chrome-side, `load-failure-controller.js` owns the panel (`#load-failure-surface`, frozen DOM contract `#load-failure-heading`/`-body`/`-url`/`-code`/`-retry`/`-reload`) and is the sole writer of the strip's `data-load-state` (via `deriveStripLoadState`) + `.tab-status` glyph; `tab-controller.js`'s `activateTab` projects exactly one of crash/load-failure/welcome/neither. `renderer.js`'s `onTabTitle` short-circuits while `tab.loadFailure` or `tab.crash` is set (a late error-document title can't clobber the host title); F6 (`shortcut-controller.js`'s `focus-content`) lands in the panel's heading instead of the hidden guest. `listTabs()`'s census carries `loadState`/`loadError` (`LOAD_STATES`, `src/shared/load-failure.js`).
- **Crash and hang (Mission 20 F3 Leg 2, DD1/DD3).** A registry entry additionally carries `crash: { reason, exitCode, url } | null`, `hung: boolean`, and `killRequested: boolean`. `guest-wiring.js`'s `render-process-gone` handler (`reason !== 'clean-exit'`, window/entry both live) stamps `entry.crash`, clears `loadFailure`/`hung` in the same step, and pushes `tab-crash { wcId, crash }` — a dead renderer is never ALSO reported failed or hung. The hang bar's kill-and-reload sequencing gates on `entry.killRequested` ALONE, never on the reported `reason` (a live-rig finding: `wc.forcefullyCrashRenderer()` reports itself as `reason: 'crashed'`, not `'killed'`, on Linux/WSL2/Electron 44 — only a real externally-delivered `SIGKILL` yields `'killed'`); the flag is set immediately before the call and consumed — cleared, `wc.reload()`d, no panel — by the following `render-process-gone` regardless of its reason, and also cleared defensively by `did-start-navigation` (a navigation landing before the crash event means the kill never happened). `unresponsive`/`responsive` stamp/clear `entry.hung` and push `tab-hung { wcId, hung }` on their own channel — skipped entirely for a trusted (internal) entry, a crashed entry, or a kill-pending one. Chrome-side, `hang-notice-controller.js` owns `#hang-notice` (a fixed-height, `#bookmarks-bar`-shaped row between the toolbar area and `#main`, INSTANT reflow — never animated) with Wait (dismisses for the current hang episode only; a fresh `unresponsive` re-arms it) and Kill-and-reload (`tabNavigate { verb: 'kill-reload' }`); it delegates the strip write to `load-failure-controller.js`'s `applyStripState` rather than owning a second `dataset.loadState` writer. A crashed guest's Reload falls back to `wc.loadURL(effectiveUrl(entry))` when `navigationHistory.length() === 0` (a guest that crashed before its first commit has nothing for `wc.reload()` to replay). Popups (`popupRegistry`) have no strip/panel to update — a popup's `render-process-gone` records and closes the popup window instead. The admin-only census `pid` field and the `showCrashPanelForAudit`/`showHangNoticeForAudit` evaluate-seam hooks are documented in "Chrome panel in the guest slot" and "Automation engine" respectively.
- **The search handoff (M16 F2 Leg 2, DD3).** `navigate(input)`'s merged body: empty/whitespace input is a no-op (no handoff, no navigation); otherwise `toUrl(input)` returns `null` when the input is a search and `currentSearchEngine()` is `null` — checked BEFORE the welcome-record attach branch (`attachView(tab, null)` would silently drop the query) — and routes to `handoffSearch(tab, capPendingQuery(input))` in `navigation-controller.js`: an already-viewless welcome record gets `'search'` added to `reasons` and the query stamped onto `pendingQuery` **in place** (latest query wins, re-rendered via the injected `refreshWelcome`); any other active tab gets a **new** `openWelcomeTab({ container: tab.container, reasons: ['search'], pendingQuery })` beside it — the page the user is on is never discarded. The page-context "Search for …" path (`renderer.js`'s `sel:search` dispatch) shares the exact same null-check-then-`openWelcomeTab` shape; `createTab` is never called with a `null` URL. `PENDING_QUERY_MAX = 2048` (`src/shared/search-engines.js`) caps the query at both capture sites via `capPendingQuery` (trim + truncate) and again inside `buildSearchUrl` itself (belt-and-suspenders) — the pending query is chrome-held per-tab state, never a URL, never persisted, and renders in the welcome panel via `textContent` only.
- **DOM/CSS structure** (`styles.css`): `.tab` is the pure sizing/query container (`flex: 0 1 240px`, `overflow: hidden`, `container-type: inline-size`, **no padding** — its container-query size equals its rect width); `.tab-row` carries the flex layout + padding. Three `@container` disclosure stages: title-hide at 72px, inactive-only close-hide at 56px (the active tab's close is never hidden), padding-compress at 40px on `.tab-row`. `.tab.active` carries a **64px min-width floor** paired with hiding its favicon when narrow — without the floor its close button shrinks to render outside its clipped bounds ("`display:block` in the DOM ≠ painted"); every other tab shrinks floorless. `#tabs` is `overflow: hidden` — no scrollbar at any count, by design.
- **⚠️ Container-query self-restyle is a silent no-op**: a `@container` rule whose selector targets the container element itself never applies — no error, no warning, `getComputedStyle` never reflects it. Only descendant selectors work.
- **DOM order is the single order authority.** The renderer's `tabs` Map is id→tab lookup ONLY (iteration order not load-bearing). `orderedTabIds()` is the one order-reading accessor; `commitTabMove(id, targetIndex)` the one order-mutating call. Never `[...tabs.keys()]` for order. `listTabs()`/`enumerateTabs` deliberately stays **creation-order** (FD ruling — consumers address by wcId, never position); `enumerateTabs` is an **all-windows census**: every row carries a registry-stamped `windowId` (the renderer never learns `windowId`), ordered by window creation then per-window creation, returned as a plain array. A mid-boot window contributes zero rows — `enumerateWindows().booted` is the completeness signal.
- **Tab activation under native DnD**: all tab drags (reorder, tear-off, cross-window) are native HTML5 DnD, which fires no trailing `click` — so the tab click handler's activate is **unconditional** (no suppression flag; don't reintroduce one), and a drag activates its tab in `dragstart` (Chrome parity).
- **Keyboard map** (all global chrome shortcuts, never lightbox-deferred, via the one classifier `keydownToAction` in `src/shared/keydown-action.js`): `Ctrl+Tab`/`Ctrl+Shift+Tab` + `Ctrl+PageDown`/`PageUp` cycle visual order with wrap; `Ctrl+1`–`8` jump to position (out-of-range no-op), `Ctrl+9` last; `Ctrl+Shift+T` reopens the last closed tab; `Ctrl+N` new window (lowercase-only; `Ctrl+Shift+N` deliberately unassigned); `Ctrl+Shift+ArrowLeft/Right` reorders the focused tab (strip-scoped, not global). The classifier's digit branch is gated on `!alt` (AltGr layouts report ctrl+alt for digits) and shift-tolerant (AZERTY). **`sheet-accelerator.js` hand-mirrors `keydownToAction`** — every classifier change must land in both files in the same change, or the sheet's accelerator path silently diverges on AltGr locales.
- **Closed-tab stack** (`src/shared/closed-tab-stack.js`): pure, main-owned, bounded (25, oldest evicted) — **one global stack with `windowId`-tagged entries** (documented divergence from Chrome's per-window reopen; entries must outlive their window). Capture at two sites through `closed-tab-capture.js` (shared allowlist body): (1) `tab-close`, before destroy; (2) whole-window capture at the window's `close` (every persist-jar tab in insertion order, `stripIndex` = append sentinel; `win.destroy()` skips `close` so it skips capture — accepted; the block is try/caught so it can never break close). Same positive persist-jar allowlist idiom as the recorder — burner/internal are structurally never captured. Reopen is **renderer-orchestrated**: main pops and returns the entry (pop rule: `stripIndex` honored iff `entry.windowId` === the invoking window's id, else append — whole-window entries therefore always append); the renderer resolves the jar and calls `createTab(url, container, { restoreHistory, insertAt })`. `tab-create` with `restoreHistory` **skips `loadURL` entirely** and calls `navigationHistory.restore({entries, index})` — running both would race. Stack size is PUSH-fed: every mutation broadcasts `closed-tab-stack-changed {size}` to all chromes; the renderer caches via `push-cache.js` (a received push always wins; the boot-seed invoke applies only if no push arrived).
- **Tab context menu**: right-click or Context-Menu key/Shift+F10 on a tab — one `contextmenu` listener per tab button handles both (Chromium dispatches the same native event for both; the document keydown catch-all's exclusion gate covers `target.closest('.tab')` — no parallel keydown listener). Pure model `src/shared/tab-context-model.js`, ids `tab:*`, **omitted-only** (the sheet has no disabled-item shape): `close-others` omitted when sole tab; `close-right` when none to the right; `reopen-closed` at an empty stack; `move-new-window` omitted at last-tab AND for internal tabs (its dispatch sends the strip snapshot to `tab-move-to-new-window`; main re-parents the live guest into a `noBootTab` window). Batch closes are **ordered sweeps**: snapshot the target ids, activate the ANCHOR first when the active tab is a target (Chrome parity), then close each — so `closeTab`'s next-tab fallback never fires mid-sweep. `duplicate` reads live url/title/container renderer-side + the `tab-history-snapshot` invoke (web tabs only), then `createTab(..., { restoreHistory, insertAt: sourceIndex + 1 })`. `reopen-closed` reuses `dispatchChromeAction('reopen-closed-tab')`; `openTabContextMenu` is synchronous (fed by the push cache).

### `action:rowId` confirm-transition key

When a shared confirm area serves N sibling-visible actions on one row (the per-jar data-controls block), key the open/swap transition on the **`(action, rowId)` pair** (compared string-or-null) — never a boolean. A boolean silently breaks the same-row action swap: no rebuild fires, leaving stale copy and handlers wired to the wrong action.

### Automation engine (`src/main/automation/`)

Programmatic drive + observe of tabs. `engine.js` is the single entry point; the pure op modules (`tabs.js`, `nav.js`, `input.js`, `observe.js`, `resolve.js`) hold the logic.

- **Injected deps, Electron-free**: op modules never `require('electron')` at module scope; `engine.js`'s `deps()` is rebuilt per call (a recreated window is always picked up). New ops follow the same shape.
- **`wcId` is the canonical tab handle** — per-tab state (locks, etc.) keys on the stable wcId, never a resolved `wc` reference.
- **Foreground-to-act + re-resolve — with a read/act ASYMMETRY.** Ops that need RENDERED OUTPUT (`actOn`/`actOnPaced`/`scroll`, `captureScreenshot`, `readAxTree`, `printToPDF`, `findInPage`) run resolve → activate → **re-resolve** → act (the pre-activate handle may be stale after the async hop; re-resolving re-applies the exclusions). **`readDom` and `evaluate` do NOT activate** — `executeJavaScript` works on background guests, and a read that steals the operator's foreground is the worse bug. Both halves are pinned in `automation-observe.test.js`; do not "harmonize" them. The raise is at WINDOW scope and lives in `tabs.activateTab` (routes to the owning window's chrome, then `win.focus()` + `registry.noteFocus()` — programmatic focus fires no focus event under WSLg). The predicate is structural: ops that call `activate` raise; ops that don't, don't.
- **`executeJavaScript` is the main→guest read path — not CDP.** Debugger-free, no single-client conflict, CSP-safe for self-contained reads. CDP `Runtime.evaluate` exists only to bypass page CSP for *library* injection (the a11y audit's case) — the opposite use case.
- **CDP is centralized in `cdp.js` and limited to `readAxTree` + `scroll`**: `withDebuggerSession` + one shared single-client lock Set keyed on wcId + the `debuggerUnavailable` refusal — attach on demand, detach in `finally`, never left attached. A busy debugger returns a discriminated `{ automation: 'debugger-unavailable', … }` refusal, not a throw; the shared lock means concurrent `scroll` + `readAxTree` on one wcId can't both attach. Why these two: no pure-JS path to the platform a11y tree, and `sendInputEvent` mouseWheel does NOT scroll `WebContentsView` guests (confirmed live) — `scroll` uses CDP `Input.dispatchMouseEvent` while click/type/key stay on `sendInputEvent`. Route any new debugger need through `cdp.js` — never a second attach path.
- **Menu-overlay sheet: the (menuType × op) gate** (M15 F3 DD1/DD1a–DD1f). `resolveContents`' guard 3 no longer refuses the sheet absolutely; it admits it **iff both allowlists pass**: (1) the sheet's **current** menuType is in `AUTOMATABLE_MENU_TYPES` (exported from `resolve.js`; `bookmarks-overflow`, `bookmark-edit`, `site-info`, `cert-viewer` — M20 F2 L4 added the latter two, DD10) **and** (2) the op opted in with `allowSheet` — exactly three dispatch entries do (`readDom`, `readAxTree`, `captureScreenshot`). **Allowlist on both halves, never a denylist**: every other menuType, a `null` current menu (no menu open, or the sheet hidden), every other one of the 23 `WCID_FIRST_OPS`, and anything added later is **refused by default**, at every tier including admin. `sheetMenuFor(wc)` (window-registry) is threaded as a **live reader** into deps at **both** `createEngine` sites — the fallback is silent, so both are grep-pinned; the predicate is **fail-closed in shape** (an absent injection refuses rather than throwing a `TypeError` from inside a live guard). All three admitted ops snapshot `{menuType, token}` **inside the op after its first resolve** (`deps()` has no wcId, and the sheet is per-window-record) and **re-check after their async work**, discarding on mismatch — `token` too, so a close-and-reopen of the same menu also discards; `null → null` is not a mismatch. `captureWindow`'s sheet layer rides the **same imported predicate** (DD1c — it composited the visible sheet unconditionally, so admin captures returned `vault-unlock` pixels), post-await re-check included. The premise all of this rests on — that the sheet's DOM holds no closed menu's content — is made true by DD1f's eager scrub above, not assumed. **Why `readDom` is admitted though it executes script**: the distinction is *fixed app-authored snippet vs caller-supplied code*, not "executes script vs doesn't" — `evaluate`/`injectScript` inject into a realm that outlives the menu; "leaves nothing resident" is retired as the rule (`printToPDF` leaves nothing resident and is still refused). **Jar keys are refused by `out-of-jar` (session identity), not by this guard** — `scope.js`'s `memberDeps()` threads neither `isSheetContents` nor `isTabViewWcId`, so this leg widened the **admin tier only**.
- **Standing unobservable-surfaces list** (what no automation apparatus can see — check here before writing an acceptance criterion against a surface):
  - **Menu-overlay sheet — READABLE BUT NOT SCRIPTABLE since M15 F3.** Under `bookmarks-overflow` / `bookmark-edit` / `site-info` / `cert-viewer` (M20 F2 L4, DD10 — `site-info` and the new read-only `cert-viewer` certificate-summary card both joined the allowlist this leg), admin may `readDom` / `readAxTree` / `captureScreenshot` it. Under every other menuType (kebab, container picker, page/tab context, suggestions, `input-dialog`, `cert-override` — the flight's one security-decision channel, never admitted — the whole `vault-*` and `auth-*` family) it is fully unobservable. `evaluate` / `injectScript` are refused on it **unconditionally**, so **axe-core auditing of any sheet state stays out of reach** (axe needs library injection into a realm that outlives the menu) — accessibility-*tree* inspection is what became reachable.
  - **Toast layer — wholly unobservable.** No apparatus reads it at any tier; assertions about toast copy are operator-only.
- **`automation:dev-invoke` is a deprecated, dev-only seam** (`!app.isPackaged`-gated; new dispatch keys auto-expose). Do not build durable consumers against it — the MCP transport is the supported path.
- **Bind model**: in production the Settings `automationEnabled` toggle is the **sole** bind gate (`shouldBindAutomation` in `src/shared/automation-dev.js`); enablement is human-only (minting a key never enables). In dev, `--automation-dev` force-binds without writing the setting — a complete no-op when packaged (every call site ANDs `!app.isPackaged`); dev runs are profile-isolated (`~/.config/goldfinch-dev`). Dev/admin key acquisition (the `AUTOMATION_DEV_MINT` stdout line) → `docs/dev-testing.md`.
- **Management UI** (`goldfinch://settings` → Automation): enable toggle, live MCP address + `.mcp.json` block, persisted `automationPort` (default 49707) with live rebind. `resolvePort` precedence is dev/prod split: dev honors `GOLDFINCH_MCP_PORT` (env > setting > default; an env pin binds-exactly-or-fails-loudly); production ignores the env (setting > default) with free-fallback to the next free port (the persisted preference is not overwritten; the bound port is surfaced live). Per-jar + env-gated admin key generate/rotate/revoke (show-once plaintext; only hashes stored). An ungraceful client disconnect (dropped standalone GET SSE stream) tears the session down so the activity indicator clears — teardown attaches on the GET stream only; trades away resumable-SSE, correct for these clients.
- **Convention: any handler that mutates settings directly must broadcast `settings-changed` itself** (`broadcastToChromeAndInternal('settings-changed', settings.getAll())`) — only the `internal-settings-set` path does it automatically; otherwise live UI silently lags.

#### `runSerialized` (`src/main/automation/toggle.js`)

The shared mutex serializing `applyEnabledChange`/`rebind` through one `inFlight` promise chain: single in-flight op; rejection-tolerant continuation (a failed prior op doesn't wedge the chain — each op still surfaces its own error to its own caller); identity-guarded `finally` clear (`inFlight === mine`). **Prefer `runSerialized` over a bare `await prior`** for serializing any mutating ops — a bare await wedges on a prior rejection.

#### MCP transport (`@modelcontextprotocol/sdk`)

The sanctioned first runtime dependency — pinned to an **exact** version, imported **only** in `src/main/automation/mcp-server.js` + the `main.js` mount. The engine and op modules stay SDK-free; the MCP layer is a thin adapter.

- Node `http.createServer` bound to **`127.0.0.1` only**, default port 49707, SDK `StreamableHTTPServerTransport` on the raw `(req, res)` pair; stateful sessions (per-connection `randomUUID`).
- **The Origin/Host guard runs FIRST** (`origin-guard.js` — pure, exhaustively unit-tested): a denied request gets a 403 and never reaches the SDK. A loopback bind is necessary but not sufficient — *this browser renders hostile pages*, which can reach a loopback server via DNS rebinding unless Origin/Host are pinned.
- **30 tools**: 18 drive (incl. `dragPointer`, a paced synthetic pointer drag — for NON-tab in-page drags; tab drags are native DnD, which synthetic injection cannot drive; unpaced bursts get coalesced by Chromium, so events dispatch one macrotask apart), 4 observe (`captureWindow` takes optional `windowId` and binds by window identity; `enumerateWindows` — not captures — is the window-topology read), 2 eval (`evaluate`/`injectScript` — `executeJavaScript` in the guest main world, zero CDP; the internal session is excluded even for admin; `evaluate` returns must be JSON-serializable, and an `undefined` return collapses to the same `{"ok":true}` a void op returns — indistinguishable at the wire, squawk 0092), 2 devtools, 3 admin chrome/app-level (`getChromeTarget` (optional `windowId`), `enumerateWindows` — the single window-topology discovery primitive, one row per window `{windowId, chromeWcId, booted, activeTabWcId, lastFocused, sheetWcId?, sheetVisible, findWcId?, findVisible}`, zero cached state — and `downloadsList`; jar keys get `automation: admin-only`), 1 jar-confined `getHistory` (a jar key reads its own jar; admin reads any known jar with `jarId` required). Result semantics: drive ops → JSON text; screenshots → image content; the `openTab`-`null` and `debugger-unavailable` outcomes are **normal results** (read and react), not `isError`. Full consumer reference: `docs/mcp-automation.md`; runnable client: `scripts/mcp-example-client.mjs`. The repo `.mcp.json` ships an empty `mcpServers` map — off-by-default; consumers opt in at their configured port. The 5 **vault** tools (`vaultUnlock`/`vaultList`/`vaultTotp`/`vaultFill`/`vaultAnswerAuth`) are non-engine-op — see the **Password vault** pattern.

### Password vault

Encrypted per-jar + global credential vaults (Mission 12). A self-contained substrate: `.gfvault` files + `manager.json` under `userData/vaults/`, **not** `app.db`; zero runtime deps (`node:crypto` only). Full reference: `docs/vault.md`.

- **Module layout.** `src/main/vault/`: `vault-crypto.js` (pure crypto core — AES-256-GCM items, the four envelope ops, `.gfvault` serialize/parse, RFC-6238 TOTP), `vault-store.js` (stateful `manager.json` + `.gfvault` persistence, unlock lifecycle, rotations, export/import, `deleteVault`/`hasVault`), `vault-context.js` (per-session fill-only automation ctx), `vault-human.js` (gesture picker/fill/capture), `psl.js` (vendored PSL). Browser-CSV import (M19 F1, below): `csv-parse.js` (the RFC-4180 parser), `browser-import.js` (the Chrome-row→`login` adapter + DD3 dedupe + outcome summary), `pending-browser-imports.js` (the held-plaintext-payload store, a sibling of `pending-imports.js`), `browser-import-flow.js` (the Electron-free pick→hold→confirm→commit flow, injected `dialog`/`fs`). `src/shared/`: `vault-item-schema.js` (per-type secret/non-secret SSOT — the metadata whitelist + save-preserve complement), `origin-match.js`, `reserved-ids.js` (`GLOBAL_ID`), and the `vault-*-template.js` sheet family. **Chrome side** (M15 F2 Leg 1, extracted from renderer.js): `src/renderer/chrome/vault-controller.js` (`createVaultController`, the `downloads-controller.js` shape) owns the flow end to end — the pick-and-fill state machine, the picker/capture sheet openers, the lock indicator, every cross-renderer vault trigger, and the vault-owned overlay-menu states/dispatch/close handling; `renderer.js` only constructs it and chains its `handleActivation`/`handleClosed` ahead of the generic dispatch (the `downloadsController` precedent). **Vault-page side** (M19 F1 Leg 2): `src/renderer/pages/vault-browser-import-controller.js` (`createVaultBrowserImport`, the `vault-nav-controller.js` injected-deps shape) owns the browser-CSV-import UI end to end — pick/destination/completion modals — built OUTSIDE `vault.js` from day one (DD10); `vault.js` wires only construction, a trigger button, `refresh()`'s held-state join, and a pagehide drop.
- **Vault page — pure display models.** Page display/decision logic for `goldfinch://vault` lives in `src/shared/vault-page-model.js` as pure, DOM-free functions consumed by the vault page/controller (which just maps over the result) and unit-tested in `test/unit/vault-page-model.test.js` without a DOM — the `jar-page-model.js` precedent. Demonstrated repeatedly: `restoreDestinationOptions`/`restoreOutcomeLines` (M18 F3), then `browserImportDestinationOptions`/`browserImportSkipLines`/`browserImportOutcomeLines` (M19 F1). New vault-page display/decision logic should follow the same split rather than growing inline in the controller.
- **MRK model.** One random 256-bit Manager Root Key wrapped in `manager.json` — v1: THREE required wraps (scrypt/master, HKDF/recovery, X25519/admin); v2 (M18 F2): master + recovery required, the admin pair (`mrk.admin` + `adminPublicKeyB64`) optional-but-paired (absence = unprovisioned/revoked, a lone half is malformed). Every vault key is wrapped under the MRK (one `mrk` envelope per `.gfvault`), so each held wrap credential opens everything — including jars created after setup. Single-slot rotations rewrite ONLY `manager.json`; **compromise rotation (`compromiseRotate`, M18 F2) is the exception** — fresh MRK + fresh key per vault, rewriting `manager.json` (as v2 no-admin, every access envelope dropped) PLUS every on-disk `.gfvault` as one crash-safe transaction. A per-jar automation access key wraps a single vault key DIRECTLY (holds no MRK envelope → opens only its own vault). Keys live main-process-only as Buffers; idle auto-lock + lock-on-quit `.fill(0)`-zeroize. **Load-loudly** (opposite of `app-db.js`): a tampered/unknown-version file throws a typed error and is NEVER quarantined.
- **Fill trust boundary (F2 DD5 / F3).** No master-equivalent secret ever enters the vault PAGE DOM (`goldfinch://vault`); entry/display route through the chrome-owned **menu-overlay sheet** over a **dual-zeroized Buffer channel** (secrets ride as `Uint8Array`, never a JS string; main zeroizes its copy + the transferred array). One-time recovery-key / admin-key displays are **dismiss-locked** (`dismissible:false` — only explicit acknowledge closes; the value is unrecoverable). The internal `goldfinch://vault` page can't be axe-audited via `--target` (the accepted settings-class a11y gap); the sheet states ARE audited.
- **Sheet family.** Twelve `src/shared/vault-*-template.js` sheets (`vault-unlock`/`set`/`recovery`/`stepup`/`accesskey`/`adminkey`/`import`/`change-master`/`recover`/`picker`/`capture`/`compromise`), rendered by `src/renderer/menu-overlay.js` on the per-window sheet — same model-render-only, APG-contract discipline as the **Menu-overlay sheet** pattern.
- **Payment cards (issue #152).** Card items fill and capture in-page like logins, with ONE deliberate asymmetry: **a card fill is not origin-gated at all** (a card belongs to the operator, not to a site — `reachableCardItems(jarId)` takes no origin). Every other gate is identical (unlocked → persistent jar → jar+global scope → top-frame → explicit picker selection), and the branch is chosen by the **stored item's own `type`** inside `fillHuman` — never by anything the guest/page/chrome sends, so a page can't steer a login onto the card path. Guest detection is ROLE-based off `autocomplete` `cc-*` tokens (`src/preload/vault-card-fields.js`) with a narrow name/id fallback that is skipped entirely on any form that hints at all; cards ride their own `vault-fill-card` channel and the gesture fill-target is **kind-tagged** so the two families can't cross-consume. Capture adds a **plausibility gate with no login equivalent** — 12–19 digits passing Luhn (`src/main/vault/card-identity.js`) — because a card field is detected heuristically where a password field is self-identifying; capture identity is the **full PAN**, never last4 (two cards can share a last4). PAN/CVV/expiry stay secret per `vault-item-schema.js` — the picker, offer and sheet carry only title/cardholder/brand/last4. **The MCP surface stays login-only**; `docs/mcp-automation.md`'s "never card data" guarantee is unchanged.
- **Identity items — admissibility (Mission 21 Flight 2).** *(Fill and capture shipped in Flight 3 — see the "fill and capture" bullet below.)* A fourth item family, with neither login's structural anchor (`input[type=password]`) nor card's plausibility gate (Luhn) — so admissibility IS the whole security story. **A SCOPE ANCHOR gates the form; token rules then gate the field** (`src/preload/vault-identity-fields.js`, DD1): a scope (a `<form>`, or the whole document for a form-less field) is an identity context only if it contains an admissible **postal** role (`street`/`street2`/`postalCode`, or a PREFIX-qualified `city`/`region`/`country` — prefixes: billing/shipping/delivery/mailing/contact/home/work) **AND** at least one **non-postal** role (`fullName`/`firstName`/`lastName`/`email`/`phone`) — without both, nothing in that scope is admissible, not even fields that would otherwise resolve a role. Rationale for each half: a postal anchor alone is not a person (a shipping-cost estimator — zip + country, no name — would otherwise qualify); a non-postal role alone over-admits `email` — a bare standalone email field is among the most overloaded widgets on the web (newsletters, contact forms, password resets). **`address` is NEVER admissible bare** — at the anchor or as a field, always prefixed or compound (`billingAddress`, `streetAddress`, `address1`, `address-line1`, …) — a bare `{address}` alternative would create a reachable TIE with `emailAddress`, which tokenizes to `["email","address"]` and would match `email`'s `{email}` and street's bare `{address}` at equal length, decided by iteration order (found in two design-review passes: round 1 made bare `address` non-anchor-eligible, which protects only the scope-anchoring phase; round 2 found the identical tie still reachable at field-role resolution once some other field had already anchored the scope, and closed it by dropping bare `address` entirely). **Matching is ALTERNATIVES, not a flat token set**: each role maps to a list of `{tokens, anchor}` alternatives, conjunctive within an alternative, disjunctive across alternatives (and roles), longest match wins (`fallbackResolution`) — required because `billingAddress1` tokenizes to `["billing","address1"]` with NO "address" token, and `firstName`/`lastName`/`fullName` all carry a `"name"` token that only alternative length can disambiguate. **The vocabulary is written TWICE, in two structurally different tables — do not consolidate them**: `AUTOCOMPLETE_ROLES` (literal, hyphen-preserving WHATWG token strings, matched by `resolveAutocompleteToken`, which splits only on whitespace) vs. `ROLE_ALTERNATIVES` (pre-split, hyphen-free token arrays, matched against `normalizeFieldHaystack`'s output, which turns `-`/`_` into spaces) — a hyphenated literal like `"postal-code"` pasted into `ROLE_ALTERNATIVES` is a DEAD ENTRY that can never fire, silently. Both tokenizing primitives (`normalizeFieldHaystack`, `resolveAutocompleteToken`, `fieldHaystack`) live in the family-agnostic `src/preload/field-tokenizer.js` (Leg 1, extracted from and now also consumed by `vault-card-fields.js`) so login/card/identity can never silently drift on which four attributes (name/id/placeholder/aria-label) feed detection. **Login wins a contested field**: `resolveLoginEntry` (`vault-fill-fields.js`, untouched) picks the username by document POSITION only (the last text/email/tel input preceding a password field) — so `isClaimedByLogin` filters every login-claimed field out of identity's candidate list BEFORE role resolution, including as the scope's own anchor candidate. **Named accepted false positive**: a form carrying a third party's address plus the reporter's own name/email clears every gate — DD1's founding "nothing inferred from shape, position or value" structurally forbids the one signal (label proximity) that could tell whose address it is. Irreducible to a vocabulary-only detector; the backstop is the conflict rule below.
- **Identity items — the store (Mission 21 Flight 2 Leg 3).** A fourth `ItemType`, `identity` — non-secret `title`/`fullName`; secret `firstName`/`lastName`/`email`/`phone`/`street`/`street2`/`city`/`region`/`country`/`postalCode` (`vault-item-schema.js`'s `SCHEMA.identity` — field names are the detector's role names verbatim, no translation layer). **ONE profile per vault, enforced at every write path**, not just `saveItem` (a design-review HIGH — the first draft's `saveItem`-only scoping was trivially bypassable via bundle import): `_saveItem` refuses outright (no write) on a second identity item with a different id; `mergeVaultItems` KEEPS the destination's profile and reports the incoming one skipped — never a conflict copy, which would create a second profile — folded into the SAME `skippedTypes` array the tolerant-import path below populates, not a second mechanism; `capSingleIdentity` caps a bundle's own item array to at most one identity item at `_importVault`'s writes and `restoreProfile`'s COMMIT + PREVIEW. **FOUR type sources must be edited in parallel, not one cascading into the other** (amended mid-flight from two, to three, to four): `vault-item-schema.js`'s `SCHEMA`; `vault-store.js`'s independent `ITEM_TYPES` `Set` literal (checked at three separate call sites); `vault-editor-model.js`'s `EDITOR_LAYOUT`/`EDITOR_TYPES`, pinned to the schema by an `assert.deepEqual` drift guard so a new type goes red until the editor gains a UI label for every field; and `vault.js`'s `ITEM_SUBSECTIONS`, which renders only the types it lists — a type added everywhere else but not there is bucketed correctly by `partitionItemsByType` and then silently never drawn (the fourth source was found at design review, not by any test). **Bundle import is now tolerant of unknown item types and REPORTS them** (`partitionImportedItems`, a new sibling to the unchanged, still-strict `validateImportedItems`): an item whose type isn't in `ITEM_TYPES` is dropped and its type name recorded in `skippedTypes` instead of throwing, at all three call sites (`_importVault`; `restoreProfile` COMMIT, now catching per-entry so one bad entry no longer aborts an entire multi-vault restore; `restoreProfile` PREVIEW, so `itemCount` never silently under-counts). This deliberately **softens Mission 18's "load loudly" stance for these bundle-import paths ONLY** — the `.gfvault` PARSE path, and `validateImportedItems` itself, are untouched and still load loudly. `classifyCapture(stored, captured)` (`src/main/vault/identity-profile.js`, pure; its live caller is `disposeIdentityCapture`, M21 F3 Leg 4 — see the "fill and capture" bullet below) makes the conflict rule real: `{kind: 'match'|'gap-fill'|'conflict', gapFilled: [{field,to}], conflicting: [{field,from,to}]}`, byte-exact equality — `"555-1234"` vs `"5551234"` IS a conflict, no normalisation. `identityProfileOf(items)` is the canonical "the profile" read (`{profile, extra}`) — never `items.find(it => it.type === 'identity')`, which would silently pick past a duplicate instead of surfacing it via `extra`. **Named residual**: on a FRESH profile every captured field is a gap, so the conflict rule's own motivating scenario (a gift-shipping checkout carrying a stranger's details) classifies as an ordinary gap-fill merge if it happens to be the first identity capture ever — still an offer, never a silent write, but the rule doesn't catch its own headline case in that one situation. **Automation stays login-only** — identity inherits card's exclusion structurally (`vault-context.js` filters `item.type === 'login'` at every vault-tool resolution site), so `vaultList`/`vaultFill` never expose an identity item; no code change was needed for this.

An earlier design said exactly that ("the settle read routes main → IPC → …") and was corrected at design review — do not reintroduce it.
- **The isolated world is the read substrate; the isolated-world script carries no policy (DD3f/DD3g/DD3h).** Detection, the provenance `Map` (keyed by ITS OWN node references — no node identity ever crosses the world boundary, only plain `{detected, value}` data), the MutationObserver-driven detachment eviction, and the DD3 value-equality check all live in `src/preload/vault-entry-observer.js`, deployed into a dedicated isolated world (`webview-preload.js`'s `VAULT_ENTRY_OBSERVER_WORLD_ID`) via `webFrame.executeJavaScriptInIsolatedWorld`; `src/preload/vault-entry-tracker.js` is the Electron-free main-world POLICY half (install lifecycle, fill routing, the gesture-time `readSnapshot()` call) and carries none of the observation logic. **The fourth-wall fact that forces this split**: because web guests run `contextIsolation:false` (farbling needs the preload sharing the page's main world), a same-origin page can `Object.defineProperty` a spoofed getter on `Event.prototype.isTrusted`/`.target` or `HTMLInputElement.prototype.value` — and four separate design-review rounds each defeated a main-world-only defense in turn (no provenance → a sticky per-field flag → a spoofed `.value` getter → a spoofed `.target` getter) before a live spike (Leg 2) proved a page-world accessor override is structurally invisible from a separate isolated world, ending the category BY CONSTRUCTION rather than by remembering to enumerate one more accessor. A stale or out-of-range ordinal falls back to entry 0, never throws, never fills an unrelated form on purpose.
- **Provenance is value-bound, never a sticky flag, and TTL-bounded (DD3/DD3i).** A field's value enters a capture only if the field STILL holds the exact string recorded at the granting instant (a trusted `input`/`keydown` on that field, or a Goldfinch fill) — a mismatch is treated as unprovenanced, never "trust the newer value" (this is what defeats the keystroke-then-overwrite and fill-then-mutate TOCTOU cases a sticky boolean would pass). Goldfinch's own fills grant provenance FOR THIS REASON — they run in the isolated world specifically so a fill can grant without a main-world fill ever needing to hand a node reference across the boundary. Provenance also EXPIRES (`PROVENANCE_TTL_MS` = 15 min, evicted passively at read and actively by an armed per-grant timer): before this flight a plaintext password existed only transiently inside one synchronous `submit` handler; `grant()` now stores an un-zeroable plain JS string in the isolated world's Map on every trusted keystroke, so both the retention window and the count of un-zeroable copies genuinely grew, and DD3i states that honestly rather than claiming parity with the old discipline. **Accepted gap, budgeted deliberately**: this is an exposure-DURATION cost, not a value-forgery one — the string is unreachable from the page and from any other origin, so it never touches a hard-zero bar.

### Auth challenges (HTTP basic auth + client certificates)

`src/main/auth-challenges.js` (M14 F1) — one shared Electron-free store behind both `app.on('login')` and `app.on('select-client-certificate')` (both registered top-level in `app-lifecycle.js`, both unconditionally `preventDefault()`ed), with per-window FIFO queues, challenge `kind` (`'basic-auth'` / `'client-cert'`), and chrome-sheet presentation (`auth-basic` / `cert-picker` on the menu-overlay sheet).

- **⚠️ INVARIANT: every Electron auth callback is resolved exactly once — `resolveOnce` is the SINGLE callback site** (source-scan pinned in `auth-challenges.test.js`; even the routing ladder's silent cancels mint a challenge shell and resolve through it). Every close reason maps to one of two buckets: **resolution** (escape / outside-click / activated / tab-close / teardown — and the fail-safe default for any UNKNOWN reason) or **occlusion** (blur / superseded / tab-hide / tab-switch — the challenge re-presents later). Never call a challenge's callback anywhere else, and never add a close path that can leave a callback dangling.
- **Cert selection is human-only.** The agent seams (`getPendingChallenge` / `answerWithCredential` — the `vaultAnswerAuth` path) kind-filter to basic-auth, so a string credential can structurally never reach a Certificate callback; the sheet never closes itself on answer — the store owns the single close site.

## Release / CI

Both workflows are supply-chain hardened; preserve these invariants:

- **All `uses:` pinned to full commit SHAs** with a trailing `# vX.Y.Z` comment — never mutable tags. When bumping an action, **including accepting a Dependabot PR**, resolve the new version's commit SHA and pin to that (Dependabot proposes mutable tags; applying them verbatim regresses the hardening).
- **Least privilege**: top-level `permissions: contents: read`; only the `create-release`/`build` jobs escalate to `contents: write` per-job.
- `ci.yml` (PRs): `npm ci → test → typecheck → lint → npm audit --audit-level=high → package`. A high in a dev-only dep is fixed by bumping the dep, never by lowering the gate.

### Cutting a release (`build.yml`, on `v*` tag push)

Tag-driven — full flow in `docs/RELEASING.md`. Short form: from green `main`, `npm version patch -m "release-prep: bump to %s"` (the `version` npm-lifecycle hook regenerates the README download links into the same commit — there is no post-release README job) then `git push --follow-tags`. Strict semver is enforced; a prerelease tag publishes as a GitHub prerelease. Rollback: `gh release delete vX.Y.Z --yes --cleanup-tag`, fix, re-tag. App icon: `build/icon.png`.
