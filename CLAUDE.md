# CLAUDE.md

Goldfinch — an Electron desktop browser with a media panel (scan/play/download page media) and a privacy panel (Shields + cookie-jar identities).

## Commands

- `npm start` — run the app
- `GOLDFINCH_AUTOMATION_ADMIN=1 GOLDFINCH_AUTOMATION_DEV_MINT=1 npm run dev:automation` — canonical dev launch (`scripts/dev-launch.mjs`, WSL/headless friendly). **Always include both env flags** (dev-only, profile-isolated; a bare launch mints no keys and admin-tier MCP ops are refused). Startup prints one parseable `AUTOMATION_DEV_MINT {"key":"<jarKey>","adminKey":"<adminKey>"}` line — admin key shown once; agents attach via env-key scripts (`scripts/lib/mcp-client.mjs`), never a static `.mcp.json` entry. Launch states, key capture, attach recipes, ozone/WSLg notes: `docs/dev-testing.md`; full MCP reference: `docs/mcp-automation.md`.
- `npm run dist` — build installers (electron-builder); `npm run pack` for unpacked
- `npm test` — `node --test` over `test/unit/**` (pure security/privacy helpers). For real-environment / UI behavior, drive the running app over the MCP automation surface (`npm run dev:automation`); behavior specs live in `tests/behavior/`.
- `npm run lint` — ESLint, flat config (`eslint.config.mjs`)
- `npm run typecheck` — `tsc --noEmit -p jsconfig.json` (all `// @ts-check` files)
- `npm run a11y` — axe-core audit (`scripts/a11y-audit.mjs`) against the RUNNING app over the MCP surface (zero CDP). Verify-only — NOT part of headless CI (needs the live GUI). Violations diff against the curated `ACCEPTED` allowlist baked into the script — only NEW `(rule id, node-selector)` findings fail. Run recipe (attach, audited states, gate tags, fixture, exclusions): `docs/dev-testing.md` → *a11y audit*.

## Architecture

Three processes; understand the boundary before editing.

- **Main** (`src/main/`): `main.js` is the composition root, not the behavior owner. `window-factory.js` constructs each `BaseWindow`/chrome view and owns per-window close teardown; `window-registry.js` owns records `{win, chromeView, tabViews, activeTabWcId}`; `register-{tab,overlay,download,settings,browser}-ipc.js` own their channel families; `app-lifecycle.js` owns ready/restore/activation/quit; `session-runtime.js` owns web-session policy and retention cadence. `shields.js` = Shields config + tracking-param stripping; `jars.js` = container definitions; `trackers.js` = eTLD+1 + tracker classification; `settings-store.js` = app preferences; `internal-ipc.js` = origin-checked bridge for trusted `goldfinch://` pages.
  - **Main↔chrome routing has three classes — classify any new send/handler site before writing it**: (1) **sender-resolved inbound** — chrome-sender IPC resolves its window via `registry.getWindowForChrome(event.sender)`, guest-sender via `getWindowForGuest(event.sender.id)`; window lifecycle events (resize/maximize/…) route to their OWN chrome via the per-window create closure. (2) **broadcast fan-out** — `broadcastToChromeAndInternal` sends to ALL chromes + internal-session contents once globally. (3) **per-tab owner-routed pushes** — every main→chrome send tied to a specific tab resolves the tab's owning window's chrome AT EVENT TIME via `getChromeForTab(wcId)` — never fanned out, never left on a focused-window accessor (event-time resolution is what makes move-to-new-window's re-bind automatic). `getChromeContents()` survives only as a last-focused accessor (registry-tracked, seeded at create AND programmatic `win.focus()` — WSLg-safe, membership-validated) — don't build new code against it when a routing class fits.
  - **Lifecycle split**: `window-factory.js` tears down at `close` in this order: find overlay → tear-off overlay → menu sheet → whole-window closed-tab capture/session snapshot → per-tab side effects + **explicit guest destroy** (Electron never auto-destroys an attached view's webContents). `closed` then removes the record and defers chrome-wc destruction with `setImmediate`. `app-lifecycle.js` owns app-level MCP/store quit ordering. Closing one of N windows never quits; the last close rides `window-all-closed` (non-darwin).
  - **⚠️ Never read `win.*` inside `closed`-or-later handlers** — capture teardown inputs (e.g. `const winId = win.id`) at create time. A destroyed-`BaseWindow` property access throws, and an uncaught throw inside the native `closed` emission aborts the listener chain AND permanently wedges the Wayland close path with zero error output.
- **Preloads** (`src/preload/`): `chrome-preload.js` exposes `window.goldfinch.*` (contextBridge) to the chrome. `webview-preload.js` runs in every web page's **main world** (media scanner + fingerprint detect/farble). `internal-preload.js` is a third, distinct preload for trusted `goldfinch://` pages — context-isolated (opposite of `webview-preload.js`), exposes `window.goldfinchInternal` behind an `INTERNAL_ORIGINS` allowlist check (defense-in-depth; main-side `registerInternalHandler` is the authoritative boundary). Keep the three separate.
- **Renderer** (`src/renderer/`): `renderer.js` is the chrome composition/boot root. `chrome/context.js` owns DOM/state references; `tab-controller.js`, `navigation-controller.js`, `media-controller.js`, `privacy-controller.js`, `downloads-controller.js`, `window-controller.js`, `shortcut-controller.js`, `jars-client.js`, and `overlay-menus.js` own behavior. Each tab is addressed by `wcId`. Popup menus + the new-container dialog render from the main-owned **menu-overlay sheet**, not chrome DOM: chrome controllers own triggers/models/actions; the sheet owns presentation + the APG keyboard contract. The ARIA tab-strip contract remains pinned by `tab-keyboard-operability`.

Key cross-cutting facts:
- **Shields apply to every jar through `session-runtime.js`'s `onSessionCreated`.** Each container/burner/default tab is a session partition; new jars inherit automatically. One `webRequest` listener per event per session — recording and enforcement share it (`applyShields`).
- **Web `WebContentsView`s run `contextIsolation:false`** (preload in the page main world — required for farbling). `nodeIntegration` stays off; preload internals stay module-scoped. Internal views are additionally context-isolated.
- **Web guests run `sandbox:true`** (F2 DD4 — chrome view is the one deliberate, tracked exception, deferred per DD4): a compromised web-guest renderer (a hostile page's V8/Blink RCE) is contained by the OS sandbox instead of running with full user-account privileges. `contextIsolation` stays `false` on web guests regardless — farbling needs the preload sharing the page's main world — so the sandbox restricts the preload's Node API surface, not world isolation; the guest↔preload trust boundary (`nodeIntegration:false`, the `isTrusted` caveats) is unchanged.
- **`asar:false`** in the build config so `src/**` stays as unpacked disk files — required by the internal-page `path.join(__dirname, …)` resolver.
- **Find-in-page is a per-window floating overlay `WebContentsView`** — NOT chrome DOM. `src/renderer/find-overlay.{html,js,css}` + its preload (chrome-class trust), managed by the Electron-free `src/main/find-overlay-manager.js`, one lazy instance per window in the registry record's `findOverlay` slot; main owns lifecycle, positioning, focus, and the find session, and fans `found-in-page` counts directly to it. The guest is never inset — the bar floats over full guest bounds. Per-tab `findText`/`findOpen` stay in the chrome renderer, which drives `find-overlay:open`/`close` (per-tab restore sent AFTER `tabSetActive`) and syncs back via `find-overlay-text` (every query) and `find-overlay-closed` (overlay-side user Esc/✕ only). Close refocus resolves by SENDER: overlay-side close refocuses the guest; chrome-side moves no OS focus. Hidden on internal tabs and while a sheet menu is open. Not in `tabViews` → invisible to `enumerateTabs`, admin-tier only.
- Per-tab privacy data: main aggregates → `privacy-net` IPC → renderer; preload fingerprint counts → `ipcRenderer.send('guest-privacy-fp', …)` (web tabs, not `sendToHost`). Farble config is fetched synchronously at page load — toggling farble needs a reload.
- Persisted state lives in `userData/app.db` (`documents` table, one row per store — see App database). Legacy JSON files (`shields.json`, `containers.json`, …) import once on first boot and are renamed `.migrated`. The jars row is a v2 envelope `{ version: 2, defaultId, containers }`; a v1 bare array migrates on import.
- **The password vault is a separate, self-contained substrate** — encrypted `.gfvault` files + `manager.json` under `userData/vaults/` (NOT `app.db`), a main-process-only key hierarchy, a chrome-owned entry/display sheet family, and a fill-only MCP surface. See the **Password vault** pattern below and `docs/vault.md`.
- **Frameless window**: `frame:false` on win/linux (custom minimize/maximize/close controls in the tab strip's `#window-controls` zone, wired via sender-resolved `window-minimize` / `window-toggle-maximize` / `window-close` IPC; Close is the record's `win.close()`, NOT `app.quit()` — the last close rides `window-all-closed`); `titleBarStyle:'hidden'` + traffic lights on macOS. `maximize`/`unmaximize` forwarded per-window over `window-maximized-change` keeps the button's `aria-label`/`data-state` live.
- Drag regions: `#tabstrip` is `drag`; the pill, tabs, and window-control buttons are `no-drag`; a `#tabstrip-drag` spacer guarantees a grab area. `chrome-preload.js` exposes `platform`; the renderer tags `<html>` with `platform-{platform}` for platform CSS.
- **⚠️ `WebContentsView` native-surface gotcha — "DOM correct ≠ render correct."** A guest view is an out-of-process native compositing surface, not a DOM box. Bounds/visibility changes around it can mis-render the composited pixels while every `getComputedStyle`/`getBoundingClientRect` read looks correct. A guest bounds change is a discrete `setBounds` STEP, not an animatable quantity — sustaining a chrome-ramps-while-guest-steps mismatch mis-renders on EVERY platform (operator-confirmed on native Windows; not a WSLg quirk). **INVARIANT: never animate chrome layout that resizes/repositions the guest slot; animate only things that float OVER the guest (find bar, menu sheet — view stacking that changes no layout around it), or make the layout change instant.** Rules: (1) prefer compositor-only properties that change no layout around the guest; (2) "DOM geometry reads correct" is necessary-but-insufficient — the acceptance signal is the rendered surface observed by a human in motion (even `captureWindow` misses inter-frame defects; discrete grabs land on settled frames); (3) gate any mechanism touching the guest region on a cheap on-platform spike; (4) don't attribute a render defect to the rig (WSLg) without a cross-platform control.

## Patterns

### `src/shared/` ESM modules

`src/shared/` is real ESM: pure modules use `export`/`import` with explicit `.js` extensions, loaded via `<script type="module">`. Unit tests `require()` the same file (Node ≥22 synchronous `require(esm)`) — the test runs the exact code the app ships.

- **Two specifier shapes, by consumer.** The `file://` chrome imports disk-relative (`../shared/url-safety.js`). Internal `goldfinch://` pages import **flat** specifiers (`./safe-color.js`) because `internal-page-map.js` owns an exact-match host→pathname→file map, not a directory passthrough — a disk-true relative specifier 404s at boot. Flat imports carry `// @ts-ignore` and type `any` (tsc can't resolve them; backlog, not a bug).
- **CJS-by-design quartet + eslint parse guard.** `automation-dev.js` and `internal-page.js` are **preload-reachable** (renderer-side Node `require` has no `require(esm)`) and MUST stay CJS; `dev-profile.js` and `guest-forward-allowlist.js` stay CJS by zero-benefit ruling. `eslint.config.mjs` binds all four to `sourceType: 'commonjs'`, and the later `src/shared/**` module block's `ignores` entry for them is **LOAD-BEARING** — without it, later-wins re-binds the quartet to `module` and deletes the parse guard (an `export` in a preload-reachable file must FAIL lint, not misbehave at a live boot).
- **Evaluate-seam closed set.** Controller implementations remain module-scoped; `renderer.js`'s composition tail republishes exactly the FD-approved 34-entry set with `Object.assign(globalThis, {…})`. Moving an implementation into a controller does not publish it. Growing the set requires an FD ruling.
- **Defer/module pin (permanent house rule, contract-tested).** Every classic `<script>` on a page that also loads a module script must carry `defer` — a non-defer classic executes during parse, before any module. `menu-overlay.html`'s `menu-controller.js` is the product's one remaining classic script (carve-out).
- **New-shared-module checklist**: module script tag only; internal-page consumers need an exact `internal-page-map.js` route; evaluate-reachable entry points go through the closed-set seam (FD ruling); a new contextBridge method still needs its `renderer-globals.d.ts` entry.
- **Two real-boot defect classes `npm test` can't catch**: (1) `mkdirSync`-before-synchronous-persist — `app-db.js`'s `open()` now does it once for the whole substrate; unit fixtures pre-create temp dirs so the suite never surfaces it; (2) classic-script top-level scope collisions — structurally gone for `src/shared/` (module scope); the old collision nets are retargeted as script-tag contract tests (tag-count guard + defer pin + module pin).
- **Grep-AC convention.** Negative/invariant ACs ("this body must not change", "this literal no longer appears") may specify a literal reproducible grep/diff, with each hit judged exempt-or-real, instead of a unit test.
- **MockTimers recipe.** Enable per test (`t.mock.timers.enable(...)` inside the test body — never file-global, which leaks fake time file-wide). Drain with real `setImmediate` around single-step ticks — never one big tick that jumps past intermediate states. Exemplar: `test/unit/automation-find.test.js`.

### Two-point hostile-URL security boundary

`isSafeTabUrl` enforces at two independent points: the renderer `createTab` gate (rejects non-`http:`/`https:`/`about:blank` before `tab-create` fires) and the main `will-navigate` guard (`e.preventDefault()` on the same predicate — blocks bypasses via `window.open` etc.). The shared predicate keeps both in sync.

**PDF-viewer carve-out (M14 F1 DD5) — the ONE relaxation, keep it exactly this shape**: `guardNav` stays strict on all three guest nav events (`will-navigate`, `will-redirect`, `will-frame-navigate`); only the `will-frame-navigate` registration is a wrapper that additionally allows a **subframe** (`isMainFrame === false`, fail-closed when the field is absent) on a **non-internal** guest whose URL parses to scheme `chrome-extension:` with host exactly `PDF_VIEWER_EXTENSION_ID` (`guest-wiring.js`). Web guests carry `plugins: true` (web branch only — internal guests have no `plugins` key, so the viewer can't instantiate there). Top-frame `chrome-extension:` navigations stay refused on every event; never widen the carve-out (unit-pinned matrix in `guest-wiring.test.js`).

### Recurring module shapes

Default choices for new logic:
- **Electron-free, injected-deps modules** (main-side): live Electron handles (an fs path, `app`, a view constructor) passed as constructor/call arguments, never `require('electron')` — the logic runs offline under `node --test` with fakes. Exemplars: `automation/engine.js` (`deps()` rebuilt per call), `settings-store.js`, `internal-assets.js`, `menu-overlay-manager.js`, `find-overlay-geometry.js`.
- **`src/shared/` ESM pure decision modules**: e.g. `jar-page-model.js`, `inherit-container.js`. A module consumed only main-side stays plain CJS (`guest-forward-allowlist.js`).

### Internal `goldfinch://` pages — trusted-embedder security model

Three equally-privileged internal origins: `goldfinch://settings`, `goldfinch://downloads`, `goldfinch://jars`. The trust boundary is **"internal vs web," never per-page** — all internal pages share the same `goldfinchInternal` bridge and can call any `registerInternalHandler` channel. Security-critical; treat as such.

- **The welcome surface is NOT a fourth internal page (M16 F2 Leg 1, DD1).** It is a chrome-owned tab (`tab-controller.js`'s `openWelcomeTab`/`attachView`, `welcome-controller.js`) with no `goldfinch://` URL at all — none of the gates above are engaged, widened, or bypassed by it. `welcome-controller.js`'s `show(tab)` delegates to `settle(tab)` (fix at the Leg 2 acceptance gate) — the block rendering (`render(tab)`, home / engine, only while `reasons.has(x) && current<x>() == null`) and the attach decision are both driven from `settle`, the single place that decides: if a reason is still unset, render; otherwise a pending search runs (M16 F2 Leg 2, DD3), else the home page attaches if it is now set, else (defensive — every welcome record's reasons always include `'home'`, so this should be unreachable) the panel hides and the address bar gets focus. A block disappears the instant its preference is set by ANY path (this tab's own submit, Settings, another window) **the next time the record is rendered or settled** — `onSettingsChanged` settles only the currently-shown record; a background welcome record whose last unset preference was filled in elsewhere catches up via `settle` the moment `show(tab)` is next called on it (e.g. switching to that tab), not eagerly in the background. Both blocks render together on a fresh profile (`DEFAULTS.homePage`/`searchEngine` both `null`, M16 F2 Leg 2 / DD5) — first launch, and every new tab thereafter, until at least one preference is chosen. The engine block renders `src/shared/search-engines.js`'s `SEARCH_ENGINES` table via `createElement`/`textContent` (no engine data hand-typed in the chrome), with the heading `Where should we search for "<query>"?` when a pending query exists.

- **Scheme + session.** `goldfinch` is registered privileged (`{ standard: true, secure: true }`) at module load (before `app.ready`, which `registerSchemesAsPrivileged` requires); `standard: true` is load-bearing (real origin semantics + CSP). Pages are served from a dedicated in-memory internal session (`session.fromPartition(INTERNAL_PARTITION)`) whose `protocol.handle` is **session-scoped** — the global `protocol` would bind the default session.
- **`INTERNAL_PARTITION` is single-sourced** in `src/shared/internal-page.js` — import byte-for-byte, never re-type. Literal drift silently resolves a different session, the `__goldfinchInternal` marker goes absent, and every gate fails open.
- **CSP is stamped IN the response** (`INTERNAL_CSP` in `main.js`) — custom-protocol responses bypass `webRequest`/`onHeadersReceived`, so that hook would silently never fire. Do not relax the CSP without a security review.
- **The internal route map is owned by `src/main/internal-page-map.js`** (`createInternalPageMap`) and resolved per request by `createResolver` (`internal-assets.js`). It is a host → pathname → absolute-file exact map, traversal-proof by design: no path arithmetic on `url.pathname`. New subresources get explicit entries; never a directory passthrough.
- **The four gates** (defense in depth): (1) trust is **call-site provenance** — `createTab(url, container, { trusted: true })`, never inferred from the URL; the page-reachable `onOpenTab` route passes no flag, so web content can never select the internal branch; (2) the trusted branch validates with the `isInternalPageUrl` allowlist; the untrusted branch uses `isSafeTabUrl`, which rejects `goldfinch://`; (3) session-aware `will-navigate` — the internal session may navigate only within `isInternalPageUrl`; web views keep the stricter rule; (4) the protocol handler lives on the internal session alone — web tabs literally have no handler for the scheme.
- **NEVER widen `isSafeTabUrl` to admit `goldfinch://`.**
- **Chrome-fetch invariant (Mission 13 Flight 1): no page-controlled URL is ever fetched by the browser chrome outside the owning jar's session.** This is structural, not conventional: the chrome CSP forbids remote `img-src`/`media-src` origins (`img-src 'self' data: blob: goldfinch-media:; media-src 'self' blob: goldfinch-media:` — no `http:`/`https:`), pinned by `test/unit/csp-pins.test.js`. Favicons are fetched main-side in the guest's own jar session and delivered to the chrome as `data:` URLs (`favicon-fetch.js`). Media-panel remote URLs (thumbnails, posters, inline video, lightbox, docked audio) route through the `goldfinch-media:` proxy scheme below — never a direct `http(s):` assignment in `media-controller.js`.
- **`goldfinch-media:` scheme** (`src/shared/media-proxy.js`, `src/main/media-proxy-handler.js`): a session-scoped proxy, registered ONLY on the **default session** (`{ stream: true }` privileges) — the inverse trust direction from `goldfinch://`'s internal-session-only registration, but the same structural argument: jar-partitioned guest sessions have no handler for either scheme. `toMediaProxyUrl(wcId, url)` wraps only `http:`/`https:` targets into `goldfinch-media://proxy/<wcId>/<encoded url>`; every other scheme (`blob:`, `data:`) passes through unchanged — a call-site can never accidentally break blob-backed items by wrapping them. The handler resolves the live guest via `getTabContents(wcId)`, forwards the request through that guest's OWN session (`wc.session.fetch`, carrying `Range`/`Accept` only), and re-wraps the response with an allowlisted header set — the same re-wrap discipline as `handleInternal`, but streaming (no full-body buffering, required for media Range/seek to work at all).
- The internal view runs `contextIsolation: true`, `sandbox: true`, `preload: internal-preload.js`. The internal session is excluded from the web-content wirings (`applyShields`, downloads) via the `creatingInternalSession` flag + the `__goldfinchInternal` marker.
- **Address bar**: `updateAddressChip(tab)` (called from every address-sync site) sets internal/web/neutral chip state and makes the input `readOnly` on internal tabs. `#address-chip` also triggers the site-info popup (sheet-rendered; model from the shared `deriveSiteInfo`, `src/shared/site-info.js` — the one derivation source). "Site settings →" (`openSiteSettingsTab`) navigates an existing Settings tab **specifically** (host-only match, fragment- and path-blind — M16 F2 Leg 1, DD10; never any other internal tab) — or opens a new trusted one — to `goldfinch://settings/#privacy`. `navigate()` on an internal tab reroutes any non-internal URL to a new web tab (the UX half of isolation; the origin-checked `registerInternalHandler` is the security half).
- **Adding an internal page**: entry tree in `internal-page-map.js`; host in `INTERNAL_HOSTS` (`url-safety.js`); origin in `INTERNAL_ORIGINS` (both `internal-ipc.js` and `internal-preload.js`); open via the trusted `createTab` path — never by relaxing web gates.
- The downloads page's `internal-downloads-*` channels resolve the actionable `savePath` MAIN-SIDE by id. `src/main/jar-ipc.js` is a composition facade: registry/default twins live in `jar-registry-ipc.js`, data/retention twins in `jar-data-ipc.js`, and shared wipe/sweep sequencing in `jar-data-lifecycle.js`. Chrome and internal twins still execute the same named handler bodies. A successful wipe broadcasts `jar-wiped { id }` so chrome controllers close the jar's open tabs.

### `goldfinch://jars` page

Each persistent jar section renders a WAI-ARIA tab strip — History / Cookies / Other site data (`src/shared/jar-panel-model.js`'s `JAR_PANELS`; tablist build in `src/renderer/pages/jars-tabs.js`) — plus a footer (Wipe + Delete, jar-level actions outside every tab). Burner has no tabs (driven by `row.isBurner`, never an id check).

- Tab/tabpanel DOM ids use a **double-hyphen** separator `jar-<jarId>--<panelId>` — `slug()` collapses non-alnum runs to one `-` and never emits `--`, so jar names can't collide with region ids. Hash deep-links (`#jar-<id>--<panel>`) and the scroll-spy key off these ids.
- Every tab renders a live count badge ("<Label> (N)") inside its own label span, seeded by `jars-section-controller.js`'s build-time fetch and kept fresh by panel/invalidation routing — generic section/page render never writes these spans.
- `jars.js` is the jars-page composition root; `jars-page-state.js` owns pure reconciliation, `jars-nav-controller.js` owns navigation/scroll-spy, `jars-section-controller.js` owns persistent/Burner sections and panel composition, and `jars-create-controller.js` owns the stable create panel. Panel modules retain the constructor shape `{ bridge, jarId, mountEl, onError, onActivated? }`.
- **Retention**: `jars-section-controller.js` owns the per-jar header `<select>` and failure revert. `src/main/jars.js` validates/persists `retentionDays`; `jar-data-ipc.js` owns the twin handlers; `jar-data-lifecycle.js` owns immediate sweep sequencing. `session-runtime.js` owns boot/hourly `pruneAllJars`, scheduled by `app-lifecycle.js`.
- History is a fourth data class (`{ id: 'history', storages: null, custom: 'history' }` in `src/shared/jar-data-classes.js`); `handleClearData` dispatches on `d.custom === 'history'` **first**, ahead of the storages-null cache fallback (naive fallthrough would clear the cache while reporting history cleared).
- `handleWipe`/`handleRemove` share `jar-data-lifecycle.js`'s `wipeJarData(ses, jarId)`. `register-browser-ipc.js`'s `identity-new` deliberately does NOT purge history — it is an anti-tracking identity break, not a data-visibility control.

### Settings store (`src/main/settings-store.js`)

The canonical home for app preferences — do not scatter new prefs into ad-hoc constants or `shields.js`.

- **Electron-free**; `userData` injected at `load(userDataPath, opts?)` (called from `init-profile.js`'s `initProfileAndStores`, after `appDb.open`).
- Persists via the app-db `documents` row `'settings'` (transactional UPSERT). Write errors propagate. `load()` **never throws** — each field is validated per-key against `DEFAULTS`; a corrupt field silently repairs to its default, valid siblings kept, unknown keys dropped. The app must boot on a corrupt row.
- `VALIDATORS` maps each settable key to a predicate; `set(key, value)` validates **before** mutating and throws `TypeError` on unknown keys/invalid values. `homePage` requires `null` or (`isSafeTabUrl(v) && v !== 'about:blank'`) — `''` is never valid; `null` is the only unset representation (M16 F1 / DD2, `jsconfig.json` runs `strict: false` so this is enforced by the validator and unit tests, NOT by `strictNullChecks`). `searchEngine` requires `null` or membership in the curated table `src/shared/search-engines.js` exports (an ordered `{ id, label, template, description }` list, also consumed by the renderer's search-URL construction) — never a user-supplied URL template; an id removed from the table, or any other corrupt/unknown value for either `homePage` or `searchEngine`, repairs to **unset** (`null`) at load (M16 F2 / DD5 — repair-to-default no longer means silently selecting a provider or a home page on the user's behalf).
- **Schema `version` is 3, and the v2→v3 bump was a deliberate departure from this store's own ladder convention** ("only for changed defaults on existing keys" — see the `automationEnabled` comment in `DEFAULTS`). No default changed at v3; the bump existed solely to force `load()`'s save-on-migrate persist to write `searchEngine` and `homePage` explicit to disk for every profile that had run the Flight-1 build (M16 F1 / DD5) — including a row-less profile (pinned via a best-effort `save()` at the end of `load()`'s no-row branch) and a corrupt document row (also pinned, not just repaired in memory — closed by design review; a corrupt *legacy `settings.json` file* already saved unconditionally on the other import path). Rule of thumb: **any load path whose resolved config differs from the on-disk bytes persists the resolved config.** `migrateStored()`'s per-rung transforms are individually guarded on their own `from` threshold (not the single "from < current version" check that only worked while there was one rung) so a v2 row doesn't re-run the v1→v2 `restoreSession` discard.
- **`DEFAULTS.homePage` and `DEFAULTS.searchEngine` are `null` (M16 F2 "The Welcome Surface" / DD5) — NO v4 bump.** Flight 1's v2→v3 pin-on-load had already written both keys explicit into every profile that ran that build, so there was no on-disk population left for a v4 ladder transform to reach; the pin-on-load mechanism itself is unchanged, only what it pins (a row-less profile now gets `null`/`null` pinned explicit, not a Google-flavored default). A fresh profile therefore has neither preference set; the chrome-owned welcome surface (below) is what asks.
- **Pluggable `{ serialize, deserialize }` codec seam** — a future `safeStorage`-backed codec replaces only that pair. Do not add encryption now.

### Menu-overlay sheet

All chrome menus composite above the **live** guest from a transparent overlay `WebContentsView`.

- **Architecture.** A **per-window lazy singleton** (`src/renderer/menu-overlay.{html,js,css}` + `menu-overlay-preload.js`, chrome-class trust), managed by the Electron-free `src/main/menu-overlay-manager.js` (`createMenuOverlayManager`, injected deps, offline-tested), instantiated per window into the registry record's `sheet` slot — two windows can hold open menus simultaneously. Show = `addChildView` **after** the guest (z-order invariant); never focused before model init lands; hide = `removeChildView`; bounds track the active guest via the `tab-set-bounds`/`tab-set-active` hooks; `render-process-gone` → teardown-and-rebuild; destruction at per-window `close`. The sheet covers the **guest region only** (toolbar stays clickable; toolbar-anchored menus render flush at the sheet's top edge). Internal tabs are in scope (only the page-context menu excludes internal guests). Hosted surfaces: kebab, container picker, site-info, page context (+ toolbar-Unpin mode), the new-container `input-dialog`, tab-context, suggestions. Chrome owns triggers/models/actions; the sheet holds **no business logic and no privileged APIs** — it renders the model (labels via `textContent` only — guest/user strings never markup) and runs the APG contract via `menu-controller.js`.
- **Channel protocol (1–7).** 1 `menu-overlay:open` (chrome→main: `{menuType, model, anchor, startIndex, token}`); 2 `menu-overlay:close` (chrome→main, programmatic — incl. trigger re-click `toggle`); 3 `menu-overlay:init` (main→sheet; **pending-init queue**, latest-wins — absorbs the lazy first-load race); 4 `menu-overlay:activated` (sheet→main: `{id, token, value?}` — `value` sanitized main-side by `sanitizeActivatedValue`, string ≤24 or dropped); 5 `menu-overlay:dismissed` (sheet→main: `{reason, token}`); 6 `menu-overlay-activated` (main→chrome — the dispatch executes the action, validated-no-op on every id); 7 `menu-overlay-closed` (main→chrome — reset `aria-expanded`, resolve refocus per entry policy). On activation, **7 is emitted before 6**. A chrome-minted monotonic open-token rides 1/3/4/5/7; stale-token closes are dropped.
- **Close family.** Every hide routes through `closeMenuOverlay(reason)` — idempotent, the single mutation point. Reasons: `escape` / `outside-click` / `blur` (fired only when the blurred window is the sheet's own) / `activated` / `superseded` (open-while-open = **model-replace**, no hide/re-show flicker) / `toggle` / `tab-switch` / `tab-hide` / `tab-close` / `teardown`. `focusChrome()` runs for `escape`/`activated` only; fixed-trigger menus refocus their trigger; page-context and tab-context are escape-only → captured `returnFocus` else the address bar. A 300 ms same-menuType suppress window (chrome-side, armed on blur closes) kills the trigger re-click close-then-reopen blink.
- **Find interplay.** Sheet-show hides the find overlay; `closeMenuOverlay` restores it as an owned explicit step — except the tab-lifecycle reasons, which defer to `tab-set-active`'s per-tab restore (no double-handling).
- **Hardening.** All `menu-overlay:*` handlers are **sender-validated by webContents identity** (chrome for 1/2; the sheet's own wc for 4/5 — never payload-declared). The sheet is not in `tabViews`: invisible to `enumerateTabs`; non-tab non-chrome wcIds resolve **admin-only** (`isTabViewWcId` threaded into the engine). Sheet automation is governed by the **(menuType × op) gate** — see *Automation engine* below.
- **⚠ Eager close scrub (M15 F3 DD1f) — SECURITY, not tidiness.** There is now exactly ONE main→sheet close channel, `menu-overlay:close` (channel 8), sent by `closeMenuOverlay` **and** by `openMenu`'s model-replace branch when the menuType **changes**; the sheet's handler runs `report.silence()` then `menuController.closeAll()` immediately. This reverses the old *"deliberately NO main→sheet close channel; the hidden sheet keeps its rendered menu DOM"* rule, because that rule is what made a closed vault card's `textContent` co-resident with the next menu: `openMenu` sets `currentMenu` + `show()` **synchronously** and only then `deliverInit` crosses the IPC hop, so a lazy scrub leaves a window where main reports an admitted menuType while the DOM still holds the prior secret — narrower than human timing, therefore invisible to every live check. **Do not "simplify" it back to scrub-on-next-init.** A same-menuType model-replace deliberately does NOT scrub (the downloads in-place repaint needs `menuController.current` intact, and the residue is that card's own prior model). `<body>` data attributes are never cleared (the DD8 drag-probe readback depends on them).
- **Keep-focus opens (channel 9, `menu-overlay:refocus`, sheet→main).** A menu whose SPAWNING gesture also navigates the guest must survive the loading page's focus steal: `openMenu` payload `keepFocus: true` makes the sheet entry `dismissible: false` for that render (skipping the sheet controller's incidental window-blur/outside-click dismissal, exactly the `vault-capture` entry's fix) and makes the sheet report its blur back so `reassertFocus()` re-grabs OS focus — otherwise the card stays visible but unfocused and a typed master password lands in the page's own fields. Main gates the report on sheet-sender identity, `win.isFocused()` (a real app-switch must never pull focus back from another app — that case still closes main-side, `currentDismissible` stays true), and the menu's own opt-in; re-grabs are capped per menu session (`KEEP_FOCUS_MAX`) so a page that re-steals focus on a loop can't start a tug-of-war. Sole consumer: the `vault-unlock` prompt raised for a LOCKED-vault capture (unlock-to-save). Every deliberate decline path is unchanged.
- **Accelerators.** The sheet's `before-input-event` forwards the union set via pure `src/shared/sheet-accelerator.js`: guest-class actions (zoom, print, find, …) replicate against the ATTACHMENT window's active guest (internal-contents guard; Ctrl+F closes the menu then opens find); chrome-class actions ride `chrome-shortcut-action` → `dispatchChromeAction`. Unmodified APG keys (arrows/Home/End/Enter/Space/Escape/Tab) stay with the sheet — the menu contract wins inside the menu.

### App database (`src/main/app-db.js`)

Durable substrate for the five small config/state stores — settings, downloads, session, jars, shields — on built-in `node:sqlite`. It is a **clone of `history-store.js`'s seams, not a shared import**: `app.db` is independent of `history.db` (separate corruption/quarantine domains; the write-hot visits table never shares a file with config rows).

- **Substrate ruling**: built-in `node:sqlite` (`DatabaseSync`), no vendored native module — preserves the zero-runtime-dependency identity. It's an experimental API (`ExperimentalWarning` at require time is cosmetic, accepted). **Standing tax: every Electron major bump re-runs the full store suite (`history-store` + `app-db` + all five stores) and treats a `node:sqlite` API break as a first-class migration cost.** Decision records live in the respective `flight.md` files (missions 08/10).
- **One `documents` table, one row per store**: `documents(store TEXT PRIMARY KEY, payload TEXT NOT NULL, updated_at INTEGER NOT NULL)`. `createDocumentStore(name)` returns `{ read(), write(payload, now?), remove() }`; every store write is a transactional whole-document UPSERT of its serialized payload (all five are low-cardinality wholesale-replace workloads — the substrate buys corruption discipline + transactional writes, not indexing). Each store's public API, defaults/validators, legacy-shape handling, and codec seam survive verbatim — codec output lands in `payload`, keeping a future encrypted-codec swap codec-only.
- **WAL family + lifecycle**: `app.db` + `-wal` + `-shm` (`journal_mode=WAL`, `synchronous=NORMAL`). `appDb.open(userDataPath)` runs in `initProfileAndStores`; `app-lifecycle.js` then loads the session store from the open singleton. `app-lifecycle.js` closes app/history DBs at **`will-quit`**, after `before-quit`'s snapshot writers; `close()` checkpoints the WAL and is idempotent.
- **Migration — import once, rename `.migrated`**: at each store's `load()`, row-absent + legacy JSON present → parse through the store's existing load/repair logic → write the row → best-effort rename `<name>.json.migrated` (never fatal). A corrupt legacy file still migrates (the repaired result). Once a row exists, bare legacy files are ignored. **Carve-out**: jars' readable-but-unknown-schema-version `containers.json` never migrates — kept in memory, file untouched, so a future compatible build can recover the original envelope (pinned by `jars-security-forward-version.test.js`).
- **Quarantine → fresh defaults**: a corrupt `app.db` (+siblings) is quarantined to `.corrupt-<ms-epoch>` and recreated — the app must boot. Stores seed defaults; `.migrated` files are **never re-imported** (arbitrarily stale by then). Jars' post-quarantine reseed is branch-dependent on the legacy-partition probe (intentional parity with pre-migration behavior).
- Shields is at house discipline (injected `userDataPath`, codec seam, transactional writes). Pre-load `save()` stays a silent no-op, but once loaded a row-write failure **propagates** — `shields.set()`/`setPaused()` can reject through their IPC handlers.
- **`user_version` ladder is cumulative STEPS** (v0 → v1 → v2 in one open; a fresh profile never pauses mid-ladder). v2 adds `cookie_seen(jar_id, name, domain, path, first_seen_ms)` — retention-sweep bookkeeping, metadata only, via `createCookieSeenStore()` → `{ insertIfAbsent, deleteByIdentity, deleteByJar, selectExpired }`.

### History store (`src/main/history-store.js`)

Per-jar browsing history on a live `node:sqlite` handle — real schema/indexes/FTS, unlike the document-row stores (needs range queries + full-text search at scale).

- **Recording** (`src/main/history-recorder.js`, `createHistoryRecorder` — Electron-free injected-deps factory, constructed during `app-lifecycle.js` readiness; navigation hooks are installed by `register-tab-ipc.js`). Gates in order: (1) positive registered-jar allowlist; (2) `http:`/`https:` scheme allowlist; (3) per-jar 30 s consecutive-duplicate suppression. A per-`wcId` map backfills late titles; teardown calls `forgetTab(wcId)`.
- **Retention**: `retentionDays` lives on the jar record (integer 1–3650, default 30, validated by `cleanRetention`). `session-runtime.js` owns `pruneAllJars()`; `app-lifecycle.js` invokes it at store open and schedules the hourly `.unref()` cadence. It builds the live `{jarId: days}` map and GCs orphan history rows. Up to ~1 h over-retention accepted.
- **`history-changed { jarId }` invalidation contract**: every mutation broadcasts only `{ jarId }` — never rows or counts; subscribers re-query through their own read path (invalidation-not-snapshot, same as `jars-changed`).
- **IPC twins** (`src/main/history-ipc.js`): each handler body defined once, registered twice — bare `history-*` (chrome trust) + `internal-history-*` (`registerInternalHandler`). Ops validate fail-closed in order (malformed payload → unknown jar → bad args); every failure returns a **static, non-interpolated** `history: <op> — <code>` string.
- WAL family (`history.db` + `-wal`/`-shm`), closed at `will-quit`; a corrupt db is quarantined to `.corrupt-<ms-epoch>` and recreated.
- **Two live-probed sqlite gotchas**: never mix a bare `?` with numbered `?1`/`?2` placeholders in one statement (SQLite collapses them onto one bound slot); keep FTS5 on the default `unicode61` tokenizer — a `tokenchars` override turns a whole URL into one token and silently breaks prefix search.

### Jars page data panels

The Cookies and Other-site-data panels share the History panel's constructor shape.

- **Cookies panel** (`jars-cookies-panel.js`): lists the jar's live session cookies via `jars-cookies-list` — **never a `value` field, at any layer** (the handler strips it before it crosses the payload). Per-cookie delete reconstructs the removal URL via `jar-data-helpers.js`'s `cookieUrl` (scheme from `secure`; leading dot unconditionally stripped from `domain` — safe for both host-only and domain-attribute cookies). No confirm step (single cookie = low stakes).
- **Other-site-data panel** (`jars-sitedata-panel.js`): a composite union with **two-tier honest labeling** (Electron's `Session` exposes no origin-enumeration or usage/quota API): "Has stored data" = origins with an on-disk IndexedDB leveldb directory (`originFromIndexedDbDirname`; a literal `_0` port segment is Chromium's default-port sentinel, normalized portless — live-measured, not documented); "Visited — storage unconfirmed" = history origins with no IndexedDB confirmation. **Documented gaps — don't silently paper over**: Local Storage is a consolidated non-origin-keyed store (its origins are unrecoverable); never-visited third-party-only and localStorage-only origins are invisible to both tiers; no usage/quota figure anywhere (raw file sizes would mislabel leveldb overhead as user data). Per-origin delete uses the SAME storage-class set as the retention sweep (cookies excluded); a history row survives an origin clear — the origin downgrades to "visited", it doesn't disappear.
- **Freshness**: panels query on tab-SELECTION (not section visibility) and re-query on their own mutations. No live `cookies.on('changed')` UI subscription (page activity would spam every open jars page). Cross-path staleness is closed by the `jar-data-changed { jarId, classes }` broadcast — fired by `handleClearData` (classes actually cleared), `handleWipe` (unconditional), and the retention sweep's **completion** (never the `setRetention` invoke, which resolves before the async sweep finishes).

### Retention sweep (`src/main/retention-sweep.js`)

Generalizes the per-jar `retentionDays` dial (one window, all classes) from history to cookies + site data, riding the same cadence (boot + hourly, plus an immediate one-jar sweep on a retention edit). The engine is Electron-free/injected-deps — every dependency (`cookieSeen`, `historyOrigins`, `sessionFor`, `cookieUrl`, `now`) is a fake in the unit suite.

- **Two independently-aged classes (deliberate, documented asymmetry)**: cookies age by **first-seen** (Electron exposes no cookie creation time — the reason `cookie_seen` exists); storage ages by **origin last-activity** from history (`expiredOriginsForJar`). Origins with no history signal are never auto-swept (no honest age signal; operator-deletable from the panel).
- **Cookie bookkeeping**: the `session-created` hook attaches a `cookies.on('changed')` listener for jar-matching partitions (partition recovered from `ses.storagePath` via `partitionFromStoragePath` — the hook receives only the Session; never an eager `fromPartition` warm, since `session-created` fires only on a partition's FIRST `fromPartition`). **Overwrite-cause ruling (measured)**: a same-identity value refresh fires an `overwrite`/`removed:true` + `inserted` PAIR — the removal handler SKIPS deletion on `cause === 'overwrite'` (the row keeps its original `first_seen_ms`) and deletes on `explicit`/`expired`/`expired-overwrite`/`evicted`; inserts are `INSERT OR IGNORE`. Cold start: a live cookie with no row gets stamped `first_seen_ms = now` at the next sweep — honest, not backdated.
- **⚠️ SEQUENCING invariant (unit-pinned)**: snapshot the aged-out origins BEFORE the same pass's history prune, in BOTH `pruneAllJars` and `handleSetRetention` — the prune deletes exactly the evidence `expiredOriginsForJar` reads; a post-prune read sees nothing for the target case. Order: (1) snapshot, (2) history prune (sync), (3) async cookie/storage sweep from the snapshot.
- Sweeps are async, fire-and-forget, per-jar/per-item isolated; every promise chain ends in a terminal catch (log-and-drop; quit-during-sweep named-accepted). `jar-data-changed` fires on completion with the classes actually swept.
- **Will-quit quiesce guard**: the cookies listener outlives `appDb.close()` — every write checks `appDb.isOpen()` first and is try/caught, so a write-after-close can never throw into Electron's event dispatch and wedge quit.
- **Bookkeeping dies with its data**: per-cookie delete → delete-by-identity; cookies-class clear / wipe / remove → delete-by-jar. All fail-soft — a cleanup miss just re-stamps a survivor as "new" (harmless staleness, never a correctness bug).
- Other named-accepted gaps: ~1 h cadence over-retention; a page can refresh a cookie between the sweep's read and its remove (TOCTOU, bounded by the 1-day window floor).

### Address-bar suggestions

Frecency-ranked, prefix-matched history suggestions, merged with a per-jar bookmarks source (M15 F1 Leg 4, jar-addressed M15 F2 Leg 3), render on the menu-overlay sheet (the only surface that composites below the toolbar — chrome DOM is occluded by the guest).

- The `suggestions` sheet template is `role="listbox"`/`option` (all text via `textContent`); a row click sends channel-4 `{ id: 'sug:<i>' }` — **INDEX dispatch** (`sanitizeActivatedValue`'s 24-char cap forbids a URL riding `value`).
- **`noFocus` regime**: `deliverInit` is the sheet's sole focus site; a channel-1 `noFocus: true` flag gates that call, so keyboard-driven suggestion repaints never move OS focus off `#address` (existing callers omit it, unaffected). A pointer click still moves native focus — the grace timer exists for exactly that race.
- **Chrome-owned close matrix** (the non-focusing regime means no sheet-side blur/outside-click ever fires): Enter-with-selection or row click → `activated`; Escape → `escape` (input keeps focus + text); input emptied → `input-empty`; `#address` blur → `blur` via a 150 ms grace timer whose callback re-checks the captured token AND `document.activeElement` (lets a click's activation win the blur-vs-click race); tab switch → main's tab-switch close, PLUS the brand-new-tab path's explicit `closeSuggestions('navigation')` (`createTab`'s synchronous `activateTab()` precedes any IPC, so the ordinary close never fires there); `activateTab` bumps `suggest.seq` on every activation (invalidates in-flight responses for the previous jar); active-tab navigation → `navigation`. Main's Ch2 handler validates reasons against `MENU_CLOSE_REASONS` (unknown → `superseded`).
- **⚠️ Ch7-before-Ch6 activated nuance**: the Ch7 sink cancels the timers on every close, but clears `suggest.items`/`selectedIndex` only for reasons OTHER than `activated` — the immediately-following Ch6 `sug:<i>` dispatch must still resolve the clicked row from `suggest.items`; the Ch6 handler finishes the reset. A naive reset-on-every-reason silently breaks every pointer-click navigation.
- **Data path**: `history-store.js`'s `suggest(jarId, query, { limit = 6, now })` — age-bucketed frecency (≤4d→100, ≤14d→70, ≤31d→50, ≤90d→30, else 10; grouped by URL) over the FTS-narrowed subset, via the `history-suggest` twins + chrome-only `historySuggest` bridge. `suggest` has its own 1–10 limit clamp (distinct from the store's 1–500). The 1-char query rides an UNCOVERED prefix path (the FTS `prefix='2 3 4'` index) — a full-token scan, measured separately. Bookmarks (jar-addressed `bookmarksSuggest({ jarId, query })`, matched via `matchBookmarks`) are queried ALONGSIDE history via `Promise.allSettled` — never `Promise.all` — so a rejected/`{ok:false}` source degrades to `[]` independently and never blanks the other; results merge bookmark-first (see "Bookmarks" below for the source/cache side).
- **Gates**: pure `omnibox-suggest-model.js` `shouldQuery({ focused, isInternal, isBurner, value })` — burner/internal tabs structurally never query (positive allowlist, no negative exclusion). Scoped to the active tab's own jar. Responses re-validate the FULL gate at arrival (`acceptSuggestResponse`) — a stale response never model-replaces a menu the operator didn't ask for.

### Bookmarks

Jar-scoped end to end (Mission 15 Flight 2): a real `bookmarks` table keyed by `jar_id` (Leg 2), and every chrome consumer — cache, star, bar, overflow, omnibox, favicon writer, popover, page-context — re-derived against the active tab's jar (Leg 3). No `goldfinch://` page reads bookmarks; every consumer lives in the chrome renderer.

- **Store + identity** (`src/main/bookmarks-store.js`, `src/shared/bookmark-url.js`): a jar-keyed `bookmarks` table in `app.db` (schema v3, M15 Flight 2 Leg 2 DD1) — `id`/`jar_id`/`url`/`title`/`icon`/`position`/`added_at`, unique on `(jar_id, url)` (the SAME url in DIFFERENT jars is legal and independent — the feature's core claim), position-ordered per jar (gap-free `0..n-1`, DD2). The store is stateless and jarId-first (`list(jarId)`, `add(jarId, …)`, `update(jarId, id, …)`, `remove(jarId, id)`, `reorder(jarId, ids)`, `clearJar(jarId)`) — the id alone never authorizes a mutation. Flight 1's per-field validate/repair split moved from load-time array validation to READ-TIME per-row validation on `list()` (url/id DROP-worthy, title/icon REPAIRED in the returned copies only — a read never writes back). A corrupt `app.db` now quarantines the WHOLE file (settings/jars/shields/downloads/session/cookie-bookkeeping included), not just bookmarks — the document-row's independent per-store corruption isolation no longer applies (accepted trade-off, DD4); a migration-STEP bug (vs. file corruption) is distinguished by `err.errcode` and propagates instead of quarantining a healthy file (DD-B). `bookmarkUrlsMatch` (exact committed-URL string equality, no normalization) is the ONE identity predicate — the store's `add()`/`update()` dedupe (now per-jar), the chrome cache's `findByUrl`, and the star fill state all share it. `add()` is idempotent PER JAR (a re-add of an existing URL in the SAME jar returns the existing entry, no broadcast); `update()` REJECTS a URL edit that collides with a DIFFERENT existing entry IN THE SAME JAR (`{ok:false, reason:'duplicate-url'}`) rather than merging — the same URL in a DIFFERENT jar is never a collision.
- **Broadcast contract**: every mutation fires `bookmarks-changed` with `{ jarId }` (M15 Flight 2 Leg 2 DD5 — invalidation-not-snapshot, `jars-changed`/`history-changed` precedent) via `broadcastToChromeAndInternal`; subscribers re-query `bookmarksGet({ jarId })`. All six IPC channels are jar-addressed; the four mutation channels reject a `jarId` absent from `jars.list()` with `{ ok: false, reason: 'unknown-jar' }` (covers burner/internal/deleted-jar ids in one rule); `bookmarks-get`/`bookmarks-suggest` skip that check — an unknown jar naturally yields zero rows, and a read must never fail during the jar-delete race window. Lifecycle (DD9): deleting a jar drops its bookmarks (`jar-registry-ipc.js`'s `handleRemove`, its own fail-soft try/catch); the full identity wipe does NOT; a fifth `JAR_DATA_CLASSES` entry (`bookmarks`, mapped to the History panel on `goldfinch://jars`) clears them on explicit request.
- **Chrome cache** (`src/renderer/chrome/bookmarks-client.js`, `createBookmarksClient`, M15 F1 Leg 2, jar-aware rewrite M15 F2 Leg 3 L3-DD-A/A2/B): a lazily-populated `Map<jarId, list>` — `findByUrl(jarId, url)`/`listFor(jarId)` are SYNCHRONOUS over the map (`null`/`[]` on a cache miss — the DD6 first-sight flash, accepted); `ensureJar(jarId)` triggers an async `bookmarksGet({ jarId })` refresh once per unseen jar (in-flight de-dup), called from the read paths (star refresh, bar render). A `jars-changed` broadcast evicts map entries for jar ids no longer live (the recyclable-id defense — jar ids are DETERMINISTIC and REUSABLE once a jar is deleted) via its OWN independent subscription, reading that broadcast's `containers` array directly rather than `jars-client.js`'s reactive state, so eviction never depends on subscription-registration order between the two clients. A late-resolving `ensureJar` fetch for a jar evicted while it was in flight is DROPPED, not stored (re-checked against the same "last known containers" snapshot the eviction path maintains) — storing it would recreate the recycled-id hazard the eviction exists to prevent; before the first-ever `jars-changed` broadcast there is nothing to evict against, so the check fails OPEN (a cold-boot fetch is never spuriously dropped). `bookmarksClient.boot` stays joined in the startup `Promise.all` for contract stability but is now a **default-jar prefetch** (`jarsBoot`/`getDefaultJarId` late-bound closures sequence it behind `jarsClient.boot`, since the default id is unknowable at construction and can legitimately be `null` when Burner holds the flag) rather than an everything-fetch — the Flight 1 "first tab's star renders only after the cache is populated" guarantee narrows to first-sight-of-EACH-jar. ### Internal-bridge security model (`src/main/internal-ipc.js`)

`registerInternalHandler(ipcMain, channel, handler)` wraps `ipcMain.handle` with a two-condition sender check **before** the handler runs: (1) `INTERNAL_ORIGINS.has(event.senderFrame?.origin)` (a destroyed frame yields `null` → fails); (2) `event.sender.session.__goldfinchInternal === true` (strict equality). Any mismatch throws `'forbidden: non-internal sender for <channel>'` → a rejected `invoke` renderer-side. This is the authoritative boundary; the preload's `location.origin` guard is defense-in-depth only.

- **Node-vs-Blink origin gotcha**: Blink serializes a `{standard, secure}` scheme's frame origin to `goldfinch://settings` etc. — the correct values to match. Node's `new URL('goldfinch://settings').origin` returns `'null'`. Do NOT "fix" `INTERNAL_ORIGINS` to match Node's output.
- `internal-*` channels are origin-locked to internal pages; chrome channels (`shields-*`, `settings-get`, `automation:get-activity`, …) are bare `ipcMain.handle` on the `file://` chrome trust domain — see the bare-handle rule above; never wrap them with `registerInternalHandler`.
- **`chrome-welcome-set` (M16 F2 Leg 1, DD1) is a chrome-trust bare `ipcMain.handle`, NOT `registerInternalHandler`-wrapped** — the welcome surface is chrome DOM (`file://`), not a `goldfinch://` page. It is the one chrome-initiated settings WRITE (every other chrome settings channel is read/subscribe-only): restricted main-side to `homePage`/`searchEngine`, calling `settings.set(` literally (the broadcast-invariant net's detection half is a call-shape regex, squawk 0003) and `broadcastSettings()` itself — the `toggle-bookmarks-bar`/`unpin-toolbar-item` shape.

### Overlay-view patterns

Five patterns for any future main-owned overlay view:

1. **Electron's `findNext: true` means "start a NEW find session"**, not "step to next" — the inverse of the `<webview>`-era assumption. Main tracks the last query text and maps UI intent onto engine semantics (same text + Enter = step; changed text = new session). Migration-parity ACs need a spot-check of the underlying API contract, not just byte-parity.
2. **Pending-init queue**: a lazy overlay can receive its first payload before `did-finish-load`; sending immediately drops it. Queue at most one pending init (latest wins), flush on readiness.
3. **Sender-resolved close refocus**: when one IPC channel serves actors with different focus consequences, resolve behavior from the sender's webContents identity — never a payload flag.
4. **Electron-free injected-deps module** for main-side view logic (see Recurring module shapes).
5. **Enumerable vs addressable**: a view kept out of `tabViews` never appears in `enumerateTabs` (document this choice at construction) but stays addressable by wcId — admin-tier only. `enumerateWindows` reports every window's `sheetWcId`/`findWcId` directly (exact O(1) admin read; the old id-space probe walk is retired — `scripts/a11y-audit.mjs` reads `enumerateWindows` with **no fallback**). Absent id = never created (both overlays are lazy); present id + `sheetVisible: false` = instantiated but hidden. `activateTab` on a non-tab wcId returns a harmless `false`.

### Cross-view focus + tab-type idioms

- **Focus-then-send**: any branch forwarding a keyboard-input-expecting action to the chrome view (e.g. the guest→chrome Ctrl+L handoff) MUST call `getChromeContents()?.focus()` **before** `.send(...)` — the send drives only DOM focus; without OS focus you ship a focused-but-untypeable control. (The sheet's own chrome-shortcut branch deliberately omits `.focus()` — not a copyable template.)
- **Decide tab type with `isInternalTab()`/`isWebTab()`, never by reading `.trusted`** — trust is call-site provenance at `createTab`, not a tab-shape flag to re-read.
- **Patch in place, never rebuild, whatever holds `document.activeElement`** on broadcast-rendered pages — a rebuild loses the caret and fires `blur` → a spurious commit under commit-on-blur models (e.g. jar rename). One rule, all widget kinds — no per-widget carve-outs.

### Tab strip

- **Viewless welcome records (M16 F2 Leg 1, DD1/DD2/DD4).** A tab can exist with `wcId === null` past the boot round-trip: `openWelcomeTab({ container, reasons, pendingQuery })` builds a strip record exactly like `createTab`'s untrusted branch (jar resolution, strip insertion) but sends no `tab-create` IPC and stamps `tab.welcome = { reasons: Set, pendingQuery }`; the chrome-rendered welcome panel (`#welcome-surface`, a CSS child of `#webviews`; `welcome-controller.js`) shows while such a record is active. `attachView(tab, url)` is the ONLY place it acquires a view — validates with `isSafeTabUrl`, sends `tab-create`, then runs `onViewCreated(tab, wcId)`, the SAME wcId-arrival continuation `createTab` uses (extracted once so the two paths cannot drift). `openNewTab(container?)` is the resolver every "new tab" call site uses now that `createTab` has no default URL argument: a set home page always wins (`createTab`); an unset one opens a welcome tab whose `reasons` come from the pure `welcomeReasons(home, engine)` helper (`['home', ...(engine == null ? ['search'] : [])]`, M16 F2 Leg 2, DD7) — both blocks show when neither preference is set (including at boot, where the reasons are computed from the values the boot `Promise.all` **awaits**, `searchEngine` joining `homePage`, never from the live caches, which race that same barrier). Never in `tabViews` (main's registry) until `attachView` succeeds, so it is structurally invisible to `session-snapshot.js`, `closed-tab-capture.js`, and every cross-window move path (DD8/DD9 — no new exclusion code, just an absent entry). `applyToolbarAffordances(tab)` (Media/Shields/DevTools) and `updateNavButtons` (Back/Forward) both disable on `tab.wcId == null`, re-checked on `onViewCreated` too so an ordinary tab's buttons don't stay disabled after its view arrives; `tabContextModel`'s `hasView` param (default `true`) omits `duplicate`/`move-new-window`/`move-window:*` for one.
- **The search handoff (M16 F2 Leg 2, DD3).** `navigate(input)`'s merged body: empty/whitespace input is a no-op (no handoff, no navigation); otherwise `toUrl(input)` returns `null` when the input is a search and `currentSearchEngine()` is `null` — checked BEFORE the welcome-record attach branch (`attachView(tab, null)` would silently drop the query) — and routes to `handoffSearch(tab, capPendingQuery(input))` in `navigation-controller.js`: an already-viewless welcome record gets `'search'` added to `reasons` and the query stamped onto `pendingQuery` **in place** (latest query wins, re-rendered via the injected `refreshWelcome`); any other active tab gets a **new** `openWelcomeTab({ container: tab.container, reasons: ['search'], pendingQuery })` beside it — the page the user is on is never discarded. The page-context "Search for …" path (`renderer.js`'s `sel:search` dispatch) shares the exact same null-check-then-`openWelcomeTab` shape; `createTab` is never called with a `null` URL. `PENDING_QUERY_MAX = 2048` (`src/shared/search-engines.js`) caps the query at both capture sites via `capPendingQuery` (trim + truncate) and again inside `buildSearchUrl` itself (belt-and-suspenders) — the pending query is chrome-held per-tab state, never a URL, never persisted, and renders in the welcome panel via `textContent` only.
- **DOM/CSS structure** (`styles.css`): `.tab` is the pure sizing/query container (`flex: 0 1 240px`, `overflow: hidden`, `container-type: inline-size`, **no padding** — its container-query size equals its rect width); `.tab-row` carries the flex layout + padding. Three `@container` disclosure stages: title-hide at 72px, inactive-only close-hide at 56px (the active tab's close is never hidden), padding-compress at 40px on `.tab-row`. `.tab.active` carries a **64px min-width floor** paired with hiding its favicon when narrow — without the floor its close button shrinks to render outside its clipped bounds ("`display:block` in the DOM ≠ painted"); every other tab shrinks floorless. `#tabs` is `overflow: hidden` — no scrollbar at any count, by design.
- **⚠️ Container-query self-restyle is a silent no-op**: a `@container` rule whose selector targets the container element itself never applies — no error, no warning, `getComputedStyle` never reflects it. Only descendant selectors work.
- **DOM order is the single order authority.** The renderer's `tabs` Map is id→tab lookup ONLY (iteration order not load-bearing). `orderedTabIds()` is the one order-reading accessor; `commitTabMove(id, targetIndex)` the one order-mutating call. Never `[...tabs.keys()]` for order. `listTabs()`/`enumerateTabs` deliberately stays **creation-order** (FD ruling — consumers address by wcId, never position); `enumerateTabs` is an **all-windows census**: every row carries a registry-stamped `windowId` (the renderer never learns `windowId`), ordered by window creation then per-window creation, returned as a plain array. A mid-boot window contributes zero rows — `enumerateWindows().booted` is the completeness signal.
- **Tab activation under native DnD**: all tab drags (reorder, tear-off, cross-window) are native HTML5 DnD, which fires no trailing `click` — so the tab click handler's activate is **unconditional** (no suppression flag; don't reintroduce one), and a drag activates its tab in `dragstart` (Chrome parity).
- **Keyboard map** (all global chrome shortcuts, never lightbox-deferred, via the one classifier `keydownToAction` in `src/shared/keydown-action.js`): `Ctrl+Tab`/`Ctrl+Shift+Tab` + `Ctrl+PageDown`/`PageUp` cycle visual order with wrap; `Ctrl+1`–`8` jump to position (out-of-range no-op), `Ctrl+9` last; `Ctrl+Shift+T` reopens the last closed tab; `Ctrl+N` new window (lowercase-only; `Ctrl+Shift+N` deliberately unassigned); `Ctrl+Shift+ArrowLeft/Right` reorders the focused tab (strip-scoped, not global). - **Closed-tab stack** (`src/shared/closed-tab-stack.js`): pure, main-owned, bounded (25, oldest evicted) — **one global stack with `windowId`-tagged entries** (documented divergence from Chrome's per-window reopen; entries must outlive their window). - **Tab context menu**: right-click or Context-Menu key/Shift+F10 on a tab — one `contextmenu` listener per tab button handles both (Chromium dispatches the same native event for both; the document keydown catch-all's exclusion gate covers `target.closest('.tab')` — no parallel keydown listener). Pure model `src/shared/tab-context-model.js`, ids `tab:*`, **omitted-only** (the sheet has no disabled-item shape): `close-others` omitted when sole tab; `close-right` when none to the right; `reopen-closed` at an empty stack; `move-new-window` omitted at last-tab AND for internal tabs (its dispatch sends the strip snapshot to `tab-move-to-new-window`; main re-parents the live guest into a `noBootTab` window). Batch closes are **ordered sweeps**: snapshot the target ids, activate the ANCHOR first when the active tab is a target (Chrome parity), then close each — so `closeTab`'s next-tab fallback never fires mid-sweep. `duplicate` reads live url/title/container renderer-side + the `tab-history-snapshot` invoke (web tabs only), then `createTab(..., { restoreHistory, insertAt: sourceIndex + 1 })`. `reopen-closed` reuses `dispatchChromeAction('reopen-closed-tab')`; `openTabContextMenu` is synchronous (fed by the push cache).

### `action:rowId` confirm-transition key

When a shared confirm area serves N sibling-visible actions on one row (the per-jar data-controls block), key the open/swap transition on the **`(action, rowId)` pair** (compared string-or-null) — never a boolean. A boolean silently breaks the same-row action swap: no rebuild fires, leaving stale copy and handlers wired to the wrong action.

### Automation engine (`src/main/automation/`)

Programmatic drive + observe of tabs. `engine.js` is the single entry point; the pure op modules (`tabs.js`, `nav.js`, `input.js`, `observe.js`, `resolve.js`) hold the logic.

- **Injected deps, Electron-free**: op modules never `require('electron')` at module scope; `engine.js`'s `deps()` is rebuilt per call (a recreated window is always picked up). New ops follow the same shape.
- **`wcId` is the canonical tab handle** — per-tab state (locks, etc.) keys on the stable wcId, never a resolved `wc` reference.
- **Foreground-to-act + re-resolve — with a read/act ASYMMETRY.** Ops that need RENDERED OUTPUT (`actOn`/`actOnPaced`/`scroll`, `captureScreenshot`, `readAxTree`, `printToPDF`, `findInPage`) run resolve → activate → **re-resolve** → act (the pre-activate handle may be stale after the async hop; re-resolving re-applies the exclusions). **`readDom` and `evaluate` do NOT activate** — `executeJavaScript` works on background guests, and a read that steals the operator's foreground is the worse bug. Both halves are pinned in `automation-observe.test.js`; do not "harmonize" them. The raise is at WINDOW scope and lives in `tabs.activateTab` (routes to the owning window's chrome, then `win.focus()` + `registry.noteFocus()` — programmatic focus fires no focus event under WSLg). The predicate is structural: ops that call `activate` raise; ops that don't, don't.
- **`executeJavaScript` is the main→guest read path — not CDP.** Debugger-free, no single-client conflict, CSP-safe for self-contained reads. CDP `Runtime.evaluate` exists only to bypass page CSP for *library* injection (the a11y audit's case) — the opposite use case.
- **CDP is centralized in `cdp.js` and limited to `readAxTree` + `scroll`**: `withDebuggerSession` + one shared single-client lock Set keyed on wcId + the `debuggerUnavailable` refusal — attach on demand, detach in `finally`, never left attached. A busy debugger returns a discriminated `{ automation: 'debugger-unavailable', … }` refusal, not a throw; the shared lock means concurrent `scroll` + `readAxTree` on one wcId can't both attach. Why these two: no pure-JS path to the platform a11y tree, and `sendInputEvent` mouseWheel does NOT scroll `WebContentsView` guests (confirmed live) — `scroll` uses CDP `Input.dispatchMouseEvent` while click/type/key stay on `sendInputEvent`. Route any new debugger need through `cdp.js` — never a second attach path.
- **Menu-overlay sheet: the (menuType × op) gate** (M15 F3 DD1/DD1a–DD1f). `resolveContents`' guard 3 no longer refuses the sheet absolutely; it admits it **iff both allowlists pass**: (1) the sheet's **current** menuType is in `AUTOMATABLE_MENU_TYPES` (exported from `resolve.js`; seeded `bookmarks-overflow`, `bookmark-edit`) **and** (2) the op opted in with `allowSheet` — exactly three dispatch entries do (`readDom`, `readAxTree`, `captureScreenshot`). **Allowlist on both halves, never a denylist**: every other menuType, a `null` current menu (no menu open, or the sheet hidden), every other one of the 23 `WCID_FIRST_OPS`, and anything added later is **refused by default**, at every tier including admin. `sheetMenuFor(wc)` (window-registry) is threaded as a **live reader** into deps at **both** `createEngine` sites — the fallback is silent, so both are grep-pinned; the predicate is **fail-closed in shape** (an absent injection refuses rather than throwing a `TypeError` from inside a live guard). All three admitted ops snapshot `{menuType, token}` **inside the op after its first resolve** (`deps()` has no wcId, and the sheet is per-window-record) and **re-check after their async work**, discarding on mismatch — `token` too, so a close-and-reopen of the same menu also discards; `null → null` is not a mismatch. `captureWindow`'s sheet layer rides the **same imported predicate** (DD1c — it composited the visible sheet unconditionally, so admin captures returned `vault-unlock` pixels), post-await re-check included. The premise all of this rests on — that the sheet's DOM holds no closed menu's content — is made true by DD1f's eager scrub above, not assumed. **Why `readDom` is admitted though it executes script**: the distinction is *fixed app-authored snippet vs caller-supplied code*, not "executes script vs doesn't" — `evaluate`/`injectScript` inject into a realm that outlives the menu; "leaves nothing resident" is retired as the rule (`printToPDF` leaves nothing resident and is still refused). **Jar keys are refused by `out-of-jar` (session identity), not by this guard** — `scope.js`'s `memberDeps()` threads neither `isSheetContents` nor `isTabViewWcId`, so this leg widened the **admin tier only**.
- **Standing unobservable-surfaces list** (what no automation apparatus can see — check here before writing an acceptance criterion against a surface):
  - **Menu-overlay sheet — READABLE BUT NOT SCRIPTABLE since M15 F3.** Under `bookmarks-overflow` / `bookmark-edit`, admin may `readDom` / `readAxTree` / `captureScreenshot` it. Under every other menuType (kebab, container picker, site-info, page/tab context, suggestions, `input-dialog`, the whole `vault-*` and `auth-*` family) it is fully unobservable. `evaluate` / `injectScript` are refused on it **unconditionally**, so **axe-core auditing of any sheet state stays out of reach** (axe needs library injection into a realm that outlives the menu) — accessibility-*tree* inspection is what became reachable.
  - **Toast layer — wholly unobservable.** No apparatus reads it at any tier; assertions about toast copy are operator-only.
- **`automation:dev-invoke` is a deprecated, dev-only seam** (`!app.isPackaged`-gated; new dispatch keys auto-expose). Do not build durable consumers against it — the MCP transport is the supported path.
- **Bind model**: in production the Settings `automationEnabled` toggle is the **sole** bind gate (`shouldBindAutomation` in `src/shared/automation-dev.js`); enablement is human-only (minting a key never enables). In dev, `--automation-dev` force-binds without writing the setting — a complete no-op when packaged (every call site ANDs `!app.isPackaged`); dev runs are profile-isolated (`~/.config/goldfinch-dev`). Dev/admin key acquisition (the `AUTOMATION_DEV_MINT` stdout line) → `docs/dev-testing.md`.
- **Management UI** (`goldfinch://settings` → Automation): enable toggle, live MCP address + `.mcp.json` block, persisted `automationPort` (default 49707) with live rebind. `resolvePort` precedence is dev/prod split: dev honors `GOLDFINCH_MCP_PORT` (env > setting > default; an env pin binds-exactly-or-fails-loudly); production ignores the env (setting > default) with free-fallback to the next free port (the persisted preference is not overwritten; the bound port is surfaced live). Per-jar + env-gated admin key generate/rotate/revoke (show-once plaintext; only hashes stored). An ungraceful client disconnect (dropped standalone GET SSE stream) tears the session down so the activity indicator clears — teardown attaches on the GET stream only; trades away resumable-SSE, correct for these clients.
- **Convention: any handler that mutates settings directly must broadcast `settings-changed` itself** (`broadcastToChromeAndInternal('settings-changed', settings.getAll())`) — only the `internal-settings-set` path does it automatically; otherwise live UI silently lags.

#### `runSerialized` (`src/main/automation/toggle.js`)

The shared mutex serializing `applyEnabledChange`/`rebind` through one `inFlight` promise chain: single in-flight op; rejection-tolerant continuation (a failed prior op doesn't wedge the chain — each op still surfaces its own error to its own caller); identity-guarded `finally` clear (`inFlight === mine`). **Prefer `runSerialized` over a bare `await prior`** for serializing any mutating ops — a bare await wedges on a prior rejection.

#### MCP transport (`@modelcontextprotocol/sdk`)

The sanctioned first runtime dependency — pinned to an **exact** version, imported **only** in `src/main/automation/mcp-server.js` + the `main.js` mount. The engine and op modules stay SDK-free; the MCP layer is a thin adapter.

- Node `http.createServer` bound to **`127.0.0.1` only**, default port 49707, SDK `StreamableHTTPServerTransport` on the raw `(req, res)` pair; stateful sessions (per-connection `randomUUID`).
- **The Origin/Host guard runs FIRST** (`origin-guard.js` — pure, exhaustively unit-tested): a denied request gets a 403 and never reaches the SDK. A loopback bind is necessary but not sufficient — *this browser renders hostile pages*, which can reach a loopback server via DNS rebinding unless Origin/Host are pinned.
- **30 tools**: 18 drive (incl. `dragPointer`, a paced synthetic pointer drag — for NON-tab in-page drags; tab drags are native DnD, which synthetic injection cannot drive; unpaced bursts get coalesced by Chromium, so events dispatch one macrotask apart), 4 observe (`captureWindow` takes optional `windowId` and binds by window identity; `enumerateWindows` — not captures — is the window-topology read), 2 eval (`evaluate`/`injectScript` — `executeJavaScript` in the guest main world, zero CDP; the internal session is excluded even for admin; `evaluate` returns must be JSON-serializable), 2 devtools, 3 admin chrome/app-level (`getChromeTarget` (optional `windowId`), `enumerateWindows` — the single window-topology discovery primitive, one row per window `{windowId, chromeWcId, booted, activeTabWcId, lastFocused, sheetWcId?, sheetVisible, findWcId?, findVisible}`, zero cached state — and `downloadsList`; jar keys get `automation: admin-only`), 1 jar-confined `getHistory` (a jar key reads its own jar; admin reads any known jar with `jarId` required). Result semantics: drive ops → JSON text; screenshots → image content; the `openTab`-`null` and `debugger-unavailable` outcomes are **normal results** (read and react), not `isError`. Full consumer reference: `docs/mcp-automation.md`; runnable client: `scripts/mcp-example-client.mjs`. The repo `.mcp.json` ships an empty `mcpServers` map — off-by-default; consumers opt in at their configured port. The 5 **vault** tools (`vaultUnlock`/`vaultList`/`vaultTotp`/`vaultFill`/`vaultAnswerAuth`) are non-engine-op — see the **Password vault** pattern.

### Password vault

Encrypted per-jar + global credential vaults (Mission 12). A self-contained substrate: `.gfvault` files + `manager.json` under `userData/vaults/`, **not** `app.db`; zero runtime deps (`node:crypto` only). Full reference: `docs/vault.md`.

- **Module layout.** `src/main/vault/`: `vault-crypto.js` (pure crypto core — AES-256-GCM items, the four envelope ops, `.gfvault` serialize/parse, RFC-6238 TOTP), `vault-store.js` (stateful `manager.json` + `.gfvault` persistence, unlock lifecycle, rotations, export/import, `deleteVault`/`hasVault`), `vault-context.js` (per-session fill-only automation ctx), `vault-human.js` (gesture picker/fill/capture), `psl.js` (vendored PSL). `src/shared/`: `vault-item-schema.js` (per-type secret/non-secret SSOT — the metadata whitelist + save-preserve complement), `origin-match.js`, `reserved-ids.js` (`GLOBAL_ID`), and the `vault-*-template.js` sheet family. **Chrome side** (M15 F2 Leg 1, extracted from renderer.js): `src/renderer/chrome/vault-controller.js` (`createVaultController`, the `downloads-controller.js` shape) owns the flow end to end — the pick-and-fill state machine, the picker/capture sheet openers, the lock indicator, every cross-renderer vault trigger, and the vault-owned overlay-menu states/dispatch/close handling; `renderer.js` only constructs it and chains its `handleActivation`/`handleClosed` ahead of the generic dispatch (the `downloadsController` precedent).
- **MRK model.** One random 256-bit Manager Root Key wrapped THREE ways in `manager.json` (scrypt/master, HKDF/recovery, X25519/admin); every vault key is wrapped under the MRK (one `mrk` envelope per `.gfvault`), so master OR recovery OR admin opens everything — including jars created after setup — and a rotation rewrites ONLY `manager.json`. A per-jar automation access key wraps a single vault key DIRECTLY (holds no MRK envelope → opens only its own vault). Keys live main-process-only as Buffers; idle auto-lock + lock-on-quit `.fill(0)`-zeroize. **Load-loudly** (opposite of `app-db.js`): a tampered/unknown-version file throws a typed error and is NEVER quarantined.
- **Fill trust boundary (F2 DD5 / F3).** No master-equivalent secret ever enters the vault PAGE DOM (`goldfinch://vault`); entry/display route through the chrome-owned **menu-overlay sheet** over a **dual-zeroized Buffer channel** (secrets ride as `Uint8Array`, never a JS string; main zeroizes its copy + the transferred array). One-time recovery-key / admin-key displays are **dismiss-locked** (`dismissible:false` — only explicit acknowledge closes; the value is unrecoverable). The internal `goldfinch://vault` page can't be axe-audited via `--target` (the accepted settings-class a11y gap); the sheet states ARE audited.
- **Sheet family.** Eleven `src/shared/vault-*-template.js` sheets (`vault-unlock`/`set`/`recovery`/`stepup`/`accesskey`/`adminkey`/`import`/`change-master`/`recover`/`picker`/`capture`), rendered by `src/renderer/menu-overlay.js` on the per-window sheet — same model-render-only, APG-contract discipline as the **Menu-overlay sheet** pattern.
- **Payment cards (issue #152).** Card items fill and capture in-page like logins, with ONE deliberate asymmetry: **a card fill is not origin-gated at all** (a card belongs to the operator, not to a site — `reachableCardItems(jarId)` takes no origin). Every other gate is identical (unlocked → persistent jar → jar+global scope → top-frame → explicit picker selection), and the branch is chosen by the **stored item's own `type`** inside `fillHuman` — never by anything the guest/page/chrome sends, so a page can't steer a login onto the card path. Guest detection is ROLE-based off `autocomplete` `cc-*` tokens (`src/preload/vault-card-fields.js`) with a narrow name/id fallback that is skipped entirely on any form that hints at all; cards ride their own `vault-fill-card` channel and the gesture fill-target is **kind-tagged** so the two families can't cross-consume. Capture adds a **plausibility gate with no login equivalent** — 12–19 digits passing Luhn (`src/main/vault/card-identity.js`) — because a card field is detected heuristically where a password field is self-identifying; capture identity is the **full PAN**, never last4 (two cards can share a last4). PAN/CVV/expiry stay secret per `vault-item-schema.js` — the picker, offer and sheet carry only title/cardholder/brand/last4. **The MCP surface stays login-only**; `docs/mcp-automation.md`'s "never card data" guarantee is unchanged.
- **Automation surface.** Fill-only (`vaultUnlock`/`vaultList`/`vaultTotp`/`vaultFill`/`vaultAnswerAuth`, non-engine-op, per-session ctx) — a password is never returned; two access-key tiers (per-jar secret → own vault; X25519 admin key → all vaults); jar-membership + top-frame origin gates on fill (`vaultAnswerAuth` matches against the pending CHALLENGE URL's origin instead and answers the browser-owned basic-auth prompt — see **Auth challenges**); session-scoped zeroization; audit = resolved origin + unlock count, never a secret (`deriveAuditDetail`).
- **Seam contract.** The vault work's leg-authorized additions carried the evaluate-seam closed set to **`SEAM_COUNT` = 27**; M14 F1's auth-basic + cert-picker a11y hooks carried it to **31**; M15 F1 Leg 2's bookmark-edit popover carried it to **32**; M15 F1 Leg 3's bookmarks-overflow chevron menu carried it to **33**; M16 F2 Leg 1's `openNewTab` (a non-a11y, behavior-spec-driven addition — welcome-home-routing step 5's burner path) carried it to **34** (`test/unit/seam-contract.test.js`, dual-sourced with the `### src/shared/ ESM modules` seam note) — a further seam change updates both in lockstep (FD ruling).

### Auth challenges (HTTP basic auth + client certificates)

`src/main/auth-challenges.js` (M14 F1) — one shared Electron-free store behind both `app.on('login')` and `app.on('select-client-certificate')` (both registered top-level in `app-lifecycle.js`, both unconditionally `preventDefault()`ed), with per-window FIFO queues, challenge `kind` (`'basic-auth'` / `'client-cert'`), and chrome-sheet presentation (`auth-basic` / `cert-picker` on the menu-overlay sheet).

- **⚠️ INVARIANT: every Electron auth callback is resolved exactly once — `resolveOnce` is the SINGLE callback site** (source-scan pinned in `auth-challenges.test.js`; even the routing ladder's silent cancels mint a challenge shell and resolve through it). Every close reason maps to one of two buckets: **resolution** (escape / outside-click / activated / tab-close / teardown — and the fail-safe default for any UNKNOWN reason) or **occlusion** (blur / superseded / tab-hide / tab-switch — the challenge re-presents later). Never call a challenge's callback anywhere else, and never add a close path that can leave a callback dangling.
- **Cert selection is human-only.** The agent seams (`getPendingChallenge` / `answerWithCredential` — the `vaultAnswerAuth` path) kind-filter to basic-auth, so a string credential can structurally never reach a Certificate callback; the sheet never closes itself on answer — the store owns the single close site.

## Release / CI

Both workflows are supply-chain hardened; preserve these invariants:

- **All `uses:` pinned to full commit SHAs** with a trailing `# vX.Y.Z` comment — never mutable tags. When bumping an action, **including accepting a Dependabot PR**, resolve the new version's commit SHA and pin to that (Dependabot proposes mutable tags; applying them verbatim regresses the hardening).
- **Least privilege**: top-level `permissions: contents: read`; only the `create-release`/`build` jobs escalate to `contents: write` per-job.
- `ci.yml` (PRs): `npm ci → test → typecheck → lint → npm audit --audit-level=high → package`. A high in a dev-only dep is fixed by bumping the dep, never by lowering the gate.

### Cutting a release (`build.yml`, on `v*` tag push)

Tag-driven — full flow in `docs/RELEASING.md`. Short form: from green `main`, `npm version patch -m "release-prep: bump to %s"` (the `version` npm-lifecycle hook regenerates the README download links into the same commit — there is no post-release README job) then `git push --follow-tags`. Strict semver is enforced; a prerelease tag publishes as a GitHub prerelease. Rollback: `gh release delete vX.Y.Z --yes --cleanup-tag`, fix, re-tag. App icon: `build/icon.png`.
