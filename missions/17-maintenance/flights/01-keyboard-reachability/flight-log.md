The unit layer proves the classifier decision and the chrome-side dispatch wiring (`shortcut-controller.js`'s new cases, unit-pinned); it cannot prove the gesture actually moves OS focus in the running app — that is AC6's job.

**DD2 (exhaustion signal) — unit layer.** `tabBoundary(doc, direction)` is unit-pinned across every edge case in the spec (first/last/only/none, `disabled`, `hidden`, `tabindex="-1"`, an invisible element via `getClientRects().length===0`, `contenteditable`, `iframe`-as-tabbable, both directions — `test/unit/tab-boundary.test.js`, 16 cases). Both guest preloads' capturing-listener + captured-native + payload-minimal-send shape is source-pinned (`guest-tab-boundary-preload-pin.test.js`), and the main-side forwarder's sender-derived-wcId / direction-allowlist behavior is unit-pinned (`register-browser-ipc.test.js`). The `preventDefault`-at-the-boundary ordering ruling is implemented as specified (captured native, called only when `atBoundary`) but **whether the async main round-trip is actually clean in the running app — no flicker, no stray keystroke landing in the guest before the handoff completes — is an AC6 finding, not something the unit layer can observe.**

**DD3 (guest-side change) — unit layer.** `crossViewNavAction` no longer returns `'tab-handoff'` for unmodified Tab (returns `null`); `test/unit/cross-view-nav.test.js`'s pinned case was renamed and inverted in place (not deleted-and-re-added), `'Shift+Tab → null'` and every existing-accelerator regression guard left unchanged and green. This proves the guest→chrome bridge no longer claims Tab at the decision-function level; it does not by itself prove Chromium's own default Tab action now runs mid-page in a live guest (`guest-wiring.js`'s `handleCrossView` was not modified — it already only hard-codes `'focus-address'` for whatever action it receives, so retiring `'tab-handoff'` at the source needed no corresponding edit there).

**DD4 (chrome-side placement) — unit layer.** Forward-boundary → `#address` focus+select and backward-boundary → the chrome's own last visible tabbable are both unit-pinned in `shortcut-controller.test.js` via a fake chrome-document tabbable pair (asserts the LAST one is picked, not the first). `focusActiveGuest()` → `tab-focus-guest` is unit-pinned end-to-end (active-tab-only resolution, refuses no-active-tab / stale-tabViews / non-chrome-sender, never cross-window — `register-tab-ipc.test.js`, 5 cases). The collapsed-panel phantom-focusable fix (`visibility: hidden` in `styles.css`) has no dedicated unit test (no existing CSS-pin convention covers `.collapsed` — `bookmarks-bar-css-pin.test.js`'s pattern is for a different, numeric-value contract) — its correctness is a live-render question for AC6/a11y follow-up, not something a unit test can assert without becoming a change-detector on unrelated CSS. Popups: no code changes — `chromeForTab` still does not resolve a popup wcId (unchanged, pre-existing, cited in the leg's Context), so the boundary forward is structurally a silent no-op there; accepted and recorded, matching the leg's Edge Cases.

**DD5 (preload bundling) — unit layer.** `scripts/build-preload.mjs` now bundles both `webview-preload.js` and `internal-preload.js`; `main.js`'s `internalPreloadPath` points at the new bundle. `test/unit/internal-preload-bundle.test.js` (cloned from the existing web-bundle test) proves the same three sandbox-loadability properties for the internal bundle: no surviving relative `require()`, `require('electron')` stays external, `tabBoundary`/`tabSequence` are inlined. `npm run build:preload` was run to completion multiple times in this session with both bundles produced successfully — esbuild bundled the internal preload without incident (it is plain CJS with `contextBridge`/`ipcRenderer` usage only, no dynamic-require or other pattern esbuild would choke on). The rejected-alternative note (inlining `tabBoundary` into `internal-preload.js` instead of bundling) was not revisited — bundling worked cleanly on the first attempt.

## Deviations

- **Chrome-side "last visible tabbable" is a local reimplementation, not a literal reuse of `tab-boundary.js`.** DD4's Context/Outputs language ("the same `tabBoundary`-family helper") reads as importing the shared module from `shortcut-controller.js`. That's structurally impossible: `tab-boundary.js` is CJS-by-design (`module.exports`, required by the two Node-context preloads), while `shortcut-controller.js` is a real browser ES module loaded by the chrome document — which runs `contextIsolation:true, nodeIntegration:false, sandbox:false` (no `require()` reaches chrome-document scripts at all; only the preload's `contextBridge` surface does). A CJS module cannot be `import`ed by a browser `<script type="module">`. I implemented `lastVisibleChromeTabbable()` as a small local pure function inside `shortcut-controller.js`, using the identical selector list and the identical `getClientRects().length===0` visibility filter — same algorithm family, not the same file. This is documented inline in the source and is why `#media-panel.collapsed`/`#privacy-panel.collapsed` needed `visibility: hidden` (both the shared module's filter and this local mirror rely on the same zero-client-rects test). Flagging for the FD in case DD4's wording should be amended to describe this explicitly, or in case a future leg wants a shared ESM-and-CJS-dual-export version of the boundary sequence logic to close this duplication.
- No other deviations from the Implementation Guidance's rulings.
