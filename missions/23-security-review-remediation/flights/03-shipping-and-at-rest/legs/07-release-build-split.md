# Leg: release-build-split

**Status**: in-flight
**Flight**: [Shipping and At-Rest](../flight.md)

> Developer design review 2026-11-17: **approve with changes**, incorporated — only the Windows name differs on disk today, and an explicit `artifactName` changes how the builder treats the architecture, so the exact per-target settings are given; "five installers and nothing else" is done by staging exactly those five files, not by trusting the builder's output; the start check proves the app got as far as opening its database, not merely that a process exists; the profile is redirected with `--user-data-dir`; the exact `codesign` commands; `compression-level: 0`; the `upload` job needs the same `always()` condition `build` has; an existing test reads this workflow's `semver=` line; the invariant test is text-based.

## Objective

The release workflow's build job — the one that runs dependency install scripts and the project's own build — holds no write access and no token, and a separate job that runs no project code checks, names and uploads the installers.

## Context

- Flight DD4 (mission finding 19: release workflow token scope), shape **(a)**. Leg `release-integrity` then adds provenance, the stable-tag check and the documentation on top of this topology; this leg changes who can write, not what is published as proof.
- **Today** (`.github/workflows/build.yml`): top-level `permissions: contents: read`; `create-release` (tags only, `contents: write`: validates the tag as strict semver, classifies stability, checks out, creates a draft with generated notes); `build` (matrix mac / linux / win, **`contents: write`** for its whole length: checkout with default persisted credentials, `setup-node` with `cache: npm`, `npm ci`, version from tag, `npx electron-builder --<platform> --publish always|never` with `GH_TOKEN` in the environment); `publish-release` (`contents: write`: flips the draft to published, prerelease or latest). The header explains that installers go straight to the release because artifact storage once blocked releases (v0.5.x, when the repository was private).
- **Q7 is not settled by documentation.** GitHub's billing pages describe artifact storage metering for private repositories and do not say whether public repositories are unmetered (read 2026-11-17). The repository is public now. **The first manual dispatch run of the changed workflow is the measurement**: if passing installers between jobs fails on a storage quota, this leg falls back to DD4's shape (b) — one job, the token given only to the upload step — and says so.
- **Asset names are a contract.** `scripts/update-readme.mjs` links exactly: `Goldfinch-Setup-${version}.exe`, `Goldfinch-${version}-arm64.dmg`, `Goldfinch-${version}-arm64-mac.zip`, `Goldfinch-${version}.AppImage`, `goldfinch_${version}_amd64.deb` (the published names on v0.19.15). The builder's publisher produces the space-free Windows name at upload; on disk the installer is `Goldfinch Setup X.exe`. With `--publish never` and a plain upload, the names must be right on disk.
- **Flight Director decision at leg design: the updater metadata is no longer published.** `latest.yml`, `latest-mac.yml`, `latest-linux.yml` and the `*.blockmap` files are produced whenever a publish target is configured; nothing reads them (the app notifies, it does not self-update — mission decision). After this leg a release holds the five installers and nothing else. Recorded for the operator to overturn; if overturned, the expected-name list in the upload job grows and nothing else changes.
- **macOS is verified here or nowhere** (operator has no Apple hardware; Q5). The macOS build runner can do what this host cannot: check the fuses on the built app, verify its ad-hoc signature after the fuse change, and start it. That check is this leg's.
- Workflow invariants that must survive (CLAUDE.md, *Release / CI*): every `uses:` pinned to a full commit SHA with a trailing `# vX.Y.Z` comment; least privilege with per-job escalation; a prerelease tag publishes as a prerelease; a manual dispatch publishes nothing.
- **Nothing in this leg can be proved without running it on GitHub.** That needs the flight branch pushed and a manual dispatch — the operator's actions, or done on the operator's explicit word (see the checkpoint in Acceptance Criteria).

## Acceptance Criteria

- [ ] **AC1 — Names fixed in `package.json`.** Read from the builder's sources at design review: today only the Windows installer differs on disk (`Goldfinch Setup X.exe`; the publisher renames it at upload), and once an `artifactName` is set the builder stops dropping the default architecture and uses the pattern literally. So, per target and **never** at the top level or under `linux` (that would apply one pattern to both Linux targets): `nsis.artifactName` `${productName}-Setup-${version}.${ext}`; `dmg.artifactName` `${productName}-${version}-${arch}.${ext}`; `mac.artifactName` `${productName}-${version}-${arch}-mac.${ext}` (read by the zip target; the dmg reads its own first); `appImage.artifactName` `${productName}-${version}.${ext}` (no `${arch}` — it would become `x86_64`); `deb.artifactName` `${name}_${version}_${arch}.${ext}` (`amd64` is the builder's deb name for x64). `build.publish` stays as it is (the update check's slug guard reads it). The result is the five published names on disk for every platform. A unit test derives the five names for a sample version from `package.json`'s templates and from `scripts/update-readme.mjs`'s links and asserts they are identical (drift guard, throwing if either source cannot be parsed). The test substitutes the placeholders by hand, so it proves the templates agree with the README links — **not** what the builder writes; the local Linux build below is that proof for Linux, and the dispatch run for Windows and macOS. Shown locally for Linux: `npx electron-builder --linux --publish never` writes `Goldfinch-<v>.AppImage` and `goldfinch_<v>_amd64.deb` (nothing from `dist/` is launched).
- [ ] **AC2 — The build job cannot write.** `build`: `permissions: contents: read` and nothing else; checkout with `persist-credentials: false`; **no** `GH_TOKEN`, `GITHUB_TOKEN` or `secrets.*` reference anywhere in the job; `npm ci`; version from tag as today; `npx electron-builder --<platform> --publish never`; the fuse check (`node scripts/check-fuses.mjs <binary>`) on that platform's unpacked app; then a **staging directory** receives only that platform's installers by their exact expected names (the builder also writes `latest*.yml`, `*.blockmap`, debug files and the unpacked tree — none is copied; a missing expected file fails the job) plus a SHA-256 list of them; `actions/upload-artifact` (pinned by SHA) uploads that directory with `retention-days: 1` and `compression-level: 0`, one artifact per platform. `CSC_IDENTITY_AUTO_DISCOVERY: 'false'` stays on the build step. The no-token build has never run (today's dispatch has the token set) — the dispatch run is its proof. `setup-node`'s npm cache is used on a manual dispatch only, never on a tag build.
- [ ] **AC3 — Each platform's build is started once.** After packaging, the job starts the unpacked app with `--user-data-dir=<a fresh temporary directory>` (the app never touches that switch; Chromium resolves it on every platform, which avoids the differences between `HOME`, `APPDATA` and macOS's *Application Support*), polls for up to about thirty seconds, and requires **all three**: the main process is still running; the profile's `app.db` exists (the app opens it in its ready chain, so this shows the boot got that far — confirm the file name in `src/main/app-db.js` / `init-profile.js`); and the profile holds no crash log (`crash-log.js`'s file). Then it stops the process (Windows: `taskkill //F //T //PID` from bash). The unpacked-binary path is named once per platform and reused for the fuse check, the signature check and this start. Per platform: macOS (`dist/mac-arm64/Goldfinch.app`, preceded by `codesign --verify --deep --strict --verbose=2 "$APP"` and `codesign -dv "$APP" 2>&1 | grep -q 'Signature=adhoc'` — the proof that the fuse step's `codesign --sign - --force --deep` left a valid ad-hoc signature on the whole bundle; never `spctl`, which rejects any ad-hoc app), Windows (`dist/win-unpacked/Goldfinch.exe`), Linux (`dist/linux-unpacked/goldfinch` under `xvfb-run -a`; the Ubuntu runner restricts unprivileged user namespaces, so first try keeping the real sandbox with `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` on the throwaway runner, and only if that does not work pass `--no-sandbox` with the reason written beside it — the dispatch run measures which). A build that will not start fails the job. If a platform's start check cannot be made reliable on its runner after honest effort, it is made non-blocking **for that platform only**, with the reason written beside it, and macOS's `codesign` verification stays blocking regardless.
- [ ] **AC4 — The upload job runs no project code.** A new `upload` job (`needs: [create-release, build]`, with `if: always() && needs.build.result == 'success' && (needs.create-release.result == 'success' || github.event_name == 'workflow_dispatch')` — `create-release` is skipped on a dispatch, as it is for `build` today): **no checkout**, no `npm`, `npx` or `node` invocation; `actions/download-artifact` (pinned by SHA); re-computes every file's SHA-256 and compares with the list from the build; asserts the set of file names is **exactly** the five expected names for the tag's version, computed in the job from the tag (a missing, extra or renamed file fails before anything is uploaded); then `gh release upload "$GITHUB_REF_NAME" --repo "$GITHUB_REPOSITORY"` into the draft, the token given to that one step. It holds `contents: write` and no other permission (leg `release-integrity` adds the attestation permissions here). On a manual dispatch the job runs everything **except** the upload, so a dispatch exercises the whole path and publishes nothing. The expected names come from one small shell function of a version string: on a tag the version is `${GITHUB_REF_NAME#v}`; on a dispatch it is the committed `package.json` version, carried in the artifact. Because a dispatch never runs the tag branch, a unit test extracts that function from the workflow text and runs it with sample refs, including an `-rc.1` version, against the README-link names.
- [ ] **AC5 — The rest of the workflow.** `create-release` loses its checkout (it uses only `gh` with `--repo`); `publish-release` is unchanged in behaviour, now `needs` `upload` and requires its result to be `success`; the `semver=` line in `create-release` keeps its exact form (`test/unit/update-version.test.js` reads it as a drift guard); top-level `permissions: contents: read` stays; the header comment is rewritten to say what is true now (why installers pass through artifact storage, retention one day, what the dispatch does). What the digest comparison proves is stated honestly in a comment: integrity between jobs, not that the build job was honest — the build job is the party being contained.
- [ ] **AC6 — Invariants pinned by a unit test** (new; **text-based**, in the style of `ci-image-pins.test.js`, slicing jobs by their two-space keys under `jobs:` — the only YAML parser in `node_modules` is transitive, and this flight's rule is that a transitive package is not imported; no test pins `uses:` lines today): every `uses:` in both workflows is `owner/repo@<40 hex> # vX.Y.Z`; top-level permissions are exactly `contents: read`; the `build` job's permissions are exactly `contents: read` and its text contains no `secrets.`, `GH_TOKEN` or `GITHUB_TOKEN`; every `actions/checkout` step sets `persist-credentials: false`; the `upload` job contains no checkout and no `npm` / `npx` / `node` run line; `--publish always` appears nowhere; `retention-days: 1` and `compression-level: 0` are present on the artifact upload. The scan runs on the working tree's `ci.yml` as leg `runtime-fuses` left it. Each assertion throws rather than passing if its landmark is missing; each is neuter-verified once (break the workflow in a scratch copy, see the test fail) and the log says so.
- [ ] **AC7 — New actions are pinned from the source.** The commit SHA for each newly used action version is resolved from that action's repository (`gh api repos/actions/<name>/git/ref/tags/<tag>`, following an annotated tag to its commit), never copied from memory or a search result; the log records tag → SHA for each.
- [ ] **AC8 — Checkpoint: a manual dispatch run on GitHub.** After the Reviewer-independent checks above pass locally, the Developer stops with `[HANDOFF:review-needed]` and the leg stays `in-flight`. The Flight Director asks the operator to push the flight branch and start a manual dispatch of *Build installers* on it (or to say explicitly that the Flight Director may). The leg lands when a dispatch run is green on all three platforms **and**: the `build` jobs' logs show no token in the environment and `contents: read`; each fuse check and start check ran (macOS `codesign` verification passed — this closes Q5 as far as it can be closed); the `upload` job's name and digest assertions passed and it uploaded nothing; no release or tag was created. A red run is fixed by a new Developer pass and re-dispatched. If artifact upload fails on quota: fall back to shape (b), record Q7 as answered "no", and re-dispatch.
- [ ] **AC9 — Docs.** `docs/RELEASING.md`: the job list and what each may do; that a release now holds five installers and no updater metadata; that a manual dispatch runs everything but the upload. CLAUDE.md *Release / CI*: the per-job permissions line corrected (`create-release`, `upload`, `publish-release` write; `build` never), the new invariant test named.
- [ ] **AC10 — Gates.** `npm test`, `npm run typecheck`, `npm run lint`, `npm run format:check`.

## Edge Cases

- **A matrix job cannot export per-platform outputs cleanly**: the digest list travels inside the artifact (what AC2 says); do not build an outputs scheme.
- **`gh` on the runner needs a token even to upload**: it is given to the `upload` job's upload step only (`env: GH_TOKEN`), never to `build`.
- **The macOS app path or architecture directory differs** (`mac-arm64` vs `mac`): read it from the build output rather than assuming; fail clearly if no `.app` is found.
- **Windows start check**: a GUI process started from a runner shell; if it exits at once with a dialog nobody can see, capture the exit code and the app's stderr before judging.
- **A `-rc.N` tag's version in file names**: the builder writes the full version (`Goldfinch-Setup-0.19.15-rc.1.exe`); the expected-name computation uses the tag's version verbatim.
- **The deb's architecture or name template** differs from the default when `artifactName` is set: the published name `goldfinch_<v>_amd64.deb` is the requirement.
- **`upload-artifact` rejects a file name or flattens paths**: upload from one directory holding only the files to publish.
- **A manual dispatch now leaves real installers as one-day artifacts on the run.** That is a side effect worth knowing — a Windows or macOS build can be had for a hands-on check without publishing anything — and leg `release-integrity` decides whether `docs/RELEASING.md`'s release-candidate guidance should say so. This leg corrects only the statements it makes false: the dispatch paragraph ("no artifact upload … yields no installer") and the job list.
- **Anything needing a design call** (shape (b), a non-blocking start check): say so in the report; the Flight Director decides.
