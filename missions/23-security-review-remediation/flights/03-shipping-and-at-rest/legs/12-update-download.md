# Leg: update-download

**Status**: completed
**Flight**: [Shipping and At-Rest](../flight.md)

> Added during leg `hat-and-alignment`. The operator, on the installed candidate: "it occurs to me there is nothing actionable in the UI..there is no \"Update now\", what is the expectation from the user?" and then, choosing among three options the Flight Director laid out: "A download now button would be ideal in the settings page, the link in the kabab menu can continue to work as it does". Classified by the Flight Director as a **feature** (new behaviour), so it is a designed leg with a design review, not an inline walk fix.

## Objective

When a newer release exists, Settings → About offers a "Download now" button that starts an ordinary browser download of the right installer for this machine — the address built by the app, the file left for the operator to run — and says plainly what to do next.

## Context

- Flight DD1 said the app "never downloads or installs anything". The operator has now narrowed that: nothing is downloaded **unless the operator asks**, and nothing is ever installed by the app. The mission criterion's wording — "nothing is downloaded or installed automatically" — still holds as written. DD1's text is annotated, not rewritten.
- **The kebab item is unchanged** (operator): it keeps opening the release page. Nothing in `overlay-menus.js`, the chrome, or `renderer.js` (1,504 of 1,505 lines) changes.
- **What is believed stays exactly what it was**: the only network-derived value is the validated stable version in main's update state. The download address is `https://github.com/<slug>/releases/download/v<version>/<installer name>`, built in main from that version, the slug constant, and the fixed installer names — the same five names the release workflow asserts and the README links (`scripts/update-readme.mjs`; `expected_names` in `.github/workflows/build.yml`; `test/unit/artifact-names.test.js`).
- **Which installer** (decided here; the pure function is the single place):
  - `win32` → `Goldfinch-Setup-<v>.exe`
  - `darwin` + `arm64` → `Goldfinch-<v>-arm64.dmg`
  - `linux` + `x64` → `Goldfinch-<v>.AppImage` when the app is running from an AppImage (the `APPIMAGE` environment variable is set — `register-settings-ipc.js`'s relaunch path already relies on it), otherwise `goldfinch_<v>_amd64.deb`
  - anything else (an Intel Mac, Linux on another architecture) → **no direct download**: the button is absent and the release-page control is the only one.
- **Existing code** (read at leg design; the design review verifies each):
  - `src/main/register-download-ipc.js` — a `will-download` listener per session sets the save path (`item.setSavePath(…)` into `getDownloadsPath()`, name through `sanitizeFilename` / `uniquePath`), records the download and feeds the indicator and the downloads page; `ses.downloadURL(plan.url)` is how Retry starts a main-initiated download, and the media path uses `downloader.downloadURL(url)`. A normal download raises **no native dialog** (the `dialog.showSaveDialog` calls in `main.js` belong to other features) — to be confirmed, because a native dialog would be unobservable to automation and would change the design.
  - Records carry the partition of the session that downloaded; "absent for the browser's own session", and such a record is not retryable (CLAUDE.md, *Downloads*).
  - The update state and its channels: `src/main/update-check.js` (`getState()` → `{ current, available, releaseUrl, checkEnabled }`), `src/main/register-update-ipc.js` (`update:get-state`, `update:open-release-page`, `internal-update-open-release-page`), both preloads, `src/shared/update-notice-model.js`, the About controller in `src/renderer/pages/settings.js`.
- **Through which session the download goes** — a decision for the design review to confirm or overturn with evidence: the browser's own default session (`session.defaultSession`), not a jar. Reasons: the operator's github.com cookies (which live in a jar, if anywhere) are not sent, so the download does not identify them beyond their network address — consistent with the update check; and no page context is involved. Cost: the record has no partition, so the downloads page offers no Retry for it — the operator presses "Download now" again. If the default session turns out not to carry the download handler, or its downloads do not appear in the indicator and the downloads page, the fallback is the default jar's session, with the cookie consequence stated in the docs.
- **The app does not verify the file.** It arrives from GitHub over HTTPS at an address the app built; the README's digest and attestation commands are how a downloader checks it. In-app verification is out of scope and recorded as a possible follow-up.
- Contracts (flight DD9) extended, additively: state gains `downloadName: string | null` (the installer file name for this machine and the available version, or `null` when there is no direct download or nothing is available); the bridge gains `updateDownload()` on `window.goldfinchInternal` only; element ids gain `about-update-download` and `about-update-hint`. Existing ids, fields and methods keep their meaning.

## Design review amendments — these override the text elsewhere in this leg wherever they differ

Developer design review 2026-11-17: **approve with changes**. Settled by reading, with the call sites:

- **The default session is wired for downloads** — `app-lifecycle.js` calls `wireDownloadHandler(getDefaultSession())`; the internal session deliberately gets no download handler (`session-runtime.js` returns early for it), so the Settings tab's own `webContents.downloadURL` must **not** be used. A download with no page behind it is handled: `register-download-ipc.js`'s listener takes a null downloading-contents (no pending record), names the file from `item.getFilename()` through `uniquePath` / `sanitizeFilename`, records it with no partition, and reports through `broadcastToChromeAndInternal` (every chrome and every internal page — no owning tab needed). `downloads-store.js` `validateRecord` accepts a record with no partition. **No native dialog**: the handler always sets the save path; `main.js`'s two `showSaveDialog` sites are vault-bundle export only. The default session holds no site cookies (no tab lives in it). Shields and the navigation guards do not touch a `downloadURL` request.
- **AC3 — where the call lives.** `test/unit/register-download-ipc.test.js` source-scans `register-download-ipc.js` and allows only its two existing `.downloadURL(` callers. The new call therefore goes in a small wrapper wired in `main.js` and **injected** into `registerUpdateIpc` as `startUpdateDownload(url)` (a `try` / `catch` around `session.defaultSession.downloadURL`, returning `false` on a throw → the "Could not start" hint). That pin is not edited.
- **AC3 — "already in progress", defined.** `registerUpdateIpc` also receives `getDownloadsManager`. A download counts as in progress when a record with exactly the built address has no end time (`endTime == null`; states `progressing` and paused). Because the record only appears at `will-download`, the handler also keeps a short latch from the moment it calls the wrapper until a matching record appears or ten seconds pass. Unit-tested with a fake manager and an injected clock: latch hit; record hit; latch expiry; a finished record does not block. **Accepted gap, stated**: the real two-click path is not exercised live (the address is github.com and the dead proxy fails it at once) — unit tests only.
- **AC2 — computed, not stored.** `downloadName` is computed inside `getState()` from `available` and injected `platform` / `arch` / `appImage` facts (defaulting to `process.platform`, `process.arch`, and `process.env.APPIMAGE` read at construction — `default-browser.js` and `relaunch-options.js` already use that variable as the AppImage signal). Nothing is stored, so it cannot drift from `available`. Emulation, accepted and documented: an x64 build under Rosetta reports `darwin` / `x64` → no button; Windows on ARM gets the x64 installer.
- **AC1 — the address never comes from the response or the dev override.** Built from the constant slug and the re-validated version only — not from `releaseUrl`, and never from `GOLDFINCH_UPDATE_CHECK_URL`. In an unpackaged build with the override the button still builds a github.com address (kept, deliberately): **the dead proxy is then the only thing stopping a real fetch**, so the smoke's first step proves the proxy is dead and aborts otherwise. A unit test asserts the override cannot influence `installerUrlFor`.
- **AC4 — the file name is Chromium's.** The saved name is what Chromium derives after the redirect (`Content-Disposition`, else the address), cleaned by the existing sanitiser — normally the asset's own name, but not forced. The existing pending-record mechanism keys on a tab and cannot carry a name here; it is **not** extended (AC7 protects that path). AC4 reads "under the name Chromium derives, as for any download".
- **AC5 — markup facts.** Primary is plain `.settings-btn`; secondary is `.settings-btn--secondary` — "View release notes" gains the secondary class. The controller's early-return (`if (!statusEl || !btn || !check) return`) must not gain the new elements: fetch them separately and tolerate their absence. The focus rescue extends to the download button. `test/unit/update-notice-model.test.js` pins `openLabel: 'View release notes'` and its aria label — kept; the table is extended. One more unit case: a state push between render and click — the handler downloads what main's state says at the click, and the returned `name` is what the hint shows.
- **AC6 — the sweep is wider.** Patterns: `Nothing is downloaded`, `nothing is downloaded`, `never download`, `notify-only`, `Notify-only`, `no in-app download`. Known hits to correct: `settings.html` (the note), `src/main/update-check.js` header comment, `docs/updates.md`, `README.md` ("Updates are never automatic…" — check it stays true and says what the button does), CLAUDE.md's *Update check* entry, `release-notes-draft.md`. To **annotate, not rewrite**: flight DD1, and `mission.md`'s planning decision "no in-app download or install" — add beneath it a dated line: "Narrowed by operator ruling 2026-11-17 (Flight 3 acceptance walk): a download the operator asks for is allowed — 'A download now button would be ideal in the settings page'. Still nothing automatic, and nothing is installed by the app." Legs 05 and 06 are historical and left alone. CLAUDE.md's channel-table row count is set to **210** from whatever it says now.
- **AC8 — measured first, and fenced.** Step 0: with `HOME` and `XDG_CONFIG_HOME` in scratch, **no** `user-dirs.dirs` in the scratch config home and `XDG_DOWNLOAD_DIR` unset, read `app.getPath('downloads')` (through the downloads page or an admin read that reports it; if no existing surface reports it, add nothing to the product — start one page-initiated loopback download first and read its record's save path) and **abort unless it is under the scratch root**. Step 1: prove the proxy is dead (a tab to `http://example.invalid/` ends in a load failure). Step 2: a probe — does a download that cannot connect produce a `will-download` and a record at all, and what is its final state called (Electron's states are `progressing`, `completed`, `cancelled`, `interrupted` — "failed" is not one)? If no record is produced, AC8 and AC9 assert instead what **is** observable and say so (`[BLOCKED:no-record]` only if nothing is). List the scratch downloads directory before and after (does a partial file remain?). The unfinished sentence in AC8 reads: "a second click after the first has ended starts a second download and a second record; the in-progress repeat is covered by unit test only."
- **Retry note.** A record with no partition shows the existing note "Cannot retry: this download does not record which identity it came from." — true but oddly worded for an app-started download. Left as it is; recorded in the log as a candidate squawk.
- **Automation reach, stated.** An admin key that evaluates script in the Settings page can press the button, which writes one fixed, app-chosen file into the downloads folder. No secret, key or caller-chosen path is involved, so no reveal-gate call; `docs/mcp-automation.md`'s tier section gains one line saying so.
- **In-app verification of the file** is not in scope; the docs point at the README's commands.

Flight Director answers to the review's three questions: Chromium's name is accepted; the dev build keeps building the github.com address, fenced by the proxy check; `mission.md`'s planning line is annotated with the operator's ruling.

## Edge Cases

- **A normal download does raise a native dialog on some path**: stop — `[BLOCKED:download-dialog]`.
- **The default session's downloads do not show in the indicator or the downloads page**: use the fallback named in Context and say so; do not build a second downloads path.
- **The version changes between render and click** (a new check lands): main downloads what its state says at the click; the returned `name` is what the hint shows.
- **The setting is turned off mid-download**: the notice and buttons go away; the download, already an ordinary one, continues and stays in Downloads.
- **Windows and macOS**: the choice function is unit-tested; the real download on Windows is the operator's check on the next candidate.
- **A release that lacks the expected asset** (a 404): the download fails like any other; nothing special.
- **`renderer.js` would need a line**: it must not — this leg has no chrome change. `[BLOCKED:renderer-budget]` if you find otherwise.
- **Anything needing a design call**: `[BLOCKED:<reason>]`.
