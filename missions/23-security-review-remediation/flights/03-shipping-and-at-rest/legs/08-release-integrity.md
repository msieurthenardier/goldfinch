# Leg: release-integrity

**Status**: completed
**Flight**: [Shipping and At-Rest](../flight.md)

> Developer design review 2026-11-17: **approve with changes**, incorporated — the existing invariant test pins `upload`'s permissions exactly and must be rewritten, not extended; this host's `gh` (2.45.0) has neither `gh attestation` nor `gh release verify`, so the flags come from the published manual and the documented commands are first run at the acceptance walk; immutable releases do have a REST endpoint; only the verified installers are attested, after the upload; the stable-tag check proves "reachable from `main`" and is exercised for real only by a tag push; the release sequence was run in a scratch clone and the exact commands recorded; the ruleset body and the admin role id come from the REST reference and this repository's own branch ruleset.

## Objective

A published installer can be traced to the workflow run and commit that built it, a stable release can only come from history that is on `main`, a published release cannot be altered, and the documentation tells an operator and a downloader how to check each of those.

## Context

- Flight DD3 (mission findings 7 and 19: unsigned, unattested artifacts; release tags unprotected). Operator decision at mission planning: no code-signing certificates — checksums, provenance, protected tags, immutable releases. Built on leg `release-build-split`'s topology: `create-release` → `build` (read-only, no token) → `upload` (no project code) → `publish-release`.
- **Checksums already exist.** GitHub computes a SHA-256 digest for every release asset (`gh api repos/msieurthenardier/goldfinch/releases/latest -q '.assets[] | "\(.name) \(.digest)"'` — one per asset on v0.19.15). No checksum file is published; the docs point at the digest.
- **What GitHub's documentation says** (read 2026-11-17 from docs.github.com and the action READMEs; quoted in the flight log):
  - *Attestations*: available to public repositories on every plan; the attesting job needs `id-token: write` and `attestations: write` (and `contents: read`); `actions/attest-build-provenance` v4 is a wrapper over `actions/attest`, which new work should use; `subject-path` takes globs or a list; verification is `gh attestation verify <file> -R <owner>/<repo>`. The flag that pins the signer workflow was **not** in the pages read — to be read from `gh attestation verify --help` at implementation.
  - *Immutable releases*: enabled in repository Settings → Releases ("Enable release immutability"); applies to releases published **after** it is enabled; the recommended flow is exactly this workflow's (create a draft, attach every asset, then publish); after publishing, assets and the tag are locked — "Git tags cannot be moved" and cannot be deleted while the release exists; a release can be deleted, and then the tag can be deleted **but its name cannot be reused**; the title, the notes, and the prerelease / latest flags stay editable; publishing an immutable release creates a **release attestation**, checked with `gh release verify <tag>` and `gh release verify-asset <tag> <file>`. **Not stated**: whether prereleases are covered, whether a draft is locked in any way, a REST endpoint to enable it.
  - *Tag rulesets*: "Restrict creations", "Restrict updates" and "Restrict deletions" exist for tags, with a bypass list that can name the repository-administrator role. **Not stated**: whether restricted creation stops the workflow's token from creating a *release* for a tag that already exists.
- **Consequences for the existing flow** (`docs/RELEASING.md`):
  - The rollback recipe in CLAUDE.md and the clean-up recipe for release-candidate builds (`gh release delete vX.Y.Z --yes --cleanup-tag`, "fix, re-tag") stop being true: a deleted immutable release's tag name is spent. Rollback becomes "publish the next patch version"; a candidate number is used once.
  - Since leg `release-build-split`, a manual dispatch leaves real installers as one-day artifacts on the run. A hands-on Windows or macOS check no longer needs a public prerelease at all; a prerelease is needed only when the published path itself is under test.
- **How releases are really cut** (repository history, read at leg design): the last four stable tags all point at commits that are on `main` (`gh api …/compare/main...v0.19.15` → `identical`), and the version bumps arrived by pull request (`release-prep: bump to 0.19.15 (#290)`) — while `docs/RELEASING.md` still describes `npm version` followed by `git push --follow-tags` straight to `main`, which the `main` ruleset ("changes must be made through a pull request") does not allow. **Operator, 2026-11-17: "we cut a release by updating it then tagging it after merge to main."** So the sequence the doc must describe is: bump the version on a branch (the `version` hook regenerates the README links in the same change), open a pull request, merge it, then tag the **merged commit on `main`** and push the tag. The tag never exists before its commit is on `main`, which is exactly what the stable-tag check enforces — and the compare call needs no race allowance beyond one retry. The Developer confirms, in a scratch clone and without pushing anything, the exact commands that produce the bump commit without creating a tag (`npm version <level> --no-git-tag-version` still runs the `preversion` and `version` hooks — verify, do not assume) and writes those into the doc.
- The app's update notice believes a stable tag from GitHub's `releases/latest`. That makes "a stable release can only come from `main`" a property the notice depends on, not only a release nicety.
- **No crew member changes a repository setting, pushes a tag, or publishes a release.** The leg supplies exact commands; the operator runs them.

## Acceptance Criteria

- [ ] **AC1 — Provenance in the upload job.** A step using `actions/attest` (the action its own and `attest-build-provenance`'s READMEs name for new work; v4.2.2 on 2026-11-17 — re-resolve the tag's commit SHA from the action's repository on the day) placed **after** *Upload to the draft release* and before the job ends, so an attestation exists only for files that are in the draft, and a failed attestation still stops `publish-release` (it needs `upload` to succeed). **Subjects are exactly the verified installers**: *Verify names and digests* exports the verified paths (a step output or a file built from its own verified list) and the attest step's `subject-path` is that list — never a glob that could take in `VERSION` or `SHA256SUMS`, and never a bare `artifacts/*/*` (asserted by the invariant test). The job's permissions become `contents: write`, `id-token: write`, `attestations: write`. The action's README also lists `artifact-metadata: write` "to create the artifact storage record", which it ties to registry pushes; it is **left out**, and the permission set is provisional until the acceptance candidate's run — if the step fails for want of it, adding it is a one-line follow-up recorded in the walk. `build` stays `contents: read` with no token. The step runs on tag builds only. A manual dispatch attests nothing, by decision: a provenance attestation for a branch build would make an unreleased installer pass a plain `gh attestation verify`, which is the opposite of what a downloader should be able to rely on — so this step's first real run is the candidate. The invariant test's assertion `deepEqual(jobPermissions(jobs.upload), ['contents: write'])` is **rewritten** to the new exact set; added: `id-token` and `attestations` appear in `upload` and in no other job; no attest step in `build`; the attest step sits after the upload step and is tag-gated. The action is a `uses:` step on the runner's own Node — the test's "no `node` / `npm` / `npx` run line" rule also scans `with:` inputs, so no input may contain those words. The action reads the job's token by default; that is the same `contents: write` job and is stated beside "the token is given to one step" in the workflow's comment, which is corrected to say what is now true.
- [ ] **AC2 — A stable tag must be on `main`.** In `create-release`, after the semver validation and before the draft exists: when the tag is stable, ask GitHub's compare endpoint whether the tagged commit is contained in the default branch (`repos/{repo}/compare/{default}...{sha}` with `{sha}` from `GITHUB_SHA` and `{default}` from `github.event.repository.default_branch`, both passed through `env:` — never `${{ }}` inside the `run:` block). `identical` or `behind` allows; `ahead`, `diverged`, a 404, any error, and an empty or unparseable answer refuse. One retry after about ten seconds for anything but a 403; the step prints the status it saw and the commit on every path. Measured read-only at design review: `main...v0.19.15` → `identical`; `main...v0.19.0` → `behind`; `main...flight/03-shipping-and-at-rest` → `ahead`; a ref that does not exist → HTTP 404. **What it proves is "reachable from the default branch"** — not "is its head" and not "passed checks"; the docs say exactly that. The step sits after *Validate semver tag and classify stability* and leaves that step's `semver=` line byte-identical (`update-version.test.js` reads it). A prerelease tag skips the check, and stability is decided from the tag string by the existing classification — a name cannot claim the exemption while looking stable. The check needs no checkout. The decision is one small shell function; a unit test extracts it from the workflow and runs it against canned compare answers (`identical`, `behind`, `ahead`, `diverged`, an error body) for a stable and a prerelease tag.
- [ ] **AC3 — The check is shown working as far as it can be without a tag push.** The same function is run locally against the live endpoint for real commits (read-only requests): the commit of `v0.19.15` → allowed; the flight branch's head → refused; a made-up SHA → refused. Quoted in the log. **This is a substitute for the real trigger and the leg says so**: the tag-push path — `GITHUB_SHA` for an annotated tag, the job token's right to call compare, the default-branch value — runs for the first time at the acceptance walk, where a stable-looking tag on a commit that is not on `main` is pushed to watch `create-release` refuse (no release is created, so nothing is spent; the operator deletes the tag) and the real release tag later passes. A prerelease candidate cannot exercise the check at all, since prereleases skip it. Both are listed for leg `hat-and-alignment`.
- [ ] **AC4 — Verify-your-download, for people who download.** `README.md` gains a short section **outside** the generated download block (or `scripts/update-readme.mjs`'s template is extended — whichever keeps `npm version` from wiping it; `update-readme.test.js` covers the choice): how to see an asset's SHA-256 on the release page and compare it (`sha256sum` / `Get-FileHash` / `shasum -a 256`), and `gh attestation verify <file> -R msieurthenardier/goldfinch --signer-workflow msieurthenardier/goldfinch/.github/workflows/build.yml` (flags from the published `gh` manual, read 2026-11-17: `-R/--repo`, `--signer-workflow`, `--source-ref`, `--source-digest`, `--deny-self-hosted-runners`, `-b/--bundle`); plus `gh release verify <tag>` / `gh release verify-asset <tag> <file>` once immutable releases are on. The development host's `gh` is 2.45.0 and has **none** of these commands, so nothing here has been run: the section says a recent GitHub CLI is needed (naming a minimum version only if the CLI's release notes are found to state one), offers no `gh`-free method unless a source for one is found and cited, and every command in it is run for the first time, exactly as written, at the acceptance walk. ## Edge Cases

- **The compare endpoint for a tag pushed seconds ago** returns 404 or `ahead`: one retry after a wait; then fail loudly — a failed release run is recoverable (push the tag again after the commit is on `main`), a stable release from unreviewed history is not.
- **`main` is renamed or the default branch changes**: the check names the repository's default branch from the event payload rather than the literal, if that is one line; otherwise the literal and a comment.
- **The attestation action's inputs changed in the current major**: follow its README; never guess an input name.
- **A release created before immutability was enabled** stays mutable: the docs say which release is the first immutable one once known.
- **`npm version` regenerates the README block**: the verify section must survive it — proven by running `node scripts/update-readme.mjs` in the test or by hand and diffing.
- **Anything needing a design call**: `[BLOCKED:<reason>]`.
