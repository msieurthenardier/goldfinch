# Leg: admin-key-name

**Status**: completed
**Flight**: [Vault and Automation Boundary](../flight.md)

## Objective

Make the launch flag the only door to the admin tier: a settings call can no longer write an automation key hash, and a key-map entry named `admin` — or any other reserved identity name — is never treated as an identity.

## Context

- Flight DD3 and the settings bullet of DD2. Mission finding 11 (and 5d). Split from `admin-reach` at that leg's design review: it does not depend on the confirmation dialog.
- **The defect.** `validateKey` (`src/main/automation/automation-auth.js`) checks the real admin hash only when the launch flag is set, then walks the jar map and returns the matching map key verbatim. `mcp-server.js` treats the identity string `'admin'` as the admin tier. So a hash stored under the map key `admin` authenticates as admin with no launch flag. The map can be written by `internal-settings-set`, which accepts any key and any value the store's validator admits — and that validator checks the map's values only.
- **Who can plant it today**: script in an internal page, which means the admin tier itself (a jar key cannot reach internal pages). So this is persistence past the flag — admin once, admin on every later launch without it — and a stored-data defect for anyone who can write the settings document. It is not a route from a jar key to admin.
- **Already safe** (design review of the flight, verified against `src/main/jars.js`): no jar can have the id `admin` — `isReservedId` includes it, a jar named "Admin" gets `jar-admin`, a stored `admin` id is remapped on load. `mintJarKey('admin', …)` refuses today only because the caller passes a jar list.
- The settings store's rules (CLAUDE.md → *Settings store*): `load()` never throws; per-key validation against `DEFAULTS`; **any load path whose resolved config differs from the on-disk bytes persists it**; `set()` validates before mutating and throws on bad input. Design review of `admin-reach` found: an invalid `automationKeyHashes` falls back to `DEFAULTS` — the whole map, every jar's key — and the normalizers run only after the validator passes and cannot signal a persist. `test/unit/settings-store.test.js` pins "one bad value rejects the whole map"; that stays true for non-hex values.
- **Other reserved names** (design review): `src/main/jars.js` reserves `burner`, `burner-*`, `admin`, `internal`, `default` and the global id. A map entry named `global` would authenticate as the identity `global`, which the vault context aliases to the manager-wide vault; the others would yield an identity every operation refuses. None corresponds to a jar that can hold a key. This leg treats the **whole reserved set** the way it treats `admin`, through one shared predicate, so the store, `validateKey`, minting and the chrome's key state cannot drift apart.
- Leg `admin-reach` (flown first) put a confirmation in front of minting. This leg is independent of it and touches none of its files except `register-settings-ipc.js`.

- Legs `electron-45` and `admin-reach` landed (uncommitted in the tree).
- `src/main/automation/automation-auth.js` `validateKey`; `src/main/automation/mcp-server.js` `mintJarKey`, `mintAdminKey`, `revokeJarKey`, `revokeAdminKey`, and the dev-mint path; `src/main/settings-store.js` (`VALIDATORS.automationKeyHashes`, `NORMALIZERS`, `repairConfig` / `parseAndRepair`, `set`); `src/main/register-settings-ipc.js` `internal-settings-set`; `src/main/settings-chrome-view.js` (derives the chrome's key state from the map's keys).

## Acceptance Criteria

- [ ] **AC1 — Pre-change record (two launches).** Before any source change, on a scratch profile: launch **with** the admin flag, attach as admin, and through an admin `evaluate` on an internal page call the settings bridge to store a key-hash map containing an entry named `admin` whose value is the hash of a key generated by the script; quit. Launch 1 is `npm run dev:automation` with dev-mint and the admin flag (to get an admin key). Launch 2 is `npm run dev:automation` with **neither** `GOLDFINCH_AUTOMATION_ADMIN` nor `GOLDFINCH_AUTOMATION_DEV_MINT` — the dev flag binds the surface by itself, nothing is re-minted, and the planted key is the only new credential. Attach with that key and record exactly what identity it gets: whether the admin-only `getChromeTarget` answers (`scope.js` hands the full engine to `'admin'` alone), with a negative control in the same launch — an ordinary jar key minted in launch 1 is refused for it. Repeat the plant with an entry named `global` and record what that identity can reach (state only what was observed). Output saved in the scratchpad and summarised in the flight log. If the second attach is refused for a reason other than the key (automation not enabled without the flag, say), record that precisely: it changes how reachable the defect is and the flight log must say so.
- [ ] **AC2 — `validateKey` never returns a reserved identity from the jar map.** The jar loop skips any map entry whose key the shared reserved-name predicate rejects (own keys only). A presented key whose hash is stored under `admin`, `global`, `internal`, `default`, `burner` or a `burner-…` name returns `null`. The real admin path is unchanged. The function still never throws. The comment "a jar key never resolves to 'admin'" is now true.
- [ ] **AC3 — `mintJarKey` refuses every reserved name and every non-own-key name**, with or without a `jars` accessor, before a key is generated or anything is written. `__proto__` and `constructor` are refused too (assigning `hashes['__proto__']` on a plain object sets the prototype, not an entry). `revokeJarKey` still removes a stale reserved entry if one exists (it is the cleanup path).
- [ ] **AC4 — The store drops reserved entries, per entry, and persists the repair once.** On `load()`, a stored `automationKeyHashes` that is otherwise valid but has a reserved-name entry loads with that entry removed and every other entry intact, and the repaired document is written back exactly once (a second load writes nothing — tested with a write-counting document store). **Mechanism (decided):** a pre-validation strip inside `repairConfig`, for this key only, that copies the map without reserved own keys and reports "changed"; that flag is OR-ed into `needsPersist` alongside the migration flag (today `needsPersist` comes from `migrateStored` alone, and normalizers run after validation and cannot signal a persist). The stripped map is then validated as today. A comparison of resolved config against the stored bytes was considered and not chosen — it would also fire on unrelated repairs. The legacy-JSON import path must reach the same strip; verify and test it. A map with a non-hex value is still rejected whole, as pinned today. Entries for jars that no longer exist are kept (the store does not know the jar list).
- [ ] **AC5 — `set()` rejects a reserved entry.** The shared validator gains the reserved-name check, so `settings.set('automationKeyHashes', map)` with such a key throws like any other invalid value and leaves the prior value untouched. Because `load` and `set` share that validator, the strip in AC4 must run **before** it on the load path — otherwise a stored `admin` entry would reset every jar's key. Pinned: `set` with `admin` throws; `load` with `admin` plus a valid entry keeps the valid entry; `load` with `admin` plus a non-hex value still falls back to the empty map.
- [ ] **AC6 — `internal-settings-set` refuses both hash keys for every caller.** `automationKeyHashes` and `automationAdminKeyHash` reject the invoke with a fixed message naming the key; nothing is written and no `settings-changed` is broadcast. The refusal is in the handler, before `settings.set`. Minting, revoking and the dev-mint path write through the store directly and still work (unit: each).
- [ ] **AC7 — Nothing else that reads the map's keys trusts `admin`.** Every consumer of `automationKeyHashes` keys is listed in the flight log with a one-line judgement — at design time: `validateKey`, `mcp-server.js` identity resolution, `register-settings-ipc.js` `automation:list-keys` (iterates jars, not the map), `settings-chrome-view.js` (`jarIdsWithKey`), `mintJarKey` / `revokeJarKey`, jar deletion's key revocation. `jarIdsWithKey` must not report a reserved name (filter with the shared predicate, as defence in depth). Consumers that only read the string `validateKey` returns (`audit-log.js`, `vault-context.js`, `scope.js`, the server's identity branches) are safe once it never returns a reserved name from the map — list them with that judgement.
- [ ] **AC7b — One predicate.** The reserved-name check used by the store's strip and validator, `validateKey`, `mintJarKey` and `settings-chrome-view.js` is one exported function (in or beside `src/main/reserved-ids.js`; `jars.js` `isReservedId` either becomes it or is drift-guarded against it by a unit test). It must stay Electron-free and importable by `settings-store.js` without a cycle.
- [ ] **AC8 — Live.** On the changed build, AC1's two-launch recipe ends differently at each step it can: the settings call is refused; and with an `admin` entry and a `global` entry planted beside a real jar's entry in a scratch profile's stored settings before launch, the app loads, the entry is gone from the stored document after boot, the real jar key still authenticates, and each planted key is refused at `initialize`. The plant is a Node 22 script that opens the scratch profile's `app.db` with `app-db.js` and writes the raw `settings` document row (`node:sqlite` loads under system Node with an experimental warning) — it cannot use `settings.set`, which now refuses the entry.
- [ ] **AC9 — Spec.** `tests/behavior/admin-reach-refusal.md` gains (or keeps, renumbered) its step for the settings write of a key-hash map being refused, with its Expected Result stating the refusal message and unchanged key state.
- [ ] **AC10 — Docs.** `docs/mcp-automation.md` states how the admin tier is obtained (launch flag + minted key + automation on) and that neither a settings write nor a stored entry can stand in for the flag. `CLAUDE.md` → *Internal-bridge security model*: `internal-settings-set` does not write key hashes; mint and revoke are the only writers.
- [ ] **AC11 — Gates.** `npm test`, `npm run typecheck`, `npm run lint`, `npm run format:check` pass.

## Edge Cases

- **A map key that only looks reserved** (`Admin`, `admin `): not special-cased — identity strings are compared exactly. `__proto__` / `constructor`: the map is iterated by own keys everywhere, and tests pin that neither can make `validateKey` return anything but `null`.
- **The real admin key's hash also stored under `admin` in the map**: the real path still authenticates it as admin when the flag is set; without the flag it authenticates as nothing.
- **A profile that already holds a reserved entry** (possible only if someone exploited this): the entry is dropped silently at load. No operator notice is added — recorded in the flight log as a decision, since the entry never corresponded to a jar.
- **Settings `set` of the whole map by mint during a boot repair**: the store is synchronous; no interleaving.
- **Anything needing a design call**: stop and report `[BLOCKED:<reason>]`.
