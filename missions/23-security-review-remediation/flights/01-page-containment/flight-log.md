**Design points.**
1. **Views are derived from the model's entries, not from a mode field.** Warning view: `[{ action: 'certificate-continue' }]`. Confirmation view: `[{ action: 'confirm-summary', type, title, brand, last4, fullName }, { action: 'confirm-fill' }, { action: 'confirm-cancel' }]`. The only extra top-level payload field is `destination`. (The leg's design-decision 2 mentioned view mode and the certificate flag as payload fields; its acceptance criteria say the view is derived from the entries and only the destination travels. The AC governs.)
2. **Cancel** is rendered in the template as an action with its own id, but the sheet's row listener turns that id into a dismissal (`report.lastStimulus = 'escape'`; `menuController.close`) before the gated sender is reached, so it is never delayed and main's dismissal consumer drops the context. 3. **Pending is one slot per context** (`{ vaultId, itemId }`); every non-matching call overwrites it. `fillGenerated` is not subject to the confirmation (a generated password is not a stored item).
4. **The acknowledge handler** looks the context up with the origin check but without the certificate clause; a changed origin, a stale id or another tab gives `{ ok: false }`. A new gesture mints a new, unacknowledged context.
5. **`recordConfirmedOrigin` refuses silently** (returns `{ recorded: false }`) for a login, an unknown item, an uncreated vault or an empty origin, and throws for a burner / unknown jar target and for a locked store (the caller traces the failure as `confirmed-origin-record-failed` with the error name only).
