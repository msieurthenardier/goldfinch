## Flight Director Notes

### Planning session — 2026-07-30

**Storage shape taken to the operator rather than decided.** Three candidates were put up with their export and corruption consequences made explicit: per-jar document rows, a single document with a `jarId` per entry, and a real SQLite table. The operator chose the table. This overrode the Flight Director's own recommendation (per-jar document rows, chosen for minimum disruption to Flight 1's just-built pattern) — recorded here so the debrief can evaluate the call on outcome rather than on who made it.

**One consequence of that choice was not raised until after it was made, and is now DD4.** Under the document store, corrupting the bookmarks payload repaired *only* bookmarks — verified in Flight 1's `bookmarks-bar` checkpoint 12 against real byte corruption. Under a table there is no independently corruptible per-store payload: `app.db` quarantine is file-wide and takes settings, jars, shields, downloads, session, and cookie bookkeeping with it. This is a pre-existing property of `app.db` (M10 F1 DD2), not something this flight introduces, but bookmarks are now inside that blast radius and were not before. It also invalidates a currently-passing behavior-test checkpoint. Both facts are written into DD4 and the Verification table rather than left for leg 1 to discover.

**A destructive-path trap was caught at planning.** The obvious place to hang jar teardown is `wipeJarData` — it already purges history and cookie bookkeeping, and both `jars-remove` and the identity wipe route through it. But those two callers mean different things: `jar-registry-ipc.js:105` is destroying the jar, while `jar-data-ipc.js:137` (`handleWipe`) keeps it. Putting bookmarks in the shared helper would have made the identity wipe silently destroy them, directly contradicting the operator's clear-data ruling. DD9 attaches deletion to the delete call site instead, and asks for both assertions to live in one test file so the distinction stays visible.

**The re-derive trigger set is smaller than first stated.** Before the mission amendment was written, the Flight Director told the operator the new trigger would be "the active tab's jar changed, which mostly coincides with tab switch but not always." Code interrogation showed it coincides *always*: a tab's jar is fixed at creation, and `move-targets.js` moves tabs between windows only. DD7 records the narrower, verified claim, with the five sync paths tabulated by class — navigation paths do not touch the bar. Correcting this here so leg 2 is not designed against the looser statement.

**`findByUrl`'s synchronicity is what forces DD6, not a preference for caching.** `refreshStar` reads it synchronously on all five paths and one of those paths is tab activation, so a single-jar cache would gate the star on an in-flight promise at the exact moment of a tab switch. The per-jar map is the cheapest shape that keeps every read synchronous. Recorded as a forced move so a future reviewer does not "simplify" it back.

**Per the debrief's enumerate-call-sites lesson**, DD7's table carries grep-verified locations rather than a remembered count, and leg 2 is instructed to re-confirm the count before implementing.

**Risk tiering (stated in advance; renumbered after design review added the extraction leg).** Leg 1 (`renderer-extraction`) is **low-risk** — behavior-neutral, single-surface, and an established pattern in this exact file (`bookmarks-client.js` and `bookmarks-bar.js` are both prior extractions from it) — so it proceeds without a per-leg design review; the flight-end review still covers it. Legs 2 and 3 are both **high-risk** and both take a design review: leg 2 for schema migration, shared-interface break, and a destructive-path change; leg 3 for cache/freshness behavior and because it deliberately reverses a shipped, behavior-tested assertion. Leg 4 is interactive (HAT) and takes the guided protocol, not the autonomous cycle.

### Design review — 2026-07-30

The Architect returned **approve with changes** and found five high-severity defects, all of which I re-verified against code before incorporating. Four were genuine holes in my spec, not stylistic notes:

1. **An unenumerated cross-jar *write*.** `renderer.js:1491-1492` issues `bookmarkUpdate` from `onTabFavicon` with no active-tab guard — unlike `onTabLoading` directly below it at `:1497`, which returns early for non-active tabs.
