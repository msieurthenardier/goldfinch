**Slug**: `admin-reach-refusal`
**Status**: active

All 15 checkpoints pass, including 5, 10–13, and the new steps 12 (the rename-spoof note, by-eye) and 13 (the open-download gate). Steps 6b and 12 were rerun once for the operator's by-eye read. Spec cadence fixes are logged as squawk 0222. [run log](admin-reach-refusal/runs/2026-11-19-00-25-54.md)

> Finalised at Mission 23 Flight 2 leg `admin-reach` (2026-11-14): bridge method names, refusal shapes, the trace line, the 60 s wait, the one-dialog-per-window rule and the scripted-document mark are the leg's own contracts (flight DD2 / DD9; `docs/mcp-automation.md` *What each tier can reach in an internal page*). The key-hash settings-write step of the draft landed at leg `admin-key-name` as step **1b** (inserted without renumbering; it raises no dialog and needs no wait).

## Intent

Verify on the running browser that script evaluated by an admin automation key inside a `goldfinch://` page cannot obtain a cookie value, mint an automation key, or export a vault without a person confirming in a native dialog that no automation tier can see or answer — the actions Mission 23 finding 5 showed it could. A live run cannot press the dialog, so what it shows is the other half: with nobody answering, every such call is refused with the agreed shape, nothing is written, the window stays responsive meanwhile, and the refusal survives the session that raised it (the scripted-document mark).

> **A native dialog will appear on the operator's screen during this run (steps 3, 6b, 7, 8, 10–13) and stays up for up to 60 s each. Do NOT click it, and do not try to drive it from the run — an answered dialog is a different test. Make sure no dialog is left open when the run ends (each one aborts itself at 60 s).**

## Preconditions

- Goldfinch running via `GOLDFINCH_REVEAL_GATE_TRACE=1 GOLDFINCH_AUTOMATION_DEV_MINT=1 GOLDFINCH_AUTOMATION_ADMIN=1 npm run dev:automation` on a **scratch profile** (`XDG_CONFIG_HOME` in a fresh temp directory); stdout captured to a file the Executor can read (the trace line `[reveal-gate] channel=<c> decision=<d> reason=<admin-attached|touched>` is the main-side observable). Admin key from the printed `AUTOMATION_DEV_MINT` line; client attached with `connectAutomation()` (`scripts/lib/mcp-client.mjs`). **Never** a registered MCP server. `callTool` requests that await a dialog need a request timeout above 60 s (the SDK default is 60 s): pass `{ timeout: 150000 }`.
- A fixture origin that sets one known cookie in a persistent jar **A** — any tiny local server answering every request with `Set-Cookie: probe=<marker>; Max-Age=3600; Path=/` and an HTML body (the `cross-jar-fetch` fixture also works). Use a marker string no other part of the page contains.
- **Non-vacuity (recorded 2026-11-14 on the pre-change tree, Electron 45.3.2, scratch profile)**: an admin `evaluate` on `goldfinch://jars` calling `window.goldfinchInternal.jarsCookiesValue(...)` for the fixture cookie returned `{"ok":true,"value":"SECRET-COOKIE-VALUE-4711"}`, and an admin `evaluate` on `goldfinch://automation` calling `window.goldfinchInternal.automationJarKeyMint('personal')` returned a minted key (`{"key":"<non-empty>"}`) — see the leg's flight-log entry. The same calls on the leg's tree are steps 3 and 7 below.
- **No vault is needed** for steps 1–4 and 6–9 and for step 13. **Steps 5 (export gate), 10, 11 and 12 need a vault the **operator** has unlocked** (step 12 needs at least two login items in different vaults, and step 11 an item with a one-time code); no agent types a master password. If the vault is locked, they are recorded **not run**, not as a pass (step 5's locked answer is NOT EXERCISED, never a pass). Step 13 needs a plain-text attachment fixture (one-line server described in the step) and a run-unique file name; it writes into the operator's real downloads folder and deletes by exact name.
- **Operator by-eye reads (steps 12 and 13):** the operator reads the two dialogs on their screen and states the wording in the conversation; the run never clicks a dialog.
- **Only the active tab of a window is ever asked (fix 1, leg `hat-and-alignment`).** `evaluate` does NOT activate a tab, and a gated call from a tab that is not its window's active tab is refused at once with trace `decision=gone` and no dialog; switching away from a tab with a dialog pending cancels it as `gone`. So every gated step below first makes its target tab active with `activateTab` (admin key; it accepts internal tabs — `tabs.js` `activateTab` runs `resolveContents` with the admin engine's `allowInternal`, then activates through the owning window's chrome; verified by reading `src/main/automation/tabs.js` / `engine.js` and `docs/mcp-automation.md`, not run). `activateTab` is not input (it is `executeJavaScript` on the chrome), so it does not trip the real-input cancel either. **Never click, type in or scroll the window by hand during a pending step** — real input cancels a pending confirmation after 400 ms (rule 3); automation's own injected input does not.
- **Apparatus (act)**: `evaluate` on internal tabs with the admin key. **Apparatus (observe)**: each call's own return value; the trace file; `enumerateWindows` / `readDom` as responsiveness probes; the automation key state read back from the automation page.
- **Unobservable, not asserted here (`[by-eye]`, HAT leg)**: the dialog itself (wording, Cancel first and default, that pressing the affirmative button releases the value, appearance on Windows / macOS) and a person's confirmed reveal, including a confirmed item's repeat reads needing no second dialog. **Also `[by-eye]` (operator-read, steps 12–13):** the reveal dialog's original-title question and changed-while-automation-was-active note after a rename (step 12), and the open-download dialog's question naming the file (step 13).

## Observables Required

- mcp (`enumerateWindows`, `enumerateTabs`, `openTab`, `evaluate`, `readDom`, `getChromeTarget`)
- shell (fixture server lifecycle; the app's stdout log with the trace lines)

## Out of Scope

- The dialog's wording, default button and that Cancel refuses; that a person's affirmative answer releases the value; that a confirmed item's repeat reads (and the editor's code widget polling) need no second dialog; the dialog's appearance on Windows and macOS — `[by-eye]`, HAT leg. **Steps 10–12 are the only live proof for reveal and the code read, and they need an operator-unlocked vault; with a locked vault neither has an unattended trigger-driven proof — the reveal gate's unit suites and the HAT walk carry it.**
- A stored `admin` / `global` entry planted in the settings document before launch, and the "planted key is refused at `initialize`" half of the key-name work: it needs the app stopped and a raw write to the scratch profile's `app.db`, so it is the leg `admin-key-name` live check (flight log), pinned by `settings-store.test.js` / `automation-auth.test.js`, not a step here.
- Jar-scoped keys, which cannot reach internal tabs at all — `internal-session-exclusion`.
- Vault fill by automation — `vault-gesture-trust` and the vault specs.
- A run with **no** admin session and an unmarked document (everyday use: no dialog, every call answers as before) — it has no automation trigger (any attached client that reaches an internal page is admin); it is pinned by the registrar unit suites and exercised by every ungated spec.
