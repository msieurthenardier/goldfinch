# Behavior Test: Third-party cookie isolation blocks unpartitioned cookies and keeps partitioned ones

**Slug**: `third-party-cookie-isolation`
**Status**: active
**Created**: 2026-10-05
**Last Run**: 2026-10-06-17-24-03 (pass, post-merge regression on `8fdbe89` with PR #244: 14/14 judged, step 9 struck, UA appendix pass; see runs/2026-10-06-17-24-03.md)

## Intent

This test checks the native third-party cookie isolation from sortie 02 in the running app, with Shields on.

- **Blocked:** unpartitioned third-party cookies are withheld from a cross-site iframe and from cross-site subresources, on the HTTP path and on the `document.cookie` path.
- **Kept:** CHIPS `Partitioned` cookies keep working inside their own top-level site and don't leak into another top-level site.
- **Unchanged:** first-party cookies.
- **Privacy panel:** the isolate count reflects only refused cookies.
- **Storage Access:** not asserted here (an apparatus limit; see Preconditions). It is covered by unit tests and the HAT.
- **Restart-to-apply:** the setting takes effect only after a restart, and the panel and `goldfinch://settings` tell the truth about it: what is in force versus configured, the restart-pending copy at the isolate row and the master switch, the browser-wide note for paused sites, and a guarded two-step **Restart now** driven through the REAL UI (sortie 02 Leg 02).

Unit tests can't cover this. The behavior lives in Chromium's network-service cookie policy, and only a live Chromium build with real cross-site HTTPS frames exercises it. The ground truth is the `Cookie` header the fixture server actually receives.

**Re-run on every Electron major bump** (sortie 02 DD10). An unknown feature name is silently ignored, so a bump can make isolation fail open with no other signal.

## Preconditions

- **Isolated profile (load-bearing).** Run every launch with `XDG_CONFIG_HOME={scratch}/xdg`, a fresh scratch directory created for this run. Electron derives `appData` from it on Linux, so the dev profile lands under the scratch dir. The operator's own dev profile, including their claude.ai sign-in, is never touched.
- **Fixture.** Run `node tests/behavior/fixtures/third-party-cookies/serve.mjs --port {fx} --log {log}`. It listens on all interfaces and serves three distinct sites on one port:
  - A = `https://127.0.0.1:{fx}`
  - B = `https://localhost:{fx}`
  - C = `https://127.0.0.2:{fx}`

  `{fx}` must differ from `{port}`. Every cookie the fixture sets carries `Max-Age=3600`.

  The JSONL log records `{ ts, host, path, search, cookieNames: [...], setCookieNames: [...] }` per request (`search` is the raw query string, e.g. `?report-only=1`, so the two `/b/frame` variants are distinguishable). It holds names only, never values. First run: `node tests/behavior/fixtures/third-party-cookies/gen-certs.mjs` (gitignored `certs/`, 7-day validity, needs `openssl`).
- **App launch** (ONCE; restarts are driven by the app itself, see Restart attestation):
  `XDG_CONFIG_HOME={scratch}/xdg GOLDFINCH_AUTOMATION_DEV_MINT=1 GOLDFINCH_AUTOMATION_ADMIN=1 GOLDFINCH_MCP_PORT={port} npm run dev:automation -- --insecure-tls-fixtures`
  - **Capture the `adminKey` once**, from the `AUTOMATION_DEV_MINT` line of this single launch. Restart now strips `GOLDFINCH_AUTOMATION_DEV_MINT` from the environment before relaunching, so the relaunched process does **not** re-mint and the **same** `adminKey` keeps authenticating (its hash persists in `app.db`). A relaunch that re-mints is a **fail**. The relaunched child's stdout and stderr go to `/dev/null` (it is reparented, not a child of the npm wrapper), so the **only** re-mint observable is the key: a re-mint replaces the single stored admin hash (`mintAdminKey`), so the old key would 401. PID, `ss` and same-key auth are the relaunch observables.
  - Record **this run's own** main PID at launch: the electron child of the launched wrapper. The isolated profile can coexist with an operator's dev instance, so never match any electron or goldfinch process by name. After each restart, **track the new PID** (the process listening on `{port}`: `ss -ltnp "sport = :{port}"`); under `dev:automation` the relaunched child is an orphan of the old npm wrapper, which is acceptable.
  - `appQuit()` is used **only for final teardown** (last step), never for a restart. Wait for the PID to exit before declaring teardown done.
  - This is an **admin** spec: the chrome privacy panel is read via `getChromeTarget`.
- **Jar.** All pages open in a persistent container jar (e.g. `personal`; pass its `jarId` to `openTab`), never Burner.
- **Shields at defaults.** All strategies on, `pausedSites: []`, so isolation is in force from the first launch.
- **Apparatus.**
  - Use an SDK admin MCP client on `127.0.0.1:{port}/mcp`. The `chrome-devtools` MCP doesn't qualify: it drives a different browser.
  - `evaluate` reaches the **top frame only**, so every iframe observable is relayed: B's frame `postMessage`s its report to the embedding page, which renders it into `#frame-report` as JSON. Ready signal: `#frame-report[data-ready="1"]` (merged JSON in its text and in `window.frameReport`); the claude-shaped frame's message carries `cookieNames`, the sa-frame's carries `storageAccess` / `hasStorageAccess`.
  - The privacy panel is opened with chrome `evaluate` `togglePrivacy(true)`, which is in the evaluate seam.
  - **Apparatus limit (found 2026-10-05, sortie 02 Leg 01 AC10):** the MCP `click` (`sendInputEvent`) is delivered to the **top** document. Its `mousedown` target is the `IFRAME` element, and it never routes into a cross-site out-of-process iframe. So no automated click can give a cross-site frame the user activation that `requestStorageAccess()` needs; without it the call rejects regardless of policy, a false pass. **Storage Access is therefore not asserted here.** It is unit-pinned (sortie 02 AC8, both permission handlers in both states) and verified live by the operator in the sortie 02 HAT using the fixture's `/b/sa-frame` button.
  - The isolate row is addressed by `[data-shield="isolate"]`, never by a bare `.shield-count`: every row has one (the count element exists on every row and is `.hidden` with empty text when not shown). Rows: `[data-shield="enabled|block|strip|isolate|farble|pause|restart|foot"]`. Notes: `[data-shield-note="enabled"]` (master) and `[data-shield-note="isolate"]`. Restart control: `#shields-restart` (a real `<button>`, label `Restart now` then `Restart Goldfinch`) with `#shields-restart-note`. Footer: `[data-shield="foot"]` holds `.shield-foot-note` (restart line, `.hidden` unless pending) beside the always-present `Reload to apply` button. The settings page uses the same `#shields-restart` / `#shields-restart-note` ids plus `#shield-enabled-note` / `#shield-isolate-note` and the checkboxes `#shield-enabled|block|strip|isolate|farble`.
  - **Driving panel controls (R2-6).** Read each control's rect via chrome `evaluate` (`document.querySelector(sel).getBoundingClientRect()`) and click chrome-relative at its centre. Scroll `#privacy-body` so the control is in view first. **Re-read the rect before the second (confirm) click**: the control is patched in place and stays put, but the layout may shift when the confirm note appears.
  - **Settings page.** Open it with chrome `evaluate("kebabActionSettings()")`, never `openTab`. Admin `evaluate`/`click` reach the internal tab (find its wcId via `enumerateTabs`).

- **Log-matching rules (load-bearing).**
  - `/b/frame` assertions match a log entry on `path` plus `search`, within the step's own `ts` window.
  - `/b/sa-frame` and `/favicon.ico` lines are never cookie evidence. Favicons are fetched main-side and never carry jar cookies.
  - **Never restart the fixture mid-run**: `serve.mjs` truncates its log on start.
- **Session restore replays every open tab** within about 0.5 s of each relaunch, often before the MCP listener is up, including `/b/set-fp` and the C embed. After a relaunch, judge only the fresh tab's entries, timestamped after its `openTab`.
- **Restart attestation (steps 13–15), a hard gate on every restart.** After the confirm click, in order: (1) the **old PID exits** (`ps -p`); (2) a **new PID is alive and listening on `{port}`** within a **bounded wait of up to 30 s** (poll `ss`; it proves the single-instance lock hand-off: if the relaunched child loses the lock and exits, that is a **fail** and gets recorded); (3) the Executor **re-attaches** with a fresh `initialize`/connect (the old MCP session died with the process) using the **same** `adminKey`, which must authenticate (no re-mint); (4) `window.goldfinch.shieldsIsolationState().isolateEffective` **flipped**. Track the new PID as "this run's PID" from then on. wcIds are reused by session restore, so they are **not** a relaunch signal.
- **Pending state is read, never inferred.** Before any restart, assert `isolateEffective` (via `shieldsIsolationState()`) and the panel copy agree with the step's stated state.
- **Panel row lookup:** use `[data-shield="isolate"]`. Never `:has(.shield-count)` (every row now carries a count element, hidden when empty).

## Observables Required

- **http (ground truth):** the fixture JSONL log. It shows which cookie names reached which host and path. Read it via shell.
- **browser:** the top-frame DOM via `evaluate` (`#frame-report`, `document.cookie` on first-party pages), and the chrome privacy panel via `getChromeTarget` plus chrome `evaluate`: the isolate row's `.shield-count` text, the restart-pending copy, and the permission list.
- **shell:** PID liveness and the port listener across the app-driven restarts (steps 13–15), `ss`/`ps`, and teardown.

## Out of Scope

- **Storage Access API.** Automated clicks can't reach a cross-site out-of-process iframe (see Preconditions). It is covered by sortie 02 AC8 unit tests and the HAT.
- **Real third-party sites** (claude.ai and others). This spec is fixture-only; live sites are the sortie 02 HAT.
- **Privacy-panel visual layout and a11y.** Copy, state and the Restart now flow are asserted above; pixel layout is eyeballed in the HAT, and axe states run via `npm run a11y -- --restart-states` (`docs/dev-testing.md`).
- **The packaged-build startup path** (AppImage). This spec runs the unpacked dev build only.
- **Per-site pause semantics** for the other strategies (`block`/`strip`/`farble`). Unchanged by this work, and covered by `core-browsing-shields`.
