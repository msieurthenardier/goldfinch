## Findings

**No product defects.** Three findings, all about the apparatus — recorded because two of them
produced convincing false results before being understood, and both are now encoded in `drive.mjs`.

1. **`openTab` takes `jarId`, not `container`.** An early ad-hoc run passed `container: 'burner'`;
   the property was silently ignored, the tab opened in the default (persistent) jar, and the burner
   exclusion "FAILED" with icons visible. That reads exactly like a serious leak and is not one.
   `openTab` also refuses any jarId absent from the registry, so the burner case is **unreachable**
   from this surface — do not attempt to assert it here.

2. **Sheets cannot be dismissed from the apparatus, and a leaked sheet poisons later cases.**
   `pressKey` targets the guest; the sheet is refused to every drive op. A first capture run reported
   3 false failures purely because the sheet from case 1 was still open. Fixed by per-case tab
   isolation (`tab-close` closes the sheet); the driver now also asserts a clean start per case.

3. **⚠ The most dangerous one: focus-dependent detection can fake a full pass.** Blink dispatches no
   focus events to an unfocused document — `el.focus()` sets `activeElement` but fires no `focusin`,
   so the icon is never placed. Because most detection assertions are *negative*, an unfocused window
   makes them **all pass for the wrong reason**. Measured, not assumed: `activateTab` does **not**
   restore it (a programmatic `win.focus()` does not take under WSLg, as CLAUDE.md documents), and
   neither does a synthetic `click` (`sendInputEvent` moves no OS focus). Once the window loses focus
   in this environment, the detection suite is unmeasurable until a human clicks it.
   → The driver now runs a **positive control first and aborts** the focus-dependent suites, printing
   the `hasFocus` reading. Verified in both directions: it aborts and exits 1 on an unfocused window
   (capture still ran, 5/5), and does not over-fire on a freshly focused one (34/34, exit 0).
