## Orchestrator Notes

**Mode**: live two-agent continuation (`SendMessage` available) — both Executor and Validator persist across checkpoints rather than re-spawning per checkpoint. Cache mode: **cold**, satisfied by a fresh app launch immediately before the run, with all three fixture jars cleared to zero bookmarks.

**Apparatus finding — the registered MCP client pointed at a DIFFERENT LIVE BROWSER, not at the instance under test.** The session-registered `mcp__goldfinch__*` tools returned a tab set that does not exist in the instance under test (a `banking` jar showing an unrelated app), while the sanctioned script path returned the real fixtures. Initially misdiagnosed as a stale key serving cached results; run-down after the run established the actual cause, which is worse. There are **three** separate goldfinch MCP registrations on this machine, all with statically pinned bearer keys:

| Registration | Scope | Endpoint |
|---|---|---|
| `goldfinch` — **the one these tools load** | user-scope (`~/.claude.json` top level, so it loads in *every* project) | port **49152** |
| `goldfinch-development` | mission-control `.mcp.json` (gitignored — no key in the public repo) | port 49707 |
| `goldfinch-dev` | goldfinch project scope | port 49707 |

The instance under test listens on **49707**. The loaded registration points at **49152**, which the operator confirms is their **installed production browser** — their real daily driver, running outside this WSL namespace (it answers a genuine HTTP 401 while `ss` shows nothing local on that port). So an agent using those tools would not have driven a ghost; **it would have driven the operator's actual browser** — opening tabs and navigating inside their live personal session, with their real cookie jars. That is a materially more serious hazard than stale data, and it is invisible at the call site: the tools return well-formed, plausible results that simply describe a different browser. The tell was semantic, not mechanical — a jar and a tab that had no business existing in a freshly-fixtured test profile.

Both agents were therefore instructed **not** to use those tools, and a wrapper (`gf.mjs`, scratchpad-local) was built to attach the sanctioned way: `scripts/lib/mcp-client.mjs` `connectAutomation()` reading the freshly minted admin key, per `docs/dev-testing.md`'s attach-don't-pin rule. The two 49707 registrations are aimed at the right instance but carry keys from earlier mints — `curl` with the `goldfinch-dev` key gets no session, confirming the staleness the docs predict.

This is exactly what the spec's precondition — "MCP binding reaches the instance under test (probe: open a tab, confirm it appears in `enumerateTabs`)" — exists to catch, and it caught it. Recommendation for the spec: make that precondition's probe mandatory and explicit about *which* endpoint answered, since a wrong-instance binding is indistinguishable from a correct one by response shape alone.

**Apparatus finding — sheets are observable even though they are not drivable.** `captureWindow` composites the whole window including the overlay sheet, so the Executor could read the edit popover's actual contents (field values, button labels, modal scrim) despite being unable to click inside it. The spec's Preconditions assume less than this; the capability is worth folding into the spec's Observables section on a future amendment.
