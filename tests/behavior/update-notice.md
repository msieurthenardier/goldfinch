# Behavior Test: The browser says when a newer release exists, and asks nothing when told not to

**Slug**: `update-notice`
**Status**: active
**Created**: 2026-11-17
**Last Run**: 2026-11-18 — pass (14/14) on Electron 45.3.3, [run log](update-notice/runs/2026-11-18-02-07-22.md)

## Intent

Verify, on the running browser, the update notice added by Mission 23 Flight 3 and the on-demand check and kebab dot added by sortie 09 (legs `update-check` and `update-notice`): about once a day the browser asks one fixed address whether a newer stable release exists; it believes only a well-formed stable version number from the answer; Settings → About then names the running version and the newer one and offers the release page; and with the setting off it makes no request at all. Unit tests cover the version comparison, the response validation and the schedule with an injected clock; what only a running browser can show is what the request actually carries on the wire, that the page renders main's state at boot and on change, and that the control opens main's own address in the right window.

## Preconditions

- Goldfinch running in dev mode with a **fresh profile**, its output captured to a file the run can read. With `<scratch>` a run-private directory: `cd <repo> && env -u XDG_DOWNLOAD_DIR HOME=<scratch>/home XDG_CONFIG_HOME=<scratch>/xdg GOLDFINCH_AUTOMATION_DEV_MINT=1 GOLDFINCH_AUTOMATION_ADMIN=1 GOLDFINCH_UPDATE_TRACE=1 GOLDFINCH_UPDATE_CHECK_URL=http://127.0.0.1:8237/latest GOLDFINCH_MCP_PORT=<free port> npm run dev:automation -- --proxy-server=http://127.0.0.1:9 > <run-log> 2>&1 &` (record the pid of the `electron` main process, not the npm wrapper, for the stop). The admin key is the `adminKey` in the `AUTOMATION_DEV_MINT {…}` line of that file; attach with `connectAutomation({ port, key })` (`scripts/lib/mcp-client.mjs`). **Never** a registered MCP server. Every relaunch mints new keys: re-read the (last) line and re-attach. The first request arrives about 1 s after the app is ready (the dev override shortens the 60 s delay).
- **The scratch downloads folder** (step 7 starts a real download): with `HOME` and `XDG_CONFIG_HOME` in scratch, **no** `user-dirs.dirs` in the scratch config home and `XDG_DOWNLOAD_DIR` unset (the launch command above unsets it), the browser's downloads folder is inside `<scratch>` (measured on Linux: the scratch `HOME` itself). The run proves this **before** step 7 by starting one page-initiated download from a loopback fixture in a tab (a small server answering `Content-Disposition: attachment` on a free `127.0.0.1` port; loopback bypasses the proxy) and reading its `savePath` from `downloadsList` - and **aborts without pressing the button if that path is not under `<scratch>`**. It lists the scratch downloads folder before and after step 7.
- **The dead proxy keeps the run off the internet**: it makes every non-loopback request fail locally, so the release-page tab opened in step 6, the installer download of step 7 (a github.com address) and any outside tab the dev profile restores never leave the machine. Step 7's address is the app's own github.com address even in a dev build, so the proxy is the only fence: step 1 must show it dead, and if a download of step 7 ever shows `completed` or `received` above zero, stop, quit and report. Loopback addresses bypass it, which is how the fixture is reached.
- The fixture `tests/behavior/fixtures/update-check/server.cjs` listening on `127.0.0.1:8237` (and its redirect-target port, `8238`; `--port` / `--redirect-port` override) **before** the browser starts, started with `node tests/behavior/fixtures/update-check/server.cjs`; its initial mode is `higher`. Control paths: `/__mode?m=<mode>` (modes: `higher`, `equal`, `lower`, `prerelease`, `malformed`, `not-json`, `redirect`, `http-500`, `oversize`), `/__log` (JSON `{log, redirectLog, mode}`; each entry has `method`, `path`, `headers`), `/__reset` (empties both logs, keeps the mode).
- The setting "Check for new versions" is on (the default) in the dev profile at launch.
- **How the run acts on a page control**: `click` takes viewport coordinates of the tab, not a selector. The About section is below the fold and the page scrolls smoothly: `evaluate` `document.getElementById('<id>').scrollIntoView({block:'center'})`, wait about 1.2 s, then read the centre with `getBoundingClientRect()` and `click` there. `evaluate` takes `expression` (a single expression: `a; b` is a syntax error — use a comma or an IIFE) and, in the chrome, cannot `await` at top level (use `.then`). `enumerateTabs` rows carry `wcId`, `windowId`, `jarId`, `url`. **How it opens Settings**: `evaluate` `kebabActionSettings()` on the chrome target (never `openTab`, which cannot open an internal page). **How it opens a second window**: `evaluate` `window.goldfinch.windowCreate()` on the chrome target, then `enumerateWindows` for the new window's `chromeWcId`; open its Settings with `kebabActionSettings()` on that chrome wcId.
- **The 30-second gap (Check now)**: main refuses a Check now within 30 s of the last completed check (the boot-time check, a scheduled one, a previous press, or the check a toggle back on starts — each completed check restarts the gap). Every step below that expects a request from a press starts **at least 30 seconds** after the most recent of those; the dev build's first check runs about 1 s after boot, so the first press waits until the boot check is 30 s old. A press inside the gap is answered `too-soon` and makes no request (step 11 asserts exactly that).
- **The kebab button is chrome DOM and is asserted**: steps 10-12 read `#kebab` (class `update-waiting`, `title`, `aria-label`, bounding rectangle) and `#kebab-update-note` by `evaluate` on **each** window's chrome target (the dot is per window). Only the kebab **menu** (its "Update available" item) is by-eye.
- **Non-vacuity**: before these legs the browser made no such request and the About section held one placeholder sentence.
- **Apparatus (act)**: `evaluate`, `click`, the fixture's control paths over HTTP. **Apparatus (observe)**: the fixture's request log; `readDom` / `readAxTree` on the `goldfinch://settings` tab; `enumerateTabs` / `enumerateWindows`; the captured output for `[update-check] outcome=<code>` lines (printed only with `GOLDFINCH_UPDATE_TRACE=1` on an unpackaged build). Codes seen: `newer`, `current`, `bad-tag`, `bad-json`, `http-500`, `too-large`, `redirect`, `disabled`.
- **Evidence the run must keep**: the `wcId` each read, accessibility tree and screenshot targeted; for the second window, a `captureWindow` of that window (a tab screenshot of the same page in two windows is byte-identical and shows nothing about the second). The first request can already be in the fixture's log when step 1 ends — step 2's wait may be zero.
- **Notes from the second run**: if the screenshot of the failed probe tab in step 1 itself fails, the census row is the evidence. In step 4, set the fixture's mode first, then click off, then on. In step 6 any failed load satisfies the row (the code seen was a network-changed error, not a timeout). In step 7 poll until the record is `interrupted` (about 50 seconds here; allow 90), and back two claims with a recorded check: "no native dialog" by a window census taken straight after the click showing no window beyond those the run opened, and "the real downloads folder untouched" by every record's save path lying under the scratch root. Step 7 judges the downloads **page**, not the toolbar indicator's count — the indicator counting an interrupted download as in progress is a known defect outside this spec. The teardown port check includes the MCP port.
- **Unobservable, not asserted here**: the downloads popup sheet (the indicator's label and the downloads page are what step 7 reads); the Windows and macOS installers (the choice is unit-tested; the real download there is the operator's check); the kebab menu's "Update available" item (the kebab sheet cannot be read by automation) — `[by-eye]`, walked in the flight's acceptance leg. The 24-hour repeat is unit-tested, not waited for. The real GitHub address is never contacted. That a *failed* check leaves an existing notice in place is unit-tested only: the one way this test can trigger a new check is turning the setting off and on, and turning it off clears the notice by design.
