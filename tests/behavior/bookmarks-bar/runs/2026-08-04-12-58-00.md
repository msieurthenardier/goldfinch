**Attestation hygiene — the Validator's proposed standing rule, worth promoting into the crew prompts:**
> When an operator or Executor attests to which row/item/tab an action targeted, verify by **immutable identifier** (id, wcId) against a banked pre-action snapshot. Never accept a name/title-based confirmation as sufficient when multiple similar rows are in play.

Its proof is this run's checkpoint 10: a title-based check on "Debian GNU Linux Project" would have found it unchanged and **confirmed the wrong story**. Refinement it added: bank the snapshot *immediately before* the action, not at the nearest earlier checkpoint — and, for any action that could produce an async side effect later asserted as "preserved", take an immediate post-action read at the time of that action. That second half is what would have closed checkpoint 11's unobserved favicon window.

**A proposed follow-up, checked and closed — recorded so nobody re-litigates it.** The Executor proposed a unit test for `sanitizeRow` rejecting `javascript:` URLs, having exercised that only incidentally. Checked against the suite before accepting: already covered on the write paths (`bookmarks-store.test.js:179-185` for `add`, `:268-276` for `update`), and the read path's drop-with-siblings-kept at `:126-135` — using a **mid-list** bad row, which is the case this run's checkpoint 12 amendment was partly motivated by.

The Validator then verified that independently rather than taking the grep on faith, and went a step further: `validUrl` (`bookmarks-store.js:75-77`) is called from exactly **three sites — `add:167`, `update:201`, `sanitizeRow:121` — all invoking the same module-scoped function**, which delegates to `isSafeTabUrl`. Not three implementations that agree; one function, three call sites. Chaining the existing tests therefore already closes the gap: there is no path where `javascript:` survives `sanitizeRow` while being rejected by `add`/`update`, short of editing `sanitizeRow` to bypass `validUrl` entirely — which would break on *any* invalid scheme, including the `about:blank` already tested. A dedicated `javascript:`-on-read test would be a parametrized duplicate of an already-proven transitive fact.

**Disposition: no follow-up action.** (Its earlier answer had argued for adding the test on scheme-allowlist grounds — that `javascript:alert(1)` is a syntactically *valid* URI, so what is really enforced is a scheme allowlist a refactor could silently drop. The same-function-object finding supersedes that: the allowlist cannot drift between paths because there is only one path.)

**Accumulated confidence on the fix**: the overflow/chevron repair validated at 7-REVERIFY survived two further full quit/relaunch cycles (checkpoints 11 and 12) without regressing, rendering cleanly from cold boot at the same 8-visible/2-hidden partition.
