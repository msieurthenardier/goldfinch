# Behavior Test: Cross-view keyboard navigation (chrome ↔ guest)

**Slug**: `chrome-guest-keyboard-nav`
**Status**: active
**Created**: 2026-07-07 (re-authored 2026-08-27 for Mission 17 Flight 1 — issue #174)
**Last Run**: 2026-08-28-01-56-28 (pass — 15/15 on the Leg 2 build; see `chrome-guest-keyboard-nav/runs/2026-08-28-01-56-28.md`; prior: `runs/2026-08-28-01-01-15.md` pass 12/12 on the 12-row Leg 1 revision; `runs/2026-08-27-23-14-02.md` fail 8/12 on the pre-fix build; lineage `runs/2026-07-08-21-06-32.md` pinned the behaviour this re-authoring reverses)

## Intent
Verify keyboard reachability of page content across the multi-`WebContentsView` boundary. Before Flight 1,
no keyboard path ever granted a guest OS focus (Enter in the address bar `blur()`ed without focusing the
guest; the only guest `.focus()` preserved focus it already had), and any unmodified Tab inside a guest was
intercepted main-side (`cross-view-nav.js` `'tab-handoff'`) and ejected to the address bar — a WCAG 2.1.1 /
2.4.3 Level-A exclusion (maintenance report 2026-08-27, F48). Flight 1 introduces **F6** (chrome → content),
a guest-side **tab-boundary** signal (forward Tab on the last tabbable / Shift+Tab on the first → chrome),
and returns mid-page Tab to Chromium. This is a render/focus-layer property of the *running* app — which
view holds OS keyboard focus after a key — invisible to the unit suite, so it needs a behavior test. Covers:
(a) **F6 enters the page** on its first tabbable; (b) **mid-page Tab stays in the page**; (c) **Tab past the
last tabbable returns to `#address`**; (d) **Shift+Tab before the first returns to the chrome's last
control**; (e) **Ctrl+L from the guest still focuses the address bar** (the pre-existing bridge, regression
net); (f) the same on an **internal `goldfinch://` page** (trusted preload, bundled — DD5) and on a page
with **no tabbables** (immediate handoff); **(g)** F6 / Shift+F6 **from the guest** reach the chrome (Leg 2, DD6);
**(h)** Enter in the address bar hands focus to the page once the navigation commits (Leg 2, DD7). Re-authored 2026-08-28 after run `2026-08-27-23-14-02` to the
Chrome-like F6 landing contract (DD1), with the chrome-side `onTabBoundary` collector armed in setup as the
instrument that separates "signal delivered" from "chrome acted".

## Preconditions
- Goldfinch running via **`npm run dev:automation`** (loopback MCP transport); `GOLDFINCH_MCP_PORT` pinned.
- **Apparatus-wiring litmus passed**: the MCP client is bound to *this* instance at **admin** tier —
  `getChromeTarget()` returns this instance's chrome `wcId`; `enumerateTabs()` lists *this* instance's tabs.
- The Flight 1 Leg 1 build is running: `F6` present in the automation `KEY_MAP` (`pressKey(C, "F6")` accepted);
  both guest preloads bundled (`npm run build:preload` ran — `prestart` does this).
- Fixtures served over HTTP: `python3 -m http.server 8000 --directory tests/behavior/fixtures/keyboard-nav`
  → `http://127.0.0.1:8000/form.html` (three text inputs `#f1 #f2 #f3` and a button `#b1`, in that DOM order),
  `links.html` (three links `#l1 #l2 #l3`), `empty.html` (text only, no tabbables), `iframe.html` (one input
  `#top` then an `<iframe id="fr">` whose document has one input `#inner`).
- The chrome's media and privacy panels are **collapsed** (default) — collapsed panels are `visibility:hidden`
  after Leg 1 and leave the tab sequence.

## Observables Required
- mcp (MCP tool results over loopback — `pressKey`/`typeText`/`evaluate`/`readAxTree`/`enumerateTabs`/
  `getChromeTarget`/`openTab`/`activateTab`/`readDom`; measured via the Goldfinch MCP client at
  `127.0.0.1:$GOLDFINCH_MCP_PORT`). The `chrome-devtools` MCP does **not** qualify (it launches its own browser).
- browser (which view/element holds keyboard focus). **Read-path note (apparatus, load-bearing):** focus is read
  via **`evaluate(wc, "document.activeElement && (document.activeElement.id || document.activeElement.tagName)")`**
  on the **gaining** view (web guests and the chrome only — `evaluate` is refused on internal guests; use
  `readAxTree(wc)`'s focused node there), and proven by **`typeText` landing there** where the element accepts text — never by
  `readDom` (does not serialize `activeElement`) and never by `document.hasFocus()` (unreliable under WSLg —
  programmatic focus fires no focus event). The **losing** view's `activeElement` goes stale (Chromium does not
  blur a sibling view) and is not evidence. `readAxTree(wc)`'s focused node corroborates for non-text controls.

## Out of Scope
- Every `evaluate` expression that declares a binding is wrapped in an IIFE — a top-level `const` persists in
  the view's main world for the document's life and a later redeclaration throws (apparatus fact, run
  2026-08-27-23-14-02). Chrome-side `readAxTree` dumps embed the `file://` home path — scrub before saving.
- Apparatus (run 2026-08-28-01-56-28): the chrome's RootWebArea is co-flagged `focused` with the landing control on the
  `handleCrossView` paths (Ctrl+L, F6, Shift+F6) and not on boundary handoffs (control only) — a DD6-vs-DD4
  discriminator; build `evaluate` args containing single-quoted JS literals via `json.dumps`; `readDom` output is
  JSON-escaped (`id=\"f3\"`).
- Chrome-internal Tab wrapping order (the old gap (c)) — superseded: the chrome sequence now ends at its last
  visible control and hands to the page via F6/boundary; a dedicated chrome-order spec can follow Leg 2.
- Omnibox suggestion announcements (F49) — Leg 3 spec.
- Popups (M14): the boundary signal is a no-op in a popup (no chrome to receive it) — accepted for Leg 1.
